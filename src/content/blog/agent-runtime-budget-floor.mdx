A token budget sized to a child agent's task can be gone before the task is done.
A coding agent re-sends its system prompt, tool definitions and workspace context on every turn.
In six August runs, one coding agent on one model settled at 31,000 to 63,000 input tokens after one to four turns.
Its parents had budgeted 2,000 to 20,000.
Measure that fixed cost for your own agent and model, refuse smaller budgets in your own code before dispatch, and put the hard stop on dollars.

This post first said our runtime refuses such budgets against a measured floor.
It does not, and it did not when we published.
We removed that refusal five days before the post went up, and the post went out describing code that no longer existed.[^removed]
That was our mistake.
Today the runtime has no per-agent floor: it reserves a budget, reconciles what the child spent, and records an overrun instead of refusing it up front.

## A child agent pays for its scaffolding on every turn

The model you call in a loop has no memory between requests.
So every turn of a coding agent sends the same opening material again: the instructions, the tool catalog, and enough of the workspace to act on.
Then it adds whatever the last turn produced.
The task itself is a small part of that bill.

That is why a parent's instinct fails.
Say a parent writes 8,000 tokens for a one-line dependency bump, because the patch is a few lines.
In our measurements the cheapest child run settled at 31,211 input tokens.
That budget is gone long before the child finishes.

Context management moves the cost around but does not delete it.
Each turn resends a history that grows every turn, so the loop has two jobs:[^cache]

- **Compaction:** once input tokens pass a threshold, replace older turns with a summary, or the run outgrows the context window.
- **Caching:** a cache hit needs an exact prefix match, so changing the tools, the model, the system prompt or an earlier message mid-run causes a miss that pays the whole prefix again. Append a new message instead of editing old ones.

The scaffolding stays either way, because the model needs the tools and instructions on every turn.
Prompt caching helps against the cap: our runtime counts input minus cache reads, plus output, against a token budget.[^charge]
So a cache hit on the repeated prefix is cheaper against the cap.

## A budget that is too small turns a good result into a failure

The failure that made us look was not a crash.
One child wrote its artifact correctly, then kept going past its budget and was recorded as failed.

<Figure n={3} figure={overrun} kicker="One child run, August 2026" headline="A child that wrote a correct artifact spent 76,657 tokens against a 12,000 budget and was marked failed" />

A false negative like this is worse than an honest failure.
Your retry logic sees a failed child and runs it again with the same impossible budget.
Your eval sees a model that cannot do the task, when the model did it.
Someone then rewrites the prompt to fix a problem the prompt never had.

## One measurement is not a floor

We first answered this with a constant.
The runtime took the cheapest of the six settlements and refused any child budget below it, for that agent and model.
Then we removed it within days.

The number was one agent on one model, measured once.
Change the model, the system prompt, the tool list or the size of the repository and the fixed cost moves.
A constant in the runtime would refuse good budgets for agents we never measured, or wave through bad ones.
The commit that removed it called the floor guessed, and it was.

So read the figures above as one pairing at one date.
They show the size of the gap between what a parent guesses and what a coding agent spends.
They are not a number to copy into your config.

## Tokens are settled after the fact, and dollars are refused at each charge

The two caps work differently, and the difference is the answer to "is it enforced mid-turn?"

**Token budgets settle after the spend is measured.**
When a child spawns, the runtime moves free capacity into a single-use reservation.
Reconciliation then commits the measured spend and refunds the rest.
If the child spent more than its reservation, reconciliation returns a budget violation and the overspend comes out of future capacity.
When the provider reports no token count, the runtime keeps what it observed as a lower bound and lets the run continue.[^ledger]

That design keeps the books honest.
The ledger records an overrun; it does not refuse one up front.
You find out at settlement.

**Dollar caps refuse each charge past the cap.**
A fleet's `budgetUsd` is a hard cap the Platform enforces at every charge, mid-turn included,[^402] and the `costUsd` a run reports is model spend only, with sandbox time billed separately.
A turn already in flight is refused at its own next charge, and a refused turn ends `budget_exhausted`.

The fleet's policy is also checked before any sandbox is provisioned.

## The pre-dispatch gate cannot see the token budget

The runtime does have a gate that runs before a child exists.
It is opt-in, and it runs on every spawn before an assignment is minted or budget is reserved.
A refusal there leaves nothing behind: no assignment, no reservation, no journal entry, no worker.
An error thrown inside it is not a refusal; it propagates to the caller.

It can refuse for four reasons today: the model route, a full bridge, a tool it cannot mount, or a profile it cannot provision.[^preflight]
None of them is about tokens.
The context the gate receives does not include the child's token budget, so you cannot put a budget check there.
We think it should, and we filed an issue to add it.[^issue]

## Counting tokens checks one request, not a run

Provider token counters look like a preflight, and for a single call they are one.
Anthropic's endpoint counts the tokens in a message before you send it, for free within its [rate limits](https://platform.claude.com/docs/en/build-with-claude/token-counting).
Its docs call the count an estimate, and it does not support Managed Agents.

An agent run is many requests, and each one re-sends the scaffolding plus the growing history.
Counting the first one tells you the size of the scaffolding, which is useful.
It does not tell you what four turns will cost.

## Refuse a budget below what you have seen

Until the gate can see the budget, run the check in your own code.
This is the same method we used in August, moved to the caller.

Record the settled input tokens for every child, keyed by coding agent and model.
Before you spawn, refuse any budget below the smallest settlement you have seen for that pairing.
Treat a pairing you have never run as unknown: admit it, and record what it spends.
Compare like with like: if your budget counts input minus cache reads plus output, record settlements in that unit too.

Sketch, not run: adapt it to your own ledger.

```ts
// Smallest settled input tokens seen per coding agent and model, from your own runs.
const smallestSeen = new Map<string, number>([
  ['pi|tangle-router/glm-5.2', 31_211], // our August sample; measure your own
]);

type Admit = { ok: true; measured: boolean } | { ok: false; raiseTo: number };

function admitChild(agent: string, model: string, maxInputTokens: number): Admit {
  const seen = smallestSeen.get(`${agent}|${model}`);
  if (seen === undefined) return { ok: true, measured: false }; // unknown, not zero
  if (maxInputTokens < seen) return { ok: false, raiseTo: seen };
  return { ok: true, measured: true };
}

function recordSettlement(agent: string, model: string, inputTokens: number) {
  const key = `${agent}|${model}`;
  const seen = smallestSeen.get(key);
  if (seen === undefined || inputTokens < seen) smallestSeen.set(key, inputTokens);
}
```

Use the minimum, not the median.
A median would refuse budgets that a short, lucky run proves are enough.
Keep the agent and model in the key, and start a fresh key when you change the system prompt or the tool list.
Return the number in the refusal so the parent can raise the budget instead of retrying the same one.

Our rule: a token budget below your smallest observed settlement is a bug in the parent, so refuse it before dispatch. Anything above it, let the runtime account. Put the cap that must hold on dollars.

## How we tested

We read every source on 17 Nov 2026, except OpenAI's Codex agent-loop post, Anthropic's prompt caching and compaction docs and the re-recorded cancel-on-cap run, read 18 Nov 2026.

- **The August measurement.** All three figures copy numbers from the [commit message of agent-runtime #685](https://github.com/tangle-network/agent-runtime/commit/012762f00b012507d924edd6f060e5f7edec9b3a), recorded on 1 Aug 2026. Six live children ran the pi coding agent on tangle-router/glm-5.2. Parent runs authored the four budgets in Figure 2. The overrun in Figure 3 is run proof-native-tools-20260801b. This is one agent and one model at one date.
- **The removal.** [agent-runtime #736](https://github.com/tangle-network/agent-runtime/pull/736), merged on 4 Aug 2026, deleted the floor in a commit titled "fix(supervise): remove guessed worker token floor". The refusal reason and its constant are absent from the runtime's main branch as of 17 Nov 2026. The changelog does not mention the removal.
- **Today's token budget.** The header of the [runtime's budget ledger](https://github.com/tangle-network/agent-runtime/blob/main/src/runtime/supervise/budget.ts) on main describes conserved accounting (total equals free plus reserved plus committed), reservation and reconciliation, overspend returned as a budget violation, unknown counts kept as a lower bound, and tokens charged as input minus cache reads plus output.
- **The pre-dispatch gate.** The preflightSpawn section of the [runtime's MCP API docs](https://github.com/tangle-network/agent-runtime/blob/main/docs/api/mcp.md) lists its timing, what a refusal leaves behind, and its four refusal causes. Its context type has no token budget field.
- **Dollar caps.** Fleet budget behavior is from the sandbox SDK typings, version 1.0.438; the 402 refusal and KeyBudgetExhaustedError are from the sandbox SDK changelog. That costUsd is model spend only, with sandbox time billed separately, is from the sandbox SDK README. The two fleet examples above are recorded production runs; the receipt above each one gives its date and reported cost. The under-a-budget run used sandbox SDK 1.0.134 and reported $0.0611 against a $1 cap. The cancel-on-cap run, re-recorded on 18 November 2026 with SDK 1.0.443, reported $0.2129 against a $0.20 soft line and a $2 hard cap, and `fleet.cancel()` counted all six agents.
- **Token counting.** Anthropic's [token counting docs](https://platform.claude.com/docs/en/build-with-claude/token-counting), read on 17 Nov 2026.
