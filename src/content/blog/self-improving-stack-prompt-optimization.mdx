GEPA and MIPROv2 will find a prompt that scores higher on the examples they searched.
Whether that prompt is better for your users is a separate experiment.
Build that experiment before the first optimizer run: a metric you have debugged, a test split the optimizer never touches, and a hand-edit arm to beat.
The search is the cheap part.
In two of our own runs, proving a candidate cost four to eleven times what finding it did.

We learned this by getting it wrong.
Our 1 June 2026 optimizer run on a transaction-extraction task went from 0.625 to 1.0, and we archived it as a proven lift.
The baseline prompt had been written without the output schema, and the optimizer was handed that schema.
One method also picked its winner on the same cases we reported.[^extraction]
The winning prompts mostly put back what we had withheld.

## GEPA runs your examples, scores them and rewrites the prompt until the budget runs out

Both optimizers treat your agent as a program with editable text inside it.
Before GEPA runs, you supply the agent with its prompt exposed as a parameter, training and validation examples, a metric, a reflection model and a budget; it then runs the examples, scores them with your metric, has the reflection model propose new text, rescores, and keeps the best until the budget runs out.[^dspy-loop]
[MIPROv2](https://dspy.ai/api/optimizers/MIPROv2/) searches instructions and few-shot examples together.

Neither can add a tool, a worker or a bigger budget.
If the trace shows the agent never had the tool it needed, no sentence will fix that.

The GEPA authors report beating MIPROv2 by more than 10% on their own benchmarks at matched rollout budgets.[^gepa-paper]
We have not run that head-to-head, and we would not pick between them before the metric and splits exist.

## Your metric is the spec, so make it explain itself

A GEPA metric can return a score and a sentence of feedback.
The reflection model reads that sentence, so it learns why a case failed, not only that it failed.
This is DSPy's example, reformatted:

```python
return dspy.Prediction(score=0.0, feedback="Don't reference the input season verbatim.")
```

Good feedback carries what a reviewer would say.
Dropbox built theirs from the size and direction of each disagreement with a human rater, plus the rater's written rationale.
Simon Willison's feedback named the gold answer, one correct SQL query and the values the agent missed.

The optimizer will chase whatever the metric rewards, bugs included.
In Willison's run on Datasette Agent's SQL prompt, two of three apparent baseline failures were scorer bugs.[^willison]
One was a correct "no books" answer with no literal zero in it; the other was a tie the checks did not accept.
Fixing the metric moved the baseline's held-out score from 81.7 to 95.0, more than the optimizer moved it in either direction.
Read your metric's verdicts against real transcripts before an optimizer ever sees it.

## Lock away a test set, and keep it out of prompts, examples, memory and tuning

Keep test cases out of prompt text, few-shot examples, preference memory and manual tuning, and use three disjoint sets: training cases propose edits, validation cases choose the winner, and the locked test set is the only score you report.
A score the search selected on is a selection score, and it overstates the gain.
If you omit the validation set, GEPA selects on training data, which DSPy says "deliberately allows prompts to overfit those examples."

There is no standard ratio.
DSPy's advice is to keep most examples in training and make validation the smallest sample that still looks like production.

Willison's run shows why the locked split matters.
He gave GEPA 20 training questions and held out 10.

<Figure n={1} kicker="Simon Willison, Datasette Agent" headline="GEPA gained 5 points on the questions it trained on and lost 10 on the questions it never saw" figure={willison} />

GEPA fixed the one training failure its feedback showed it.
It also added advice that sent the agent into a loop on a held-out question, because the advice clashed with display rules elsewhere in the same prompt.

Leaks hide in more places than a reused test file, as the agent-eval [trajectory guide](https://github.com/tangle-network/agent-eval/blob/main/docs/feedback-trajectories.md) warns.
Our extraction run leaked through an inner gate: the same held-out cases fed one optimizer's acceptance step and the final comparison.
Whatever you measure that way is a selection score, and our 0.625 to 1.0 was one.

## Count independent cases, not runs

Running a case ten times tells you how noisy the agent is on that case.
It says nothing about cases you have not seen.
The agent-eval [statistics guide](https://github.com/tangle-network/agent-eval/blob/main/docs/statistical-evidence.md) puts it plainly: "Repeating one incident 100 times supplies one incident."
If several cases paraphrase one incident, group them as one unit.

agent-eval needs 20 paired scenarios before it will bootstrap an interval on a continuous score, and once you declare the independent unit (a `claim` or `independentUnitByScenarioId`), repeats of one case count as one unit.
That is the estimator's floor.
Your sample size comes from the variance you saw in development and the smallest gain worth shipping.
Willison's 10-question holdout made every question worth 10 points, so one regression was the whole result.

## The search is cheap; budget for the proof

Three things set the bill:

- **The `auto` budget knob:** it sets how many candidates are tried, and each is scored on the whole validation set, so cost grows with validation size times candidates.
- **The proof:** the runs after the search that show the gain holds.
- **Reflection-model calls:** the optimizer's own calls, which your cost record may leave out.

In DSPy the budget knob is the `auto` setting.
The light setting evaluates around six candidate prompts, and medium and heavy go further.
A larger validation set leaves budget for fewer candidates.

Our two logged CodeTraceBench runs show where the money went.

<Figure n={2} kicker="agent-eval audit, CodeTraceBench" headline="Proving each candidate cost 4 to 11 times what the GEPA search that found it did" figure={promptOptCost} />

The search cost a few dollars.
Telling whether its winner was real took several comparison runs and most of the money.
For scale, the GEPA paper's whole results table cost $86 for GEPA and $76 for MIPROv2 on GPT-4.1 mini, summed over every task.[^gepa-paper]

Check that your cost record includes the reflection model.
In our extraction run, the optimizer called the model directly and its usage was discarded.
We still do not know what that run cost end to end.

## A higher mean is not a win until the paired interval clears zero

Before you open the test split, fix the metric, the cases, the smallest effect worth shipping, and the rule for when you stop collecting runs.
Then run the baseline and the candidate on the same held-out cases the search never saw.
Take each case's difference, average repeats within each independent unit, and read the interval on the mean difference.
If the interval crosses zero, you have not shown a gain.

We learned this one on our first CodeTraceBench run.

<Figure n={3} kicker="agent-eval audit, CodeTraceBench" headline="GEPA's prompt scored highest, but its paired interval against stock crossed zero on both splits" figure={arms} />

GEPA's instructions scored 0.4809 pooled micro F1 against 0.4285 for the stock prompt.
The paired interval crossed zero on both final splits.
We promoted on the point estimate, because the rule we had registered in advance allowed it.
We would not write that rule again.

agent-eval's gate returns ship, hold, need more work, or a model or architecture ceiling.
Deploy only on ship.

## A selection win does not travel on its own

A selection win can reverse on fresh data, and optimizing one objective can trade away another.
Our next GEPA challenger improved its selection objective by 0.064 on 12 cases.
On two fresh agent families it lost to the prompt already shipping, and the gate rejected it.
In a later search, macro-F1 optimization raised macro F1 from 0.163 to 0.187 on selection data, while micro F1 fell from 0.34 to 0.19 and recall fell by more than half.
Report every metric your users feel, not only the one you optimized.

## Run a hand-edit arm, and give the baseline every requirement the optimizer gets

Run a hand-edit arm from the same evidence, and never start from a baseline missing requirements the optimizer is given, because that manufactures a gain; our audit concluded that these runs "do not establish optimizer superiority over a direct edit."
The manual arm in Figure 3 scored below stock, and its gap did not clear noise either.
Our extraction run had no hand-edit control at all.
Its winning prompts mostly added the merchant, amount, date and category fields the baseline left out.
Pasting those requirements in by hand might have scored the same, which is how a thin baseline manufactures a gain.

Willison's run points the same way from the other side.
Its remaining failure needed a rule GEPA could not find, because that failure only appeared in the held-out split: "prefer human-readable identifiers."

So we now run three arms on the same locked test set:

```text
A  baseline    the prompt in production today
B  hand edit   written from the same training evidence the optimizer saw
C  optimizer   GEPA or MIPROv2, with the same model, tools and budget
```

Report C against A and C against B, each with its interval.
If C does not beat B, we ship B if it beats A, and otherwise keep A, because a person wrote B and can defend each line.

## Optimization pays when a working task moves to a cheaper model

Dropbox's relevance judge is the clearest public win we know.[^dropbox]
They moved the judge from o3 to the cheaper gpt-oss-120b, and their tuned prompt lost quality on the new model.
The best DSPy-optimized prompt cut disagreement with human raters by 45% against the original hand-written prompt.
Adapting to a new model went from one or two weeks of manual iteration to one or two days.

The opposite case is a baseline with no headroom.
Willison optimized for gpt-4.1-nano because gpt-4.1-mini was "already near ceiling."
Our AppWorld runs started from competent baselines, and the small run's lift and both GEPA lifts on the scaled run were zero, though our audit notes the null does not show whether the remaining errors were prompt-fixable.
Once nearly every training batch scored 100%, Willison's reflection "had nothing to work with."

Expect the most when you move a working task to a smaller or cheaper model, and when the errors in your traces are ones a prompt can fix.
Expect the least when the baseline already passes nearly everything you can test.

## Test the judge before it becomes the metric

An LLM judge used as the metric is a second model the optimizer will learn to please.
Dropbox could lean on its judge because its scores were measured against human ratings.
agent-eval's version of that check scores known-good and known-bad outputs before the judge decides anything.

Run a trivial baseline through the metric as well.
On one of our test splits, a constant prediction scored 0.568 micro F1 against about 0.180 for the agent.
Most cases labeled the same final step, so a fixed guess beat the analyst.
We retired the split.

## Running GEPA against a TypeScript agent

agent-eval runs in your TypeScript process and calls the agent you already have.
Official GEPA, SkillOpt and DSPy run through a Python bridge, set up as the [campaign proposers doc](https://github.com/tangle-network/agent-eval/blob/main/docs/campaign-proposers.md) describes.
Pick the entry point by who owns the search:

- `compareOptimizationMethods()` lets GEPA or SkillOpt own it, and returns paired final comparisons with uncertainty and cost.
- `selfImprove()` returns a selected prompt, its final comparison and a gate decision.
- `runImprovementLoop()` takes your own proposer, selects on training cases, and compares on disjoint holdout cases whose scores the proposer cannot read.

Whichever you use, search never sees the holdout, the decision runs on disjoint holdout cases, and the shipped prompt stays until the gate says ship.
The cheapest form of that gate runs in CI and fails the build when the candidate scores lower on the same cases.

<Example path="evals/regression-gate" title="CI gate: the shipped prompt against a candidate on real sandboxes" />

In the recorded run, both prompts passed both tasks, so the gate let the candidate through.
Two cases can catch a regression; they cannot show a gain.
We use this as the floor and the paired interval as the bar.
Install from [npm](https://www.npmjs.com/package/@tangle-network/agent-eval) and check the README's install section for the matching Interface and Core lines.

## Keep every candidate, including the losers

A prompt you cannot trace back to its run is a prompt you cannot roll back with confidence.
From each run we keep:

```text
intent of the run, and the split ids for train, selection and test
every candidate prompt, with its scores and the reason it was kept or rejected
the promoted diff against the shipped prompt
model, prompt or config hash, code commit, and cost, including the reflection model
the gate decision and the paired intervals behind it
```

`runImprovementLoop()` writes the selected diff (`promotedDiff`) and the ledger cost (`cost`) into its result.
With `searchHistoryPolicy: 'require-complete'`, agent-eval also refuses to expose final evidence until the search history is closed.
A rejected candidate tells the next person what not to try.
The whole improvement loop around this decision lives in [the harness evolution loop](/blog/self-improving-stack-harness-evolution/).

## Ship the optimizer's prompt only when it beats the hand edit on cases it never saw

Start with the metric: read its verdicts on real transcripts and run a trivial baseline through it.
Lock a test split by source incident before any search.
Run the light budget first, and set aside several times the search cost for the proof.
Ship the optimizer's prompt only if its paired interval against both the baseline and the hand edit clears zero on that split.
Otherwise ship the hand edit, or nothing, and keep the run.
