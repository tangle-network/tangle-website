A model can write a response from text.
An agent must do more: inspect state, use tools, change files, wait for results, recover from failure, and show what happened.

An **agent runtime** is the software around the model that makes those actions possible and records their limits.
This article maps the pieces by the work a person wants done, not by a product catalog.

The right runtime is the smallest one that can perform the job safely.
Adding every available capability before the job is clear only increases the number of places a failure can hide.

## The pieces and their jobs

Tangle exposes several surfaces that can be composed into an agent runtime.

| Need | Tangle surface | Plain-language job |
| --- | --- | --- |
| Choose a model | Router | Find a model, send the request, and record usage |
| Run tools and files | Sandbox | Execute commands and tests inside a controlled environment |
| Operate a website | Browser Agent | Interact with a web application and keep visual evidence |
| Publish repeatable work | Blueprint | Describe a service that operators can run |
| Charge a programmatic buyer | x402 | Request payment before a paid job starts |
| Decide whether work is acceptable | Evidence and result checks | Keep records and apply a task-specific acceptance rule |

The names matter less than the boundary between them.
The router chooses a model; it does not make a file change safe.
The sandbox runs a process; it does not prove that the process produced a correct answer.
The payment layer proves settlement; it does not prove result quality.

## Add capabilities in the order the agent needs them

Start with the action, then add the smallest surface that enables it.

| Agent action | First capability to add |
| --- | --- |
| Answer a question from text | Model access and a record of the request |
| Edit code | A controlled execution environment and artifact capture |
| Use a web application | Browser access, credentials policy, and screenshot evidence |
| Sell a result | Payment, authorization, and a result record |
| Improve its own procedure | Run records, repeatable checks, and a comparison policy |

This order keeps the runtime tied to work a user can describe.
It also makes it obvious when a new surface changes the security or evidence boundary.

## Separate local work from hosted authority

Where a task runs should follow the risk of the action.

| Local or read-only | Hosted or isolated |
| --- | --- |
| Planning and public documentation | Installing packages or starting processes |
| Static analysis of public code | Tasks with credentials |
| Dry-run model requests | Browser actions that change an account |
| Mock service calls | Paid, user-facing, or irreversible actions |

The mistake is not “local” or “hosted” by itself.
The mistake is granting a runtime more authority than the task requires.
Choose the boundary per action, then record which boundary applied to each run.

## Evidence starts before integration

Before connecting several services, prove each boundary separately:

- the router returns a model list and a known response
- the sandbox starts, runs one allowed task, and rejects one disallowed task
- the browser agent can perform one read-only flow and retain its evidence
- the Blueprint definition describes the job and its operator settings
- the payment path distinguishes an unpaid request from a settled request

These are small checks, but they prevent a large integration from hiding which service failed.

The public [OpenAI-compatible router article](/blog/openai-compatible-routers-for-agents), [sandbox explanation](/blog/ai-agent-sandbox), and [Browser Agent repository](https://github.com/tangle-network/browser-agent-driver) describe individual boundaries.

## What the runtime can and cannot promise

An agent runtime can provide tools, state, limits, and records.
It cannot guarantee good judgment by giving the model more components.

| Runtime evidence | Claim it supports | Claim it does not support |
| --- | --- | --- |
| Model request record | Which model route was used | That the answer was correct |
| Sandbox policy and event record | Which limits applied to a process | That the process respected a flawed policy |
| Browser screenshots and actions | What the agent saw and clicked | That the external site accepted the intended change |
| Payment settlement record | That payment cleared | That the paid job succeeded |
| Result check | That a defined condition passed | That every untested condition is safe |

The record should preserve missing information as unknown.
A blank completion event should not become a fabricated success.

## The public runtime boundary

The deeper [self-improving stack series](/blog/series/the-self-improving-stack/) explores how repeatable checks and run records can improve agent procedures.
The [runtime topology post](/blog/self-improving-stack-agent-runtime-topology) explains why a prompt cannot create parallel workers or cancellation by itself.

Those ideas are design boundaries, not promises that every future coordination feature is already in a package.
Use the public repository and release documentation to check which surface is available for the version you deploy.

## The practical decision

Use only model access for a text-only task.
Add a sandbox when the agent needs files, processes, or tests.
Add browser access when the agent must operate a website.
Add a Blueprint and payment path when another party needs to discover, pay for, and run the work.
Add repeatable checks and records when the agent must improve or when a customer needs evidence.

If the agent cannot state which surface produced each action, the runtime is too opaque to debug.
Make the action boundary visible before adding another capability.

## Questions readers usually ask

### What is the minimum runtime for an AI agent?

At minimum, production work needs model access, a tool policy, state, records, and a way to decide whether the result is acceptable.
The exact surfaces depend on the action.

### Why is the runtime more important than the prompt?

A prompt guides behavior.
The runtime determines which actions are possible, what limits apply, and what evidence survives the run.

### Does a larger runtime make an agent better?

Not automatically.
More tools and services create more failure paths and more authority.
Add a capability only when a user action requires it.

### What should I build first?

Name one action, choose its smallest safe surface, record one successful and one rejected attempt, and expand from there.
