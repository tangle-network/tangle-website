A swap page says it will approve 10 USDC.
MetaMask opens on a different network, or asks for an unlimited allowance to an unfamiliar contract.
A page-only test still sees the “Approve” button, clicks it, and reports success.
It passed the web page and missed the security decision the user saw.

MetaMask automated testing has to inspect both sides of that boundary.
[MetaMask](https://docs.metamask.io/) is a browser and mobile wallet.
A dapp, a web application, asks the wallet through the page’s provider to expose an account, switch networks, sign data, or submit a transaction.
MetaMask presents each approval, and if a broadcast transaction is accepted and included, the chain records it.
An allowance prompt must name the token-spending limit and the spender contract receiving it.

Tangle Browser Agent drives a real Chromium session from a goal; `bad` is its command-line program.
Its [wallet-testing guide](https://github.com/tangle-network/browser-agent-driver/blob/main/docs/guides/wallet.md) runs MetaMask or Rabby against a local Anvil chain by two routes.
Background RPC calls from the extension go to Anvil, and page-level RPC interception forwards only calls involving the configured test-wallet address to Anvil.
Protocol and pool data keep using real RPC endpoints.
Run inside a Tangle sandbox, the same goal uses `client.create()` for a machine with its own browser, and `box.prompt()` reports whether the agent run succeeded.
The driver records page actions and screenshots.
A wallet test adds the wallet prompt and the provider response, so a reviewer can compare what the dapp requested, what the wallet displayed, and what happened next.
Read [DeFi Wallet Testing With Browser Agents](/blog/defi-wallet-testing-browser-agent) for the state model and [AI Browser Testing With Evidence Traces](/blog/ai-browser-testing-evidence-traces) for the evidence record.

## Test the wallet boundary a user sees

“Connect” hides several promises.
The application must request the right account access.
The wallet must show the request.
The page must reflect the selected account.
The account and the chain can both change later.

| User-visible action | Application condition | Wallet evidence |
| --- | --- | --- |
| connect | the page shows the selected test account or a clear connected state | requested account access and selected account |
| reject connection | the page stays usable and explains the rejection | wallet rejection and provider error |
| switch network | the page and wallet agree on the chain | requested and selected chain |
| sign a message | the page describes the message purpose | exact message or typed-data prompt |
| approve an allowance | the page names the token and spender | allowance amount, token, and spender |
| submit a transaction | pending, success, and failure states are distinct | transaction details and outcome |
| change account | account-specific data refreshes or the session closes | accountsChanged event and new page state |

Save the page screenshot before the prompt and the wallet screenshot at the decision.
The final page shows whether the application reported the result honestly.

## Use the public provider interface

An [EIP](https://eips.ethereum.org/) is a public Ethereum specification.
[EIP-1193](https://eips.ethereum.org/EIPS/eip-1193) defines a common JavaScript provider API for Ethereum applications and wallets.
Its `request` method makes wallet and chain calls, and its events report connection, disconnection, chain changes, and account changes.
RPC, remote procedure call, is the request-and-response interface the app uses to ask the wallet or chain for state and actions.

Those events are part of the test surface.
An app that never handles accountsChanged keeps showing balances for the previous account.
An app that ignores chainChanged can quote one chain while the wallet signs on another.
An app that treats a rejected request as success leaves a false “Connected” or “Submitted” state.

EIP-1193 recommends 4001 for user rejection, 4100 for unauthorized requests, 4200 for unsupported methods, 4900 for a disconnected provider, and 4901 when the requested chain is unavailable while another chain stays connected.
Record the code when recovery behavior matters.

An illustrative browser-side observer:

~~~typescript
type ProviderError = Error & { code?: number; data?: unknown }
type InjectedProvider = {
  request(args: { method: string }): Promise<unknown>
  on(event: string, listener: (value: unknown) => void): void
}

const provider = (window as Window & { ethereum?: InjectedProvider }).ethereum

if (!provider) {
  throw new Error('MetaMask or another injected provider is unavailable')
}

provider.on('accountsChanged', (accounts) => {
  console.log({ event: 'accountsChanged', accounts })
})

provider.on('chainChanged', (chainId) => {
  console.log({ event: 'chainChanged', chainId })
})

try {
  const accounts = await provider.request({ method: 'eth_accounts' })
  const chainId = await provider.request({ method: 'eth_chainId' })
  console.log({ accounts, chainId })
} catch (error) {
  const providerError = error as ProviderError
  console.error({
    message: providerError.message,
    code: providerError.code,
    data: providerError.data,
  })
}
~~~

[MetaMask Connect](https://docs.metamask.io/metamask-connect/) is MetaMask’s current SDK for connecting supported wallet environments.
It selects a desktop extension, QR-code, or mobile-app connection by environment, so an app using it may not read an injected provider directly.
The test should assert the connection behavior the app supports, not assume the extension is present.

## Make signing a data test

A signing test inspects the exact message, typed-data domain, spender, value, destination, and chain shown in the prompt.
Personal signing presents a message.
Typed signing presents structured fields.
Transaction signing presents a destination, value, data, and gas-related context, according to the wallet and network.

[EIP-712](https://eips.ethereum.org/EIPS/eip-712) defines hashing and signing for typed structured data.
A domain separator lets the wallet show context instead of an opaque byte string.
The standard provides no replay protection.
A nonce, a number used once, stops a signed operation from being reused or applied out of order.
The application still needs a nonce, expiry, chain binding, or another policy suited to its operation.

An illustrative typed-data fixture makes the intended prompt reviewable:

~~~json
{
  "domain": {
    "name": "Example Exchange",
    "version": "1",
    "chainId": 11155111,
    "verifyingContract": "0x0000000000000000000000000000000000000001"
  },
  "types": {
    "EIP712Domain": [
      { "name": "name", "type": "string" },
      { "name": "version", "type": "string" },
      { "name": "chainId", "type": "uint256" },
      { "name": "verifyingContract", "type": "address" }
    ],
    "Permit": [
      { "name": "owner", "type": "address" },
      { "name": "spender", "type": "address" },
      { "name": "value", "type": "uint256" },
      { "name": "nonce", "type": "uint256" },
      { "name": "deadline", "type": "uint256" }
    ]
  },
  "primaryType": "Permit",
  "message": {
    "owner": "0x0000000000000000000000000000000000000002",
    "spender": "0x0000000000000000000000000000000000000003",
    "value": "1000000",
    "nonce": "0",
    "deadline": "2000000000"
  }
}
~~~

The addresses and numbers are placeholders.
Compare the prompt to the expected fixture before a controlled test wallet approves it, and run the rejection path too.
After a rejection, the application must not record a session, allowance, or completed action.

The request and the screenshot prove different things.
The request is the structured data the dapp handed to MetaMask; the screenshot is what MetaMask rendered.
Save the intercepted `eth_signTypedData_v4` request as `captured-wallet-request.json` and the fixture as `expected-permit.json`, then compare the fields:

~~~typescript
import assert from 'node:assert/strict'
import { readFile } from 'node:fs/promises'

const captured = JSON.parse(
  await readFile('captured-wallet-request.json', 'utf8'),
)
const expected = JSON.parse(await readFile('expected-permit.json', 'utf8'))
assert.equal(captured.method, 'eth_signTypedData_v4')
const actual = JSON.parse(captured.params[1])

function assertTypedDataMatches(actualData: any, expectedData: any) {
  assert.deepEqual(actualData.domain, expectedData.domain)
  assert.deepEqual(actualData.types, expectedData.types)
  assert.equal(actualData.primaryType, expectedData.primaryType)
  assert.deepEqual(actualData.message, expectedData.message)
}

assertTypedDataMatches(actual, expected)

const lookalike = structuredClone(expected)
lookalike.domain.name = 'Lookalike Exchange'
assert.throws(() => assertTypedDataMatches(actual, lookalike))

const wrongSchema = structuredClone(expected)
wrongSchema.types.Permit[1].type = 'bytes32'
assert.throws(() => assertTypedDataMatches(actual, wrongSchema))

const wrongSpender = structuredClone(expected)
wrongSpender.message.spender = '0x0000000000000000000000000000000000000004'
assert.throws(() => assertTypedDataMatches(actual, wrongSpender))
~~~

The negative cases change the domain name, the signing schema, and the spender, and each must fail the comparison.
This check does not depend on the browser driver.
Keep the prompt screenshot beside the JSON, because a correct request can still be presented poorly.

## Build a repeatable MetaMask fixture

The fixture is the state prepared before the browser opens.
Record wallet and browser versions, permissions, balances, nonce state, and application data so a rerun can isolate fixture drift.

| Fixture | Required control |
| --- | --- |
| extension | known MetaMask version installed and enabled before the run |
| account | disposable address with test funds and no production authority |
| network | expected chain configured before the dapp opens |
| permissions | clean connection permissions between cases where needed |
| balances | reset token and native-currency balances |
| nonce | deterministic or isolated chain state |
| app data | predictable account, quote, and session records |
| browser | recorded browser version, viewport, locale, and extension set |

A local Ethereum development chain gives repeatable transaction results, but its tooling belongs to the application’s test setup.
Live-network checks reveal integration issues a local chain hides.
Keep them few, explicit, and funded only with disposable value.
Record the extension version with the browser version: when prompt identification fails, the team must know whether the page, the extension, or the fixture changed.

## Stop at the signing prompt

The public [Browser Agent manifest](https://tangle.tools/.well-known/tangle-browser-agent.json) names the scoped package, the `bad` binary, and the safe discovery commands.
The [driver README](https://github.com/tangle-network/browser-agent-driver#wallet--defi-testing) documents the wallet and DeFi commands, and the linked wallet guide covers the full setup.

~~~bash
npm install -g @tangle-network/browser-agent-driver
npx playwright install chromium
bad --help
bad run \
  --url https://app.example.com \
  --goal "Connect the disposable MetaMask account, verify the configured test chain, open the swap preview, capture the wallet prompt, and stop before signing" \
  --wallet \
  --extension ./extensions/metamask \
  --user-data-dir ./.agent-wallet-profile \
  --wallet-preflight \
  --wallet-chain-id 31337 \
  --wallet-chain-rpc-url http://127.0.0.1:8545 \
  --no-wallet-auto-approve \
  --no-headless
~~~

`--no-wallet-auto-approve` keeps the run before the signature. The driver approves extension prompts by default, so omitting this flag would sign.
A controlled transaction case needs its own goal, a disposable wallet, a local or test chain, and an explicit approval policy.
It must wait for the transaction receipt or a defined failure state before it can pass.
Do not put seed phrases or private keys in the goal text.

The DOM is the page’s structured tree of elements and attributes.
The driver’s README documents its observation modes: DOM, vision (rendered screenshots as model input), and hybrid.
Wallet prompts and visual chain details often need screenshots even when the page controls are easy to find in the DOM.

## Give rejection its own test case

A suite that covers only successful approvals misses the user’s rejection.

| Case | Expected result | Evidence |
| --- | --- | --- |
| reject account access | page remains disconnected and offers retry | prompt rejection, provider error, page state |
| reject chain switch | page explains the required chain and does not submit | requested chain, selected chain, error state |
| reject personal message | no session or authorization is recorded | message prompt, 4001 error, app state |
| reject typed data | no allowance or permission is claimed | typed-data prompt, rejection, app state |
| reject transaction | pending state is cleared or marked rejected | transaction prompt, error, retry state |
| close prompt | page does not assume approval | prompt closed, timeout, stop reason |

A false pass often comes from stale state.
The app shows a connected account from memory after the wallet disconnected, or “Submitted” after a request was sent but before a receipt exists.
Keep requested, signed, broadcast, pending, confirmed, and failed as separate states.

## Split fast wallet smoke checks from deep runs

Wallet suites are expensive to debug because they depend on browser, extension, account, network, and data state.

| Suite | Example cases | Required reset |
| --- | --- | --- |
| connection smoke | connect, reject, account change | clean permissions and disposable account |
| network smoke | wrong chain, switch, chain change | known chain configuration |
| signing suite | personal message, typed data, reject | fresh nonce and expected domain |
| transaction suite | approval, submit, pending, revert | isolated balances and local or test chain |
| release replay | full dapp journey with prompt screenshots | versioned browser, extension, and fixture |

Keep the smoke case short enough to diagnose from one trace.
Run the connection smoke on each change to connection code, and the deeper matrix on changes to signing, allowances, transaction submission, or chain handling.

## Diagnose the first wrong boundary

A trace is the ordered record of browser, wallet, provider, and chain observations for one run.
Compare account, chain, prompt fields, provider errors, transaction hash, and receipt in timestamp order.

| First divergence | Likely owner | Evidence to inspect |
| --- | --- | --- |
| app account differs from wallet account | dapp state or connection layer | accountsChanged event and both screenshots |
| requested chain differs from selected chain | network configuration | chainChanged event and wallet network |
| prompt spender differs from expected contract | transaction builder or route | typed data or transaction request |
| rejection leaves success state | error handling | provider code and app transition |
| pending never resolves | RPC, indexer, or receipt handling | request error, transaction hash (identifier), and timing |
| prompt cannot be reached | extension fixture or browser version | extension state, permissions, and screenshot |

Compare the expected account, chain, action, and outcome with the trace.
A run stays failed when the evidence contradicts the goal.
It is inconclusive when the prompt or the final chain result was never observable.

## Keep the fixture separate from the verdict

Browser Agent drives the page and records the wallet boundary.
MetaMask still presents the account, chain, message, allowance, and transaction details.
The driver cannot decide whether a contract or an economic outcome is safe.

A service built on this should report browser state, wallet evidence, transaction hash, and receipt as separate verdict fields.

## The limit of MetaMask automated testing

MetaMask automated testing shows that a dapp and a particular extension fixture presented a defined wallet flow.
It does not prove the smart contract is safe, that the quoted exchange rate stays available, or that a transaction’s economic outcome is correct.
It does not cover every MetaMask platform, mobile path, browser version, network, account, or wallet setting.
It does not make a production wallet suitable for unattended automation.

Use simulation to inspect calldata, a receipt to establish settlement, contract tests for invariants, and manual review for high-value signing.
Treat a wallet prompt screenshot as evidence of what the user was asked to approve.
Treat a chain receipt or an application-owned confirmation as evidence of what happened afterward.

## Make the prompt reviewable

Automate connection, signing, and transaction approval flows whenever they can change onboarding, revenue, or user trust.
Keep the account, chain, prompt contents, rejection behavior, and final state in the trace, and reject any pass that only proves a button was clicked.
For screenshots, action events, and stop reasons, read [browser automation and the AI evidence loop](/blog/browser-automation-ai-evidence-loop).
