Imagine saving an agent profile that says, “Use this model, these tools, this prompt, and these files.”
You start a run and it launches without one of those settings.
The run may still produce an answer, so the missing setting can look like a weak model, a bad prompt, or a random failure.

The real problem is simpler: the run path accepted a setting it could not deliver.

An **AgentProfile** is the saved set of choices for an agent.
A **worker** is the process that carries out one run.
An **execution path** is the particular route the runtime uses to start that worker.
A **runtime** is the software that starts and manages the worker.

MCP is a standard way for an agent to connect to external tools.

The runtime now treats those paths as explicit delivery contracts.
A contract says which profile settings a path can carry and refuses unsupported changes before the worker starts.

This is the first post in the repaired [runtime infrastructure series](/blog/ai-dev-container-production-agent-runtime).

## A profile is a promise, not a bag of settings

It is tempting to treat a profile as one object that every worker receives unchanged.
That is not how a runtime works.
Different workers understand different settings, and different routes expose different capabilities.

The profile-aware runtime breaks a profile into individual settings before it checks a path.
That lets it reject one unsupported setting instead of accepting a large object and silently dropping a field inside it.

The main profile areas are:

| Area | What a reader can change |
| --- | --- |
| Identity | Name, description, version, and tags |
| Instructions | System prompt and task instructions |
| Model | Default model and model-specific options |
| Agent program | Which agent program should run |
| Permissions | What the worker may access |
| Tools | Tools the agent may call |
| External connections | Connections to outside tools, including MCP connections |
| Child agents | Whether the worker may start other agents |
| Resources | Files, skills, commands, and resource instructions |
| Lifecycle | Hooks and run modes |
| Records | Privacy settings, metadata, and extensions |

The name matters less here than the rule: a path must say whether it can carry those connections.

The implementation expands compound areas such as `model` and `resources` into their individual settings before it checks them.
That is why a change to one file or one model option can be rejected on its own.

## Three paths carry different settings

The current source defines three concrete delivery contracts.
Their counts are not quality scores.
They are inventories of what each path promises to carry.

| Path | Settings it carries | Intended use |
| --- | ---: | --- |
| Full-profile execution | 15 | A worker that accepts every canonical profile area |
| Prompt-and-model execution | 6 | A deliberately narrow worker with prompt and model settings |
| Isolated worktree command execution | 19 | A local coding agent in its own worktree |

The narrow prompt-and-model path carries the worker's name, instructions, default model, agent program, and metadata.
It does not claim to carry tools, permissions, external connections, child agents, or file-backed resources.

The isolated worktree path adds native tools, permissions, external connections, child agents, files, skills, commands, hooks, and modes.
It still leaves out hub connections, confidential execution, provider-specific extensions, unused model hints, and one resource failure option.

Those omissions are useful information.
They tell a builder which path can deliver a proposed change before the runtime spends time creating a worker.

## The failure should happen before the run

Suppose a profile changes both its prompt and its tools.
The selected path accepts prompt changes but has no way to deliver tools.

Without a contract, the worker starts with half of the requested profile.
The builder sees a result and has to guess why the tools never appeared.

With a contract, the runtime reports the unsupported setting before launch.
The builder can choose a path that carries tools or remove that change from the profile.

The error includes the unsupported setting and the settings the path does support.
That makes the failure actionable instead of turning it into a mysterious model problem.

The check also preserves explicit values.
An empty list, `false`, and `0` can all be deliberate requests, so the runtime does not treat them as if the setting were absent.

## Counts do not mean behavior is complete

The number 15, 6, or 19 describes a declared input contract.
It does not prove that every worker or model implements the behavior represented by each setting.

There are two boundaries to keep separate.

Public source code can declare a contract.
The worker must still implement the behavior.
An installable package must also include that source before an application can use it.

The source checked for this article was public, while the package version available on August 1, 2026 was still `@tangle-network/agent-runtime@0.117.0`.
That means the source change and the installable release were not the same thing yet.

## The practical rule

When a profile changes, compare the changed settings with the selected path before starting a worker.

If a path cannot carry a setting, reject the candidate and name the missing capability.

If a path can carry the setting, the worker and provider still need to implement it and expose the resulting behavior.

This turns configuration loss into an explicit decision instead of a debugging session after the run has already happened.

## Questions readers usually ask

### What does “materializing” a profile mean?

It means turning saved profile settings into the concrete inputs that a worker receives.

The runtime checks those inputs against the chosen path before the worker starts.

### Why are there several contracts?

Different workers consume different settings.
A prompt-only worker cannot promise the same behavior as a full-profile worker or a coding worker with files and tools.

### What happens when a profile asks for an unsupported setting?

The runtime reports that setting and the path's supported settings before launch.
The builder must choose another path or remove the unsupported change.

### Does the count prove that every setting reaches the model?

No.
The count describes what the execution path declares as input.
The worker and provider must still implement the behavior represented by each setting.

### Is the contract in the published package?

The source implementation is public, but the package check on August 1, 2026 returned version 0.117.0.
Check the package version before depending on a newer source contract.
