Most paid APIs make the customer create an account, receive an API key, keep a balance, and reconcile invoices later.
That model works, but it asks the service owner to run a billing product alongside the service itself.

The **x402 protocol** is a payment format that uses HTTP status code 402 to make payment part of a request.
The server first explains the price, the client pays, and the client retries with proof that the payment was accepted.

On Tangle, a **Blueprint** is a public service definition that another team can run.
An **operator** is the person or team that runs that service.
A **job** is one unit of work exposed by that service, such as generating a quote or hashing a payload.
The Blueprint SDK connects x402 payment requests to those existing jobs instead of creating a second paid-only execution path.

The practical result is simple: a service can accept a payment-backed HTTP request while keeping the same job code it uses for other triggers.

This post explains that flow, the trust it relies on, the pricing boundaries, and the failure cases an operator should plan for.
The [x402 protocol site](https://x402.org) defines the payment format itself.
The [Blueprint explanation](/blog/how-blueprints-work) covers the wider service model.

## What happens when a client pays

The request has six stages:

1. The client asks for a job.
2. The service returns HTTP 402 with the accepted networks, tokens, amount, and time limit for the quote.
3. The client signs and settles a payment.
4. The client sends the request again with payment proof in an HTTP header.
5. A **facilitator**, the service that checks and settles the payment, confirms the proof.
6. The gateway sends the paid request to the ordinary job runner.

The gateway refuses to run the job until the facilitator confirms settlement.
That order protects the operator from doing work for a payment that never cleared.
It also adds a network round trip and chain confirmation time before the job starts.

The facilitator is a trust boundary.
The gateway delegates payment checking to it rather than independently reading every chain transaction.
Operators should decide whether a public facilitator meets their requirements or whether they need a service they control.

## Payment and job execution share one path

The SDK translates a verified payment into the same internal job request used by other producers.
That request carries the job identifier, the original body, and payment details such as the network, token, quote fingerprint, and caller.

The job handler does not need to know whether the request came from an HTTP payment, an on-chain event, a scheduled task, or another trigger.
It receives a job request and returns a result.

| Payment information | Why the job may need it |
| --- | --- |
| Network and token | Explain which asset paid for the work |
| Quote fingerprint | Tie the payment to the price the client saw |
| Caller | Apply an access rule when the service is restricted |
| Request body | Supply the actual job input |

This is the central design choice.
Payment changes who is allowed to start the job and whether the operator is paid.
It does not require a different handler for the work itself.

## Why payment comes before execution

The operator has two basic choices:

| Order | Risk for the operator | Benefit for the client |
| --- | --- | --- |
| Execute, then bill | The operator may perform unpaid work | The client sees a result before paying |
| Settle, then execute | The client may wait for settlement before seeing a result | The operator does not burn compute for an unpaid request |

The Blueprint SDK chooses settlement before execution for the x402 path.
That is a policy choice, not a law of the protocol.
It makes the payment guarantee stronger and the first response slower.

## How prices are represented

The SDK stores a job’s base price in **wei**, the smallest unit of a chain’s native currency.
The service can then accept other tokens by converting that base price at request time.

The conversion needs four values:

- the base price in wei
- the current exchange rate for the native currency
- an operator markup, if any
- the token’s decimal precision

For example, a job priced at 0.001 ETH becomes 3.264 USDC when the exchange rate is 3,200 USDC per ETH and the operator adds a 2% markup.
The client receives the converted amount in the price response rather than calculating it from local assumptions.

The price response also carries a **quote fingerprint**, which ties the payment to the exact amount and destination the client agreed to.
A short time-to-live prevents a client from holding a quote forever while market conditions change.

Static rates are suitable for a first deployment.
Production operators need a current-rate source and a policy for what happens when that source is unavailable.

## Three access modes

Payment and authorization are separate decisions.
The gateway supports three useful modes:

| Mode | Meaning |
| --- | --- |
| Disabled | The job is not available through x402 |
| Public paid | Anyone may call it after paying |
| Restricted paid | Payment is required and the caller must also be authorized |

In restricted mode, the caller can be the wallet that paid or a caller represented by a signed delegation.
A **nonce** is a value used once to prevent the same signed request from being replayed.
The gateway rejects an expired or already-used delegation.

This matters for agent-to-agent work.
A coordinator can pay for a job on behalf of a worker while the service still checks the worker’s identity and permissions.

## Quotes and replay protection

The gateway keeps outstanding quotes and consumes one when a payment arrives.
Trying to use the same quote twice is rejected.
The delegation check separately tracks signed nonces.

The quote store is held in memory in the implementation described by the original post.
If the gateway restarts, outstanding quotes disappear and clients must request new ones.
Payments that already settled on-chain are not undone by that restart, and jobs already handed to the runner can continue.

That restart behavior is acceptable for short-lived quotes only when clients know how to recover.
It should be part of the operator runbook rather than an invisible implementation detail.

## What the operator can observe

The gateway exposes health and counter information for accepted requests, policy denials, payment failures, replay rejections, queue failures, missing jobs, and authorization checks.
Those counters answer “what happened to the request?”
They do not replace the service’s own job metrics, such as execution time, result quality, or downstream failures.

The payment layer should also make its boundary visible:

- a payment can be accepted while the job later fails
- a job can be rejected before execution because the payment or caller is invalid
- a price can expire before the client retries
- a gateway restart can invalidate an unused quote

These are different outcomes and should not collapse into one “API error” count.

## The practical decision

Use x402 when a service needs pay-per-request access and the operator prefers payment proof before spending compute.
Keep a normal account or subscription path when customers need invoicing, refunds, or long-running business relationships that a wallet transaction does not cover.

For a first paid job, publish one price, one accepted token, one access mode, and one recovery path for an expired quote.
Add multiple chains, live exchange rates, and delegated callers only after the single-request flow is observable.

The useful promise is not “payments disappear.”
It is “payment verification and job dispatch share one path, so the job handler stays about the work.”

## Questions readers usually ask

### Does x402 require an account or API key?

No.
The client proves payment in the request, so the operator does not need a balance or API-key system for that path.
The service may still require identity checks for restricted jobs.

### What happens when payment succeeds but the job fails?

The payment and execution are separate events.
The operator needs a policy for failed work, and the service needs records that distinguish settled payment from successful job completion.

### Can the service accept more than one chain or token?

Yes.
Each accepted token needs its network, destination, decimal precision, exchange-rate policy, and markup.
The client chooses from the options in the price response.

### What does a restart do to an in-progress request?

Unused in-memory quotes are lost and must be requested again.
Already settled payments remain on-chain, and jobs already dispatched may continue.
The exact recovery behavior depends on where the request was in the flow.

### Can I use x402 without Tangle’s on-chain permissions?

Public-paid jobs need payment verification and the Blueprint job runner.
Restricted-paid jobs add an on-chain caller-permission check.
