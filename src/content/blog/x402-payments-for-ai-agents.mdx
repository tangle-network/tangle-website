A blueprint is a packaged service definition with a typed job interface. x402 is a payment protocol for machine-to-machine requests. x402 lets an AI agent pay for one HTTP request without opening an account or selecting a subscription first.
The server responds with `402 Payment Required`, the agent evaluates the price and terms, the wallet signs a payment payload, and the agent retries with that signature.
The server verifies and settles the payment before returning the purchased resource.

Payment is only the commercial step.
It does not prove that an agent service returned a correct, safe, or useful result.

This guide was checked on August 1, 2026 against the current [x402 payment flow](https://docs.cdp.coinbase.com/x402/core-concepts/how-it-works), [client and server responsibilities](https://docs.cdp.coinbase.com/x402/core-concepts/client-server), and Tangle Blueprint SDK commit [`00c3cae`](https://github.com/tangle-network/blueprint/tree/00c3cae14ade1bbaf8374934f7c5084cff0af866/crates/x402).

## Quick Answer

Use x402 when the buyer is software and the thing being purchased maps cleanly to a request, such as one browser task, model call, sandbox job, quote, conversion, or audit run.
Use a subscription or prepaid account when the buyer needs invoices, negotiated limits, refunds, team administration, or predictable monthly spend.

An agent should pay only after it checks the amount, asset, network, recipient, expiry, requested capability, and its own spending policy.

## The Current x402 v2 Flow

The v2 wire flow uses three important headers:

| Step | Header | Purpose |
| --- | --- | --- |
| Server challenge | `PAYMENT-REQUIRED` | Encodes the accepted payment options and requested amount. |
| Client retry | `PAYMENT-SIGNATURE` | Carries the buyer's signed payment payload. |
| Server response | `PAYMENT-RESPONSE` | Returns settlement information with the purchased resource. |

At a high level:

```http
POST /paid-task HTTP/1.1
Content-Type: application/json
Idempotency-Key: task-2026-08-01-001

{"task":"summarize the attached report"}

HTTP/1.1 402 Payment Required
PAYMENT-REQUIRED: <base64-encoded payment requirements>

POST /paid-task HTTP/1.1
Content-Type: application/json
Idempotency-Key: task-2026-08-01-001
PAYMENT-SIGNATURE: <signed payment payload>

{"task":"summarize the attached report"}

HTTP/1.1 200 OK
PAYMENT-RESPONSE: <base64-encoded settlement response>
Content-Type: application/json

{"result":"...","artifact":"sha256:..."}
```

The exact payload schema depends on the x402 version, payment scheme, network, and implementation.
Do not copy a v1 payload into a v2 client or infer field names from a blog post.
Use the current [seller quickstart](https://docs.cdp.coinbase.com/x402/quickstart-for-sellers) and the implementation's typed SDK.

## What the Agent Must Decide

Receiving a `402` response should start a policy decision, not an automatic payment.

| Check | Why it matters |
| --- | --- |
| Capability | The endpoint must match the task the agent intends to buy. |
| Amount and currency | The price must fit the task budget in an asset the wallet can spend. |
| Network | The wallet and payment scheme must support the requested chain. |
| Recipient | The destination should match the service or trusted payment policy. |
| Expiry | The signature should not remain usable longer than necessary. |
| Idempotency | A retry must not charge or execute the task twice. |
| Output contract | The agent should know what result, receipt, and evidence it expects. |

For autonomous spending, set a per-request limit, a daily limit, an allowed recipient or service list, and a rule for when a human must approve.
Fail closed when any required field is missing or ambiguous.

## Where Tangle Uses x402

Tangle's public [`blueprint-x402` crate](https://github.com/tangle-network/blueprint/tree/00c3cae14ade1bbaf8374934f7c5084cff0af866/crates/x402) exposes Blueprint jobs as paid HTTP routes.
The gateway verifies payment through the configured facilitator and injects the resulting call into the Blueprint runner.
The job implementation therefore receives a normal job call rather than implementing payment logic itself.

The current route shape is:

```text
POST /x402/jobs/{service_id}/{job_index}
```

The current source accepts legacy v1 `X-PAYMENT` and v2 `Payment-Signature` headers.
New integrations should prefer the current x402 version supported by their client and facilitator, while compatibility code should make the version explicit.

Each job has an invocation policy:

- `disabled` means the job cannot be called through x402.
- `public_paid` means a valid payment can invoke it.
- `restricted_paid` means payment is necessary but the caller must also pass the configured identity policy.

That distinction matters for agent services.
Paying for a task should not grant access to private data, administrative actions, or another customer's resources.

## What x402 Does Not Prove

x402 can prove or record that the payment conditions were satisfied.
It does not prove the purchased work was correct.

Pair the payment receipt with evidence appropriate to the task:

| Purchased work | Useful result evidence |
| --- | --- |
| Browser task | final URL, screenshots, DOM state, and action record |
| Sandbox job | command exit status, changed files, logs, and artifact hashes |
| Model call | model identity, request policy, token usage, and structured output validation |
| Code audit | affected lines, reproduction command, observed result, and regression test |
| On-chain action | transaction hash, receipt status, chain, contract, and decoded event |

For long-running work, payment and execution may finish at different times.
Return a stable job identifier and define whether a paid request returns the final result, a polling URL, or a callback contract.

## Failure Cases to Test

The successful request is the easiest path.
A production integration also needs tests for:

1. An expired or underfunded payment signature.
2. A valid signature for the wrong recipient, amount, asset, or network.
3. Two retries with the same idempotency key.
4. Settlement success followed by job failure.
5. Job success followed by a lost HTTP response.
6. A facilitator timeout before the server knows whether settlement happened.
7. A client that supports a different x402 version.
8. A refund or support request tied to a transaction and job identifier.

The recovery rule should distinguish “not paid,” “payment state unknown,” “paid but not executed,” and “executed but response lost.”
Treating all four as a generic retry creates duplicate charges or duplicate work.

## x402 or Subscription?

| Choose x402 when | Choose subscription or prepaid billing when |
| --- | --- |
| The buyer is an agent or script. | The buyer is a team with procurement requirements. |
| The commercial unit is one request. | Usage spans many requests and users. |
| Wallet-based payment is acceptable. | Card, invoice, tax, or refund workflows are required. |
| Stateless access is valuable. | Account history and customer administration are valuable. |
| Per-request settlement time is acceptable. | The request path needs the lowest possible latency. |

Services can support both paths if they converge on the same authorization and job-dispatch rules after payment.

## FAQ

### What is x402 for AI agents?

It is an HTTP payment flow that lets software receive payment requirements, sign a payment, retry the request, and receive a settlement response without first creating a conventional account.

### Does x402 replace API keys?

It can replace an API key for public paid access.
Restricted jobs may still require caller identity, permissions, or another authentication method in addition to payment.

### What headers does x402 v2 use?

The current v2 flow uses `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`, and `PAYMENT-RESPONSE`.
Legacy v1 implementations commonly use `X-PAYMENT` and `X-PAYMENT-RESPONSE` variants.

### Does a successful payment prove the service result is correct?

No.
Validate the result with task-specific evidence and retain a link between the payment receipt, job identifier, and output artifact.

### Why does x402 matter for Tangle Blueprints?

It gives a Blueprint job a standard paid HTTP entry point while leaving the job implementation on the normal runner path.
The public source linked above shows the current integration and its access-policy options.
