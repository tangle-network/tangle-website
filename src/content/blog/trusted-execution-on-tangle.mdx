A secure container for AI agents should limit what the process can touch and provide evidence about where it ran. Hardware isolation helps with the second part, but it does not prove the answer is correct. Suppose you send private data or model weights to a service run by someone else.
You may be able to verify the result after the job finishes, but that does not answer a different question: could the person running the machine read or change the work while it was running?

A **trusted execution environment**, or **TEE**, is a protected area of a computer that uses hardware to isolate a workload from the machine’s ordinary operating system.
The protection is useful only when the workload can also show what code is running inside that area.

On Tangle, a **Blueprint** is a public service definition that another team can run.
An **operator** is the person or team that runs that service.
The Blueprint SDK can ask for TEE execution, collect an **attestation report**, and use that report when a user needs evidence about the running workload.
An attestation report is a signed statement from the protected environment about the code and hardware that produced it.

This post explains what that arrangement can prove, how the SDK moves the evidence, and where the promise ends.
It is one part of the [Tangle Re-Introduction series](/blog/series/tangle-re-introduction/).

## Isolation changes the question

Ordinary verification asks whether a result looks correct after execution.
TEE execution adds a before-and-during question: was the code running in an environment that blocked the operator from inspecting or changing it?

That distinction matters for private inference, proprietary model weights, and jobs whose inputs must remain confidential.
Hardware isolation can restrict the operator’s access to the workload.
It cannot make a bad program correct, and it cannot prove that the user asked for the right code.

The useful claim is narrower: a user can check that a particular approved program started inside a particular protected environment.

## Three ways to place the protected workload

The SDK describes three deployment modes.

| Mode | What runs inside the protected area | When it is useful |
| --- | --- | --- |
| Direct | The Blueprint runner itself | When the whole service needs the strongest isolation boundary |
| Remote | A cloud workload started by the runner | When the runner manages a separate protected cloud instance |
| Hybrid | Only selected jobs or components | When ordinary work and sensitive work have different requirements |

Direct mode can use hardware devices exposed by a host that supports Intel TDX or AMD SEV-SNP.
Remote mode can provision protected workloads through AWS Nitro Enclaves, Google Confidential Space, or Azure Confidential VMs.
Hybrid mode can keep a pricing step in an ordinary container while sending private model inference to a protected workload.

The mode is an operational choice, not a security grade.
The right choice depends on which data, code, and keys must stay inside the boundary.

## How an attestation becomes evidence

The SDK moves evidence through five steps:

1. A provider starts the protected workload.
2. A component inside that workload asks the hardware for an attestation report.
3. The report includes a **measurement**, a fingerprint of the code or image that started.
4. The deployment keeps the report so it can be submitted again without creating a new workload.
5. Tangle stores a fingerprint of the report in an on-chain record that others can inspect.

The provider formats differ, but the question stays the same: does this report describe genuine protected hardware running the approved code?
The SDK’s provider-specific checking code handles those format differences and applies common checks such as provider identity, debug mode, measurement, and freshness.

The on-chain record is a fingerprint of the report, not the report’s entire contents.
Anyone who has the report can calculate the fingerprint and compare it with the recorded value.

## Secrets cannot be handled like ordinary container settings

In a normal deployment, a secret may arrive as an environment variable when a container starts.
Recreating that container is routine.

For a protected workload, recreation changes the measured code and can invalidate the evidence that users rely on.
The SDK therefore uses **sealed secrets**, which are secrets encrypted for one attested workload rather than copied into a general-purpose container setting.

The exchange works like this:

1. The protected workload creates a temporary public and private key pair.
2. The public key is included in the attestation report.
3. A client checks the report and encrypts the secret to that public key.
4. Only the workload holding the private key can decrypt the secret.

The SDK manages the temporary exchange session and removes it when its lifetime ends.
The security claim depends on the client checking the report before sending the secret.

## Provider differences are real

The cloud providers expose different APIs and report formats.

- AWS Nitro Enclaves start an isolated enclave alongside an EC2 instance and use a local communication channel between the host and enclave.
- Google Confidential Space starts a confidential virtual machine and exposes an attestation token for the workload.
- Azure Confidential VMs use confidential-computing hardware and Azure’s attestation service.

The SDK hides the provisioning details behind one Blueprint-facing choice, but it does not make the providers identical.
Availability, startup time, supported hardware, report contents, and operational controls remain provider-specific.

The provider documentation is the authority for those boundaries: [AWS Nitro Enclaves](https://docs.aws.amazon.com/enclaves/latest/user/nitro-enclave.html), [Google Confidential Space](https://cloud.google.com/confidential-computing/confidential-space/docs), and [Azure Confidential VMs](https://learn.microsoft.com/en-us/azure/confidential-computing/confidential-vm-overview).

## What a Blueprint declares

A Blueprint can declare that protected execution is required or preferred.
It can also restrict which providers are acceptable and how old an attestation may be.

| Declaration | Meaning |
| --- | --- |
| Required | Refuse to start if an acceptable protected environment is unavailable |
| Preferred | Use protected execution when available, with an explicitly chosen fallback |
| Provider list | Accept only the listed provider families |
| Maximum report age | Reject evidence older than the allowed interval |

This decision belongs in the service definition because it changes where the job may run.
It should not be hidden in a local operator preference that consumers cannot inspect.

## Shipped behavior and future work

The source snapshot used for the original post described direct, remote, and hybrid modes, three cloud integrations, attestation checks, and sealed-secret exchange.
That dated snapshot reported 162 tests across attestation, configuration, exchange, middleware, and runtime behavior.
It is a historical figure, not a current test count.
The [public Blueprint repository](https://github.com/tangle-network/blueprint) is the source for the implementation and its current release state.

The same source listed several follow-up items:

- refreshing attestation on a schedule rather than only at startup
- deriving hybrid routing from the on-chain service declaration
- using platform-specific hardware reports in the direct mode

Those are separate capabilities.
The presence of a TEE integration does not mean every provider, hardware mode, or refresh policy is available in every release.

## The practical decision

Use a TEE when the operator should not be able to inspect or alter sensitive work while it runs and when users can check the attestation before sending secrets.

Do not describe TEE execution as proof that the service is correct, that the provider is honest in every other respect, or that the result cannot be manipulated outside the protected workload.
Those claims require separate evidence.

Start with one job whose data boundary is clear, require an attestation report, and document what code fingerprint the client expects.
Only then decide whether to add remote provisioning, sealed secrets, or hybrid routing.

## Questions readers usually ask

### Does a TEE prove that the job produced the right answer?

No.
It provides evidence about the protected environment and the code that ran there.
The job still needs its own correctness checks.

### Can the operator read the input while the job runs?

The hardware boundary is designed to prevent the ordinary host from reading protected memory.
The exact guarantee depends on the provider, hardware, configuration, and the code inside the workload.

### Why is the attestation report important?

Isolation without identity is hard to trust.
The report lets a client compare the running code and environment with the code it approved.

### Can I change configuration after the workload starts?

Changes that alter the measured workload can invalidate the report and any secret exchange tied to it.
Treat configuration changes as a new deployment unless the provider and SDK document a safe update path.
