An AI service can return a plausible answer while leaving the customer unable to tell what produced it.
A code-execution service can return the right output while exposing the customer’s data or the machine owner’s system.

On Tangle, a **Blueprint** is a public service definition that another team can run.
An **operator** is the team that supplies the machine and runs that service.
This post uses two examples to show what those services need to make their boundaries visible:

- **Inference** runs an AI model on a customer’s input.
- **Sandbox execution** runs customer-supplied or model-generated code inside a restricted environment.

The goal is not to claim that one mechanism solves every trust problem.
The goal is to match each claim with evidence and state what remains outside the claim.

The earlier [Blueprint introduction](/blog/building-on-tangle-from-idea-to-production) covers the general development path.
The [Tangle verification overview](/blog/how-tangle-verifies-work) explains the broader result-checking model.

## Two services, two directions of risk

Inference and sandbox execution protect different sides of the interaction.

| Service | What the customer sends | Main risk | Useful evidence |
| --- | --- | --- | --- |
| Inference | Prompts, files, or structured data | The operator uses the wrong model, exposes the input, or changes the response | Model identity, protected execution evidence, and explicit output limits |
| Sandbox execution | Code and inputs | Customer code attacks the operator, or the operator changes the execution | Resource policy, isolation record, output record, and a suitable result check |

Neither service can prove “the output is good” with one generic receipt.
Quality, privacy, code identity, and result correctness are separate properties.

## Part 1: an inference service

An inference service accepts an input, runs a selected model, and returns the model’s output.
The customer usually cares about four questions:

1. Did the claimed model run?
2. Did the operator keep the input private?
3. Did the service return the model’s output without an unannounced change?
4. Is the output useful for this task?

The first three can receive technical evidence.
The fourth needs task-specific tests and human judgment.

### Model identity is not output quality

A model fingerprint is a cryptographic summary of the model files that were loaded.
If a protected workload reports a fingerprint that matches the approved model, the customer has evidence about model identity.
That does not show that the model answered well, followed policy, or handled an adversarial prompt safely.

A **TEE**, or trusted execution environment, uses hardware to isolate a workload from the ordinary host.
An **attestation report** is a signed statement about the protected workload and its code fingerprint.
The [TEE integration post](/blog/trusted-execution-on-tangle) explains that boundary in detail.

The inference response can include:

| Field | What it supports |
| --- | --- |
| Model fingerprint | Which model files the service says it loaded |
| Attestation report | Which protected environment produced the evidence |
| Usage data | How much work the model reports doing |
| Model output | The result the customer can evaluate |

The customer must check the report before treating the model fingerprint as evidence.
An unverified report is only a claim from the service.

### Hardware limits are part of the design

Protected execution has practical limits.
Some hardware provides less memory than a large model needs.
GPU protection is newer and less broadly available than ordinary GPU hosting.
Large models may need sharding, a larger protected machine, or a different verification tradeoff.

Those limits should appear in the Blueprint’s operating description.
“Runs in a TEE” is not a complete deployment specification without the provider, hardware family, model size, and fallback policy.

### Canary checks catch selected substitutions

A **canary** is a known test input with an expected behavior.
Running a set of canaries can reveal a model substitution or a large behavior change.

Canaries are useful because they test the deployed behavior rather than only the file fingerprint.
They are not a complete quality test.
A service can pass the selected canaries and still fail on inputs the canaries never cover.

Use canaries as one signal alongside model identity and task-level quality tests.

## Part 2: a sandbox service

A sandbox service runs code supplied by a customer or generated by an AI system.
The service needs isolation in both directions:

- the customer’s code must not escape into the operator’s host
- the operator should not receive more access to the customer’s data than the policy allows

The policy must be explicit.
“Sandboxed” is not a sufficient description.

| Policy area | Example decision |
| --- | --- |
| CPU and memory | Maximum time and memory for one run |
| Network | No network, or an allow-list of destinations |
| Filesystem | Read-only inputs, temporary output, or selected directories |
| Process privileges | Which operating-system capabilities are unavailable |
| Lifetime | When the environment is destroyed |
| Records | Which output, resource, and event data is retained |

Each execution should start from a known environment and end with a clear state transition.
If data or processes can persist between customers, the isolation claim is incomplete.

### A trace shows what happened

A **trace** is the time-ordered record of an execution.
For a sandbox, it can include the input fingerprint, start and end times, exit result, resource usage, network decisions, and selected tool or process events.

The trace is evidence about the execution path.
It is not a guarantee that the code was safe or that the output was correct.
Those questions require policy checks and workload-specific tests.

### Verification depends on determinism

Some jobs produce the same result every time when the input and environment are fixed.
Those jobs can use replay: run the same input again and compare the results.

Many real programs depend on time, network responses, random values, dictionary order, or floating-point behavior.
For those jobs, exact replay may be impossible.
Possible alternatives include:

- multiple operators with a documented agreement rule
- statistical checks that define an acceptable range
- protected execution with an attestation report
- financial collateral that creates a consequence for proven failure

No alternative is automatically equivalent to replay.
Name the property the chosen mechanism supports.

### Resource limits are product behavior

Resource accounting also determines whether one customer can starve other work.
It determines whether one customer can starve other work and whether a result can be reproduced under the same limits.

Record at least CPU time, peak memory, network bytes, disk writes, exit status, and the policy applied.
Label missing fields as unknown instead of filling them with zero.

## Combining inference and execution

The two services can form a useful workflow:

1. An inference service generates a proposed program or analysis plan.
2. A sandbox runs that program against the customer’s data.
3. The customer receives the result, the program, the execution record, and the evidence each stage produced.

This arrangement makes the boundary visible.
The inference evidence concerns the model and protected environment.
The sandbox evidence concerns isolation, policy, resource use, and execution.
Neither stage proves the final answer is correct without a task-specific check.

For example, a data-analysis service can return the generated program and its result so a reviewer can inspect both.
That is more useful than returning a number with no explanation of how it was produced.

## What these mechanisms do not solve

TEE evidence does not prove that a model is safe or that its output is helpful.
Model fingerprints do not prove the model was trained well.
Canaries do not cover every prompt.
Sandbox isolation does not make an arbitrary program correct.
Resource records do not prove that a customer’s policy was appropriate.
Operator stake does not replace a result check.

These limits are not a reason to discard the mechanisms.
They are the reason to state the claim each mechanism can support.

## The practical decision

Build inference first when the product’s central question is “which model ran, and what did it return?”
Build a sandbox first when the product’s central question is “can this code run under a policy without escaping?”
Combine them when generated code must operate on private data and the customer needs evidence from both stages.

Start with one job, one model or language, one resource policy, and one result check.
Publish the evidence fields before adding more providers, languages, or verification choices.

The useful service promise is a statement a customer can test: what ran, where it ran, what policy applied, what was recorded, and what remains unknown.

## Questions readers usually ask

### Can a TEE prove that the model’s answer is correct?

No.
It provides evidence about the protected environment and code identity.
Output quality needs its own task-specific evaluation.

### Can a sandbox run arbitrary code safely?

Only within a clearly defined policy and a tested isolation boundary.
Network, filesystem, process, and resource limits must be explicit.

### What languages can the sandbox support?

The source described support for Python, JavaScript, Rust, Go, and WebAssembly.
The available languages and their isolation strength depend on the release and the operator image.

### Why use multiple operators?

Independent runs can provide a disagreement signal for deterministic or near-deterministic work.
They do not automatically resolve non-deterministic output or prove which result is correct.

### What should a customer ask before using the service?

Ask which code and model ran, what inputs were visible to the operator, which limits applied, what evidence is returned, and which failures the service can detect.
