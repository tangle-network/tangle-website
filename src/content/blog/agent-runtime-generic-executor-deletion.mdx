An agent runtime is your loop (call the model, run the tools it asks for, repeat until a final message) plus a record that outlives your process.
Pick the setup by the tools: a run that needs no tool, file or session is one model call; your own loop with no sandbox is enough while every tool is a function you wrote, a hosted connection or an HTTP read, and the run finishes inside one request; and when the run needs a harness, files, a shell or MCP servers, add a sandbox, which your loop can use as its tools.
Our client places runs by the same rule.
Adopt a runtime when a run has to survive your process dying, spends money while nobody watches, or runs Claude Code or Codex.
We build one, agent-runtime, and we would keep a hand-written loop until one of those needs shows up.

## A runtime runs the loop and keeps the record

Our library exports it as a tool loop, and it stops on a finish, a turn cap, a deadline, a cost limit or a stuck-loop check.

A framework is a library for writing that loop.
It gives you prompt templates, tool schemas and step graphs, and it lives and dies with your process.

A harness is a coding agent that brings its own loop.
Claude Code, Codex, OpenCode and Pi each decide when to read a file, run a command or stop.
You hand a harness a task and a machine, and it drives.

A sandbox is the machine the agent acts on: files, a shell, a git checkout.
On our service it is a container on the host kernel or a microVM with its own kernel.

The runtime sits around all of them.
It starts the run on the harness or your loop, in the sandbox, under limits, and records every step and how it ended.
Restate puts it well: the harness runs the agent loop, and the runtime helps you run and manage it in production.[^restate]

## Your own loop is enough while every tool is your own function

Pick the setup by what the run needs:

- no tool, file or session: one model call;
- only your own functions, hosted connections or HTTP reads, nothing the model writes gets executed, and the run fits in one request: your own loop, no sandbox;
- a harness, files, a shell or MCP servers: add a sandbox, which your loop can use as its tools.

A crash there loses one request, and a retry costs one request.

Things change when any of these become true:

- the model writes code and something has to run it;
- a run lasts longer than the process that started it;
- the agent spends real money unattended;
- someone will ask what the agent did, and you need more than a final message;
- you want Claude Code or Codex, which bring their own loop.


## Keep your loop and give it a sandbox

If a shell is all you need, add a sandbox and keep everything else.
The sandbox SDK hands your Chat Completions loop a tool list and a handler for the assistant's tool calls.
The model, the loop and the stop rule stay yours.

## The loop you keep has to manage its own history

Keeping your loop means keeping its bookkeeping, and the model call is the easy part.
Every turn re-sends the whole message list, so the request grows with each tool result.
Past the context window, the call fails.

Prompt caching makes the long history affordable, but only for an unchanged prefix.
OpenAI and Anthropic both describe caching as reusing the unchanged start of the prompt.[^cache]
Swap the tools, the model or an early message mid-run, and the whole history is billed again at the uncached rate.
We infer that from how prefix caching works; we did not measure it.

So a long-running loop needs compaction: summarize older history once it crosses a token threshold.
Codex has a config key for that threshold, and Claude Code has an auto-compact window.[^compact]
If you run a harness, it does this for you; if you keep your own loop, you write it.

## A spend cap that stops running turns can still overshoot

A cap checked after each run only reports money already spent.
Ours holds while a turn is running:

- `budgetUsd` is a hard cap the Platform enforces at every charge, mid-turn included;
- the `costUsd` that `client.run()` reports is model spend only, and sandbox time is billed separately.

A fleet's dollar budget rides on a budgeted key for every turn.
A refused turn ends with the status budget_exhausted.
Turns already running are not aborted.
Each one is refused at its own next charge.[^cap]
So the hard cap can overshoot by whatever calls were in flight when it was crossed.
We have not recorded a run that reached the hard cap, so we cannot tell you how large that overshoot gets.

The pattern we use is a hard cap well above the number we care about, plus our own soft stop below it.

## Reattach to a run by its execution id

A long run on your laptop dies with your laptop.
Retrying it from the top repeats every side effect.

Ours runs the agent in a hosted sandbox and hands you two ids.
Dispatch the run when it must continue after the caller disconnects. On our batch streams, disconnecting an unkeyed stream cancels the work, while a keyed run continues.
The first invocation below creates the box, dispatches the task under a session id you choose, prints the ids and exits.
A second, separate process uses those ids to collect the result.

<Example path="sandboxes/worker" />

In the recorded run, the first process printed both ids in under seven seconds and exited.
The second waited 45 seconds more for Codex to finish upgrading the dependencies, then printed the result.
Dispatching again with the same session id finds the existing session instead of starting a second run.[^dispatch]
The execution id pins collect and interrupt to that one run.

That is one run with a 45-second gap, and we have not recorded a longer one.
agent-runtime also documents how a dead coordinator process resumes from its run directory.
Its README says an external effect the record leaves unconfirmed is reconciled at that effect's own boundary.
Your code still owns idempotency at the edge.

## Every tool call is in the stream, and a dead run says why

The record has two layers.
The stream gives you each tool call as the agent makes it, with its input, its output and its status.
It ends with a result carrying the final text, then a done event carrying the run's total cost (`totalCostUsd`), which the any-cloud example above prints.

<Example path="sandboxes/watch-an-agent" />

That run made twelve tool calls.
The last one ran the test suite.
The agent's final text reports the timezone test passing and 7 of 9 tests passing; the two still failing, cli-flag and null-guard, fail by design in the demo repository.
That is the agent's own test run on one attempt, so read it as one result.

The second layer is a report over the trace.
We asked for a deterministic report on a Claude Code turn that made eight tool calls, and it came back unbilled.
Its findings were structured claims, each with a severity, a confidence and pointers into the trace.
They covered compute and egress rather than narrating each call.

A run that dies before it produces output reports its cause on the session status: a binary that could not start, or a profile that could not be built.[^failure]

## Agents that share a sandbox share trust

The isolation boundary is the sandbox.
Agents in one sandbox share a broad trust and resource boundary, so use separate sandboxes for untrusted agents or separate tenants.
Pick a microVM when you want a separate kernel; a Firecracker request never falls back to a container.

A fleet policy caps machines, concurrent creates, total CPU and memory, spend and accelerators, and `maxLifetimeSeconds` in the fleet's defaults caps each sandbox's lifetime.
It is checked before provisioning and does not replace account quotas.

Your account key controls the whole account, so it never goes to a browser or into a sandbox.
Mint a scoped token on your server instead; the runtime refuses to inject the account key into a sandbox.
Keys you do inject can carry a lifetime, after which the runtime removes them.
Processes already running keep their environment, so removal does not revoke a copy the agent already read; give it keys you can rotate.

## What runs without us, and what you lose if you leave

agent-runtime (`@tangle-network/agent-runtime`) is MIT-licensed on npm and runs in your process; it has shipped seven major versions since 3.0.24 on 1 November, so pin the version.
The tool loop runs with a scripted model and no credentials.
Supervised runs keep their record in a directory on your disk.
Its real-model example calls a model through our router and exits until a router key is set.

These need our hosted service:

- the hard spend cap, because the budget lives on a Platform-minted key;
- hosted sandboxes, and reattaching to them by execution id;
- model calls on every provider, which go through our router;
- trace reports.

We host the sandboxes.
On-premises hosting is planned and not available today.

You can move the sandbox.
Swap the Tangle provider for E2B, Daytona or ComputeSDK; the imports and the provider setup change (ComputeSDK also needs its own cloud configured). Daytona also needs a model in the profile, and the turn loop loses its cost line.

<Example path="runtime/any-cloud-e2b" />

Those versions are typechecked on every site build but have never run.
On those clouds the harness still sends its model calls through our router on a per-run key, so the sandbox moves and the model account does not.
Their events also omit per-run cost, because the dollar figure there is the harness's own catalog estimate.

We do not document what happens to a running agent, or to budget enforcement, if our Platform or router is down.
We do not know yet, and you should plan as if the answer is "the run stops".

The agent-runtime examples here ran on version 3.0.24, most of them on 12 November, and we have not rerun them on 10.x.
Each release carries a conformance manifest that marks every capability as supported, unsupported or unproven.
Two are unproven today: acknowledging an interaction response, and transferring context.

If you leave, you keep the library, your profiles and your own loop.
You lose the hard cap, reattach and the hosted traces, and you point each harness back at its usual model vendor.

## Pick by the first thing your loop cannot do

Keep your loop while every tool is your own function and a run fits in one request.
When the model's code needs a shell, add a sandbox as your loop's tools and change nothing else.
When a run must outlive your process, spend money unattended, or run Claude Code or Codex, adopt a runtime.
Before you do, run its crash path and its cap against your own task.
