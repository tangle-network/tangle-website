Suppose two pieces of software start the same kind of coding job.
One is 3,360 lines spread across 16 files.
The other is shared by every run that uses the same remote service.

Deleting the larger one looks like obvious cleanup, but line count cannot tell you whether the two paths behave the same.
The safe question is narrower: can the shared path deliver the settings, controls, errors, and records that users depend on?

We removed the second path only after the answer was “yes” for the capabilities we promised and “no” for the differences we could not carry.
The result removed duplicate code, made saved settings apply consistently, and published the remaining losses instead of hiding them.

This is the second post in the repaired [runtime infrastructure series](/blog/agent-profile-materialization-contracts).
The [observability post](/blog/agent-runtime-worker-observability) explains the run signals that made this deletion safe.

## Start with the user-visible differences

An **agent** is software that uses a language model and tools to complete a task.
A **worker** is one running copy of that software.
An **execution path** is the program route that starts and controls a worker.

The special path started Pi, a coding-agent program, directly.
The shared path used a connection to a remote model service, which we call a **bridge**.
A bridge sends a worker's requests to that service.

Before removing the special path, we compared what a person could observe and control through each route.
The comparison found four differences:

| Capability | Shared path before the change | Why it mattered |
| --- | --- | --- |
| Live progress | No current activity was available | A parent program could not tell whether to wait or stop the worker |
| Tool-call records | Tool requests stayed inside the final result | A reviewer could not see which tools the worker asked to use |
| Mid-run steering | The request accepted no new input after it started | A person could steer only by stopping the process and starting again |
| Provider errors | One provider failure could look like a successful empty response | A caller could mistake missing work for a valid result |

The comparison did not say the special path should remain forever.
It named the missing behavior that had to exist before removal.

## Add the missing shared behavior first

The shared path then gained two pieces of information from its existing event stream:

- current progress, such as a tool request or active turn
- the input needed to record those tool requests in the run record

The implementation also kept unknown values unknown.
When the remote service did not report that a tool finished, the shared path did not invent a success or a duration.

That distinction matters because a record of “the model asked for a tool” is not a record of “the tool completed successfully.”
The [observability post](/blog/agent-runtime-worker-observability) shows that boundary in detail.

## The deletion

Once those shared capabilities existed, the special path was removed.
The public source change measured:

| Part of the source change | Count |
| --- | ---: |
| Files changed | 16 |
| Lines added | 50 |
| Lines deleted | 3,360 |
| Special executor code deleted | 880 lines |
| Special tool-connection code deleted | 534 lines |
| Tests for the special path deleted | 1,525 lines |
| Public exports removed | 15 |

These counts describe the source diff.
They do not prove that the two paths were equivalent.
The capability comparison is the evidence for that narrower claim.

After the deletion, a Pi worker uses the same shared path as other workers.
Pi is now a model choice within one execution route, not a second runtime family that needs a separate fix for every new feature.

## Saved settings now travel through one route

An **agent profile** is a saved set of instructions, model choices, tools, and resources for a worker.
The shared path carries the four profile areas that previously made the special path different:

| Profile setting | What the shared path does |
| --- | --- |
| Reasoning effort | Converts the saved level into the coding agent's thinking setting |
| Tools | Applies the saved exclusions to the tools available in the run |
| Resources | Places the saved files and instructions in the run directory |
| System prompt | Passes the saved instructions to the coding agent |

The important change is not the field count.
It is that a saved profile no longer takes one interpretation on the special path and another on the shared path.

## The losses stayed visible

The deletion did not preserve every Pi-specific behavior.
Those differences are part of the public contract:

| Capability | Behavior after the deletion |
| --- | --- |
| Mid-turn steering | New input arrives after the current non-interactive request; an interrupt stops the process tree |
| Per-worker arguments and environment | The shared connection has no per-worker channel for them; configure them on the bridge service instead |
| Per-worker program override | The shared connection has no field for it |
| Worker trace propagation | The old worker-specific environment row is removed because the shared connection has no worker environment channel |
| Pi tool-connection file | Tool registration belongs to the bridge service; the runtime no longer writes a Pi-specific file |

This is why “3,360 fewer lines” is not the conclusion.
The useful conclusion is: use one path when it carries the behavior the worker needs, and keep a specialized path only for a capability the shared connection cannot express.

## Source and install boundaries are different

The source change is public.
An installable package is the version a user can add to an application, and it can lag behind the source repository.
The latest package version checked for this article on August 1, 2026 was still `@tangle-network/agent-runtime@0.117.0`.

Readers who need the source-level change should read the [public deletion record](https://github.com/tangle-network/agent-runtime/commit/fee88987ed5d495a765f2ea04bd0657ed9b71c8b).
Readers who need an installable release should check the [agent-runtime package and release history](https://github.com/tangle-network/agent-runtime) before depending on the newer source.

## The practical decision

Do not remove a special execution path because its code looks repetitive.
First compare the user-visible settings, controls, error behavior, and records.
Add missing shared behavior before deleting the special case.
Then publish the capabilities that remain unavailable.

That process turns cleanup into a decision a reader can inspect instead of a smaller diff that asks everyone to trust it.

## Questions readers usually ask

### Why remove a backend-specific path?

Because the shared path now carries the profile settings and run signals that made the special path different.
Keeping both would make future fixes land twice.

### Did the deletion remove behavior?

Yes.
Mid-run steering is less immediate, per-worker argument and environment overrides have no shared channel, and tool registration moved to the bridge service.

### Does the line count prove the architecture is better?

No.
The capability comparison and the named losses provide the evidence.
The line count only shows how much duplicate source was removed.

### Is the deletion in the published package?

The source record is public, but the package check on August 1, 2026 returned version 0.117.0.
Check the package version before depending on a newer source change.
