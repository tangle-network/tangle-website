An agent is preparing a migration plan.
One cheap completion notices the database change but misses the rollback path.
A larger model would probably do better, but the team wants to know whether extra work from the cheaper model can buy enough reliability without changing the model tier.

**Recursive Self-Aggregation**, or RSA, generates several candidate reasoning chains, asks the model to combine subsets of them over several rounds, and returns one candidate from the improved population.
It is **test-time scaling**: the extra computation is spent when the request arrives, not on the model’s weights beforehand.

The product surface is the Tangle Router’s chat-completions endpoint with one request option, `gateway.rsa`.
The application sends an ordinary request and gets back the answer plus a trace record: planned and completed calls, latency, cost, and stop reason.
The Router changes how one request is executed. It does not make the underlying model or the evaluation reliable.

The trade is concrete.
RSA adds model calls, token usage, and serial rounds.
Use it when parallel candidates can be checked before an irreversible action or release.
It is a poor default for every chat turn.

## The paper’s idea in one population

The [RSA paper](https://arxiv.org/abs/2509.26626) keeps a population of candidate reasoning chains.
Each round samples a subset of candidates for each population slot, asks the model to aggregate them into an improved candidate, and feeds the new population into the next round.

~~~text
generate N candidate chains
repeat T rounds:
  for each population slot:
    sample K candidates
    ask the model to aggregate them
return one candidate
~~~

The paper reports gains as inference-time compute increases and describes competitive results from a small model on several reasoning benchmarks.
Those results are workload-specific.
RSA does not turn a small model into a universally stronger one.

RSA differs from majority voting because the model sees candidate reasoning, not only final answers.
It differs from sequential self-refinement because several paths exist before each aggregation.
It differs from best-of-N because no external scorer picks the winner.
That last property is also its main limit: if every candidate shares a false assumption, aggregation can make the mistake more coherent.

## The call budget is visible before work starts

With population size N and T aggregation rounds, the simple call count is:

~~~text
initial candidates: N
aggregation calls: N × T
total: N + (N × T) = N × (1 + T)
~~~

The subset size K changes the context given to each aggregation call.
It does not change the number of aggregation calls in this basic design.

| N | K | T | Maximum calls | Practical use |
| ---: | ---: | ---: | ---: | --- |
| 4 | 2 | 2 | 12 | Small smoke test |
| 8 | 3 | 3 | 32 | Asynchronous quality pass |
| 16 | 4 | 5 | 96 | Expensive run requiring explicit budget |

The gateway should calculate the maximum call count and estimated cost before the first candidate launches.
If the caller cannot cover the maximum, fail before any work begins.
Partial fan-out is difficult to bill, retry, or explain.
Cost also depends on prompt length, output length, model prices, context reuse, and failures, so the call count is an upper bound, not a final invoice.

## Turn the call budget into a spending limit

An application can convert the upper bound into an estimate before it enables RSA.
Suppose a candidate call consumes 1,500 input tokens and 500 output tokens, and an illustrative model price is 2 units per million input tokens plus 8 units per million output tokens.
For the N=8, T=3 configuration, the 32-call upper bound gives:

~~~text
input tokens = 32 × 1,500 = 48,000
output tokens = 32 × 500 = 16,000
input cost = 48,000 ÷ 1,000,000 × 2 = 0.096 units
output cost = 16,000 ÷ 1,000,000 × 8 = 0.128 units
estimated model cost = 0.224 units
~~~

Replace the illustrative prices with current provider prices, and add a margin for retries, longer aggregation prompts, failed calls, and Router or operator fees.

A figure on paper does not stop a run. A hard cap does. The verified fleet example runs four agents under one `budgetUsd`: the Platform refuses any charge past the cap, mid-turn included, and `fleet.spend()` reports what was spent. It enforces the pattern an RSA budget needs. It does not aggregate candidates or count rounds, so the RSA call count still comes from the trace.

The output proves the cap holds across the agents and that the spend object reports remaining balance.
It does not prove the RSA call count or the per-candidate cost.

A budget also needs a stopping rule.
Stop after the configured rounds, stop when a deterministic checker passes, or stop when the remaining budget cannot change the decision.
Do not keep aggregating because the first answer looked uncertain. That turns a bounded strategy into an unbounded bill.

## A request-time Router option

Tangle’s public RSA article documents this request shape:

~~~json
{
  "model": "gemini-3.5-flash",
  "messages": [
    {
      "role": "user",
      "content": "Write and justify the migration plan."
    }
  ],
  "gateway": {
    "rsa": {
      "n": 8,
      "k": 3,
      "t": 3
    }
  }
}
~~~

The endpoint stays OpenAI-compatible from the caller’s side. That describes the request shape, not identical pricing or parameter support.
The strategy is an option on one request, not a second application-level service.
Check current model names, authentication, and option support at the [Tangle Router](https://router.tangle.tools) and the [OpenAI-compatible router guide](/blog/openai-compatible-routers-for-agents).

| Parameter | Meaning |
| --- | --- |
| n | Number of candidates in the population |
| k | Number of candidates sampled for each aggregation |
| t | Number of aggregation rounds |

Record the selected values with the result.
Otherwise a reviewer cannot tell whether a quality change came from RSA, a different model, a changed prompt, or a different budget.

## Latency grows with the rounds

The initial N calls can run in parallel.
Each aggregation round depends on the previous population, so wall time grows with T even when each round fans out internally.

That makes RSA a good fit for:

- Agent planning before an irreversible action.
- Code generation before a pull request or release.
- Structured analysis with a human review step.
- Research synthesis that can run as a background task.
- Evaluation pipelines where cost and latency are recorded.

It is a poor fit for:

- Live chat where users expect a quick first response.
- Autocomplete or interactive tool selection.
- Tiny extraction tasks with a deterministic checker.
- Real-time control loops.
- High-stakes decisions with no independent review.

The right unit of selection is the agent step.
Turn RSA on where the consequence of a weak answer justifies an extra minute or extra calls, and leave ordinary low-risk turns on the cheaper path.

## A trace makes the strategy inspectable

A **trace** is a structured record of one run.
For RSA it should record the request, model, population settings, maximum and completed calls, timing, cost, failures, and a final result reference.

~~~json
{
  "strategy": "rsa",
  "model": "gemini-3.5-flash",
  "n": 8,
  "k": 3,
  "t": 3,
  "calls_planned": 32,
  "calls_completed": 32,
  "latency_ms": 12480,
  "stop_reason": "completed",
  "trace_id": "router-run-id"
}
~~~

The trace does not need to expose every candidate to the end user.
It does need to stay available to the team deciding whether RSA improved the product.
The [Tangle trace article](/blog/self-improving-stack-trace-systems) explains why a final score without the path that produced it is hard to improve.

## Evaluation decides whether extra calls were worth it

An [**evaluation**](/blog/self-improving-stack-evaluation-gates) is a task-specific check against a stated success condition.
For code, that might be the test suite. For structured data, a labeled answer. For a migration plan, a review rubric that checks rollback, data-loss risk, and sequencing.

Do not judge RSA by whether its answer sounds more polished.
Compare a baseline model, RSA configurations, and a stronger model on the same tasks, and record pass rate, cost, latency, failure type, and the task denominator.

The test of whether aggregation bought a lift is a gate with the baseline as the shipped surface and the RSA configuration as the candidate.
The shipped gate in `evals/regression-gate` fails a candidate that scores below the baseline. For RSA, that is too weak: require the RSA score to exceed the baseline by a margin set before the run, or the extra calls are not justified.

The public [Tangle RSA benchmark repository](https://github.com/tangle-network/rsa-benchmark) reports a six-prompt smoke run:

| Strategy | Model | N | K | T | Quality pass rate |
| --- | --- | ---: | ---: | ---: | ---: |
| baseline | Gemini 3 Pro Preview | not applicable | not applicable | not applicable | 50% |
| rsa-small | Gemini 3 Flash Preview | 4 | 2 | 2 | 50% |
| rsa-medium | Gemini 3 Flash Preview | 8 | 3 | 3 | 50% |
| rsa-large | Gemini 3 Flash Preview | 16 | 4 | 5 | 33% |

These results are a small smoke run, not a general conclusion.
The repository also states that its displayed RSA cost was zero because preview-model pricing was missing from the Router pricing table. Treat that field as a measurement gap, not free inference, and rerun with current pricing before making a cost claim.

RSA-medium matching the baseline on six prompts does not prove a win on your workload.
RSA-large scoring lower shows that more calls can over-aggregate or reinforce a weak candidate.

## Compare strategies under equal budgets

Give each strategy the same prompts, the same maximum wall time, and a declared cost ceiling.
If RSA gets 32 model calls while the baseline gets one, the quality difference is real but the product comparison is incomplete.

| Strategy | Model calls | Quality pass rate | Median latency | Cost per task | Failure mode |
| --- | ---: | ---: | ---: | ---: | --- |
| Baseline | 1 | measured | measured | measured | timeout, wrong answer, or other typed outcome |
| RSA | maximum N × (1 + T) | measured | measured | measured | budget, aggregation, or model failure |
| Stronger model | declared by provider | measured | measured | measured | provider, budget, or task failure |

The table is a template, not benchmark data. It stops a quality percentage from hiding why an answer cost more or arrived later.
If extra calls help only on hard tasks, report per-task results instead of averaging the easy cases into one headline.

Use paired tasks where possible: the same prompt and input for the baseline and RSA paths, the same acceptance rule, and a record of whether both had the same tools and context.
For a migration plan, the paired result might show both strategies notice the schema change, while only RSA includes a rollback step on three of twelve tasks.
That is a hypothesis for more testing, not a general RSA advantage.

For best-of-N sampling under the same budget question, see [When best-of-five sampling pays](/blog/when-best-of-five-sampling-pays).

## Mixture and selection variants

**Mixture-of-Agents** uses different models for the candidate population and one model to aggregate them.
Diversity can help when models have different blind spots, but it complicates cost, latency, licensing, and failure analysis.

~~~json
{
  "gateway": {
    "rsa": {
      "n": 4,
      "k": 3,
      "t": 2,
      "models": [
        "glm-5.3",
        "gpt-5.4-mini",
        "gemini-3.5-flash"
      ]
    }
  }
}
~~~

**Best-of-N** generates several candidates, scores each with a separate checker, and returns the highest-scoring one.
It is stronger when the application has a real scorer, and misleading when the scorer rewards style over the behavior the user needs.

RSA is most interesting when no reliable external scorer exists and the model can use partial reasoning from several candidates.
That is a hypothesis to test, not a reason to remove a domain checker.

## Shared blind spots and uncontrolled diversity

More candidates do not mean more independent evidence.
If every call uses the same model, prompt, retrieved document, and temperature, the population repeats one blind spot, and aggregation makes the shared mistake more fluent without adding information.

The opposite failure is uncontrolled diversity.
Different models, prompts, or retrieval contexts expose useful alternatives, but they also bring different formatting, safety, licensing, and factual assumptions.
The aggregator may spend its context resolving disagreements a domain checker could settle more cheaply.

| Source of variation | Possible benefit | Cost or failure mode |
| --- | --- | --- |
| Sampling settings | More independent candidate paths | More variance and less reproducibility |
| Different models | Different blind spots | Model price, latency, and policy differences |
| Different retrieval slices | Broader evidence | Conflicting or stale context |
| Different prompts | Alternative decompositions | Harder attribution when quality changes |

Change one source of variation at a time when the budget allows it.
Otherwise a real quality change may be impossible to explain.

## What RSA does not prove

RSA does not prove a response is correct.
It does not replace a domain evaluation, a safety policy, or human approval for consequential actions.
It does not remove provider outages or privacy concerns, and it does not guarantee that candidates are independent.

Candidates can share a model, prompt, retrieved context, and mistaken assumption, and aggregation can amplify that error.
Longer context can also degrade later rounds if the model loses the important constraint among the candidates.

The strategy can fail economically too.
If 31 extra calls cut the error rate by less than their cost, RSA is a worse product even when the answer looks better.
If a 10-second run blocks a tool call that a deterministic check could have settled, the extra reasoning is waste.

## Decision rule

Use RSA for asynchronous agent steps where the output matters, a few extra rounds are affordable, and you can measure the result.
Start with N=4 and T=2, record the trace, and compare it with a single call on a fixed task set.

Keep RSA only when the measured quality gain pays for its extra cost and latency.
Use a stronger model, a domain checker, or human review when one of those solves the task more directly.
