We gave six coding agents a fresh sandbox and one job: add a client for our model router to an empty Node project.
None of them opened our llms.txt or our setup guide.
None installed our package.
Every one found the router in its own box within its first ten tool calls, five of them in its own settings or environment.
In our run, the discovery files were never reached: the box pointed the agents at the router first.
So if you are choosing between llms.txt, Markdown docs, an MCP server and a setup skill, start with the pointer.
Put it where the agent looks first, then measure what the agent does.

Our test is small, and I want its limits next to the claim.
It is six runs (n = 6) of one prompt about one product, on one model, DeepSeek V4.1 Flash.
Three runs were Claude Code and three were Codex.
Claude Code ran on DeepSeek because our router does not serve Anthropic models for our internal work.
Each box carried its own scoped router key, and its settings already named the router.
So the box itself pointed at our product before the agent did anything.
The test tells you nothing about answer engines.

## The box was the discovery surface

Five agents read the router's address straight out of their own settings or environment.
The sixth found it by searching the command-line packages preinstalled in the image.
Two Claude Code runs also ran web searches and opened the router's docs page, and one read our OpenAPI file.
The Codex runs probed router endpoints with curl.

Four agents then hand-wrote a dependency-free client against the OpenAI-compatible endpoints, with tests that stub the network.
Four finished with a working client.
That is a reasonable outcome for a router that speaks the OpenAI shape, and it says something uncomfortable about packages.
An agent that can write a fetch call against a familiar API shape has little reason to install your SDK.

The other two runs never finished.
They used their whole forty-call budget, most of it reading internal packages that ship in our default sandbox image.
That one is our bug, and we have filed it against the image.
It also shows that an agent reads whatever is nearest, whether or not you meant it as documentation.

Two runs sent a request with a made-up credential, even though the task said not to send an authenticated request.
The router refused both without running inference.
We think refusals are a discovery surface too, since an agent that hits one has to read the response.

## Put the pointer where agents look first

Our run suggests an order of places for the pointer.

Start with configuration.
If you ship a CLI, a template, a devcontainer or an environment variable, make it name your base URL and your setup document.
That is what our agents read within their first ten calls.

Next is the README inside your package and repository.
One of our agents found the router by searching preinstalled packages, and a README is prose such a search can hit.
Put the exact install line and the setup link at the top.

Then your error messages.
A refused request is a moment the agent is likely to read your response.
We think every authentication error should name the setup URL and the variable the key belongs in.

The package itself comes after those, then llms.txt, Markdown docs and manifests.
Keep all of them, as the places a pointer leads.

## Does anyone read llms.txt?

Barely: Google says it is not needed, logs show almost no AI fetches, none of our six agents opened ours, and the one regular reader Evil Martians saw was a coding agent, Claude Code. We would still ship one:
- Google says files like llms.txt are not needed to appear in its generative AI search.
- Logs show almost no AI fetches: 97% of the files Ahrefs tracked got zero requests in May 2026.
- On its own site, evilmartians.com, Evil Martians found one AI assistant that read the file regularly, the coding agent Claude Code.
- It is cheap to keep, so ship it with a pointer to your setup document on its first line, and let your server logs decide whether it earns more work.

Ahrefs looked at 137,000 sites.[^ahrefs]
About 28% publish an llms.txt, which Ahrefs calls an upper bound because its customers skew technical.
Among the fetches that did happen, 19.5% came from named AI tools, with GPTBot first and Claude Code second.
John Mueller called the file "not done for search" and a "temporary crutch, perhaps to save some tokens" for coding tools.
Chrome's Lighthouse has added an experimental llms.txt audit.

Evil Martians logged two months of agent traffic on evilmartians.com.[^em]
Their llms.txt and llms-full.txt got 170 requests, 0.3% of agent reads.
In their words, "Only one AI assistant reads `llms.txt` regularly: Claude Code."

## Serve Markdown to coding agents and plain HTML to everyone else

Serve both formats from the same URL:
- Server-rendered HTML for everyone, because AI crawlers do not run JavaScript, so they miss anything rendered in the browser.
- Markdown to any request that sends `Accept: text/markdown`, with a Vary header on Accept; coding agents took Markdown on 88% of their requests on evilmartians.com.

Claude Code took Markdown on 88% of its requests there, OpenCode 93% and GitHub Copilot 100%.
Chat assistants took it on 0.9%, and ChatGPT's fetcher on 0.7%.
Client-side analytics never see these readers.

<Figure n={2} kicker="Evil Martians, one site" headline="Markdown beat HTML for agent reads, but Claude Code made 94% of the Markdown requests" figure={readsByFormat} />

Claude Code's volume is why I would not overstate the case.
With crawlers excluded, 56% of agent reads on that site were Markdown.
Without Claude Code, the other named agents fetched Markdown 6% of the time; the largest of them is ChatGPT's fetcher.
Coding agents want Markdown; chat assistants read the HTML your visitors get.

You do not have to build the conversion yourself.
Vercel publishes a guide to [making documentation readable by AI agents](https://vercel.com/kb/guide/make-your-documentation-readable-by-ai-agents).
Cloudflare offers [Markdown for Agents](https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/), which converts HTML to Markdown at the edge.

## Is there evidence AI drives signups?

[Vercel reported](https://vercel.com/blog/how-were-adapting-seo-for-llms-and-ai-search) in June 2025 that ChatGPT referred around 10% of its new signups, up from 4.8% the month before and 1% six months earlier.
That rise, from 1% to around 10% in six months, is a vendor's own report, and it is the one public number worth repeating.

<Figure n={3} kicker="Vercel, vendor-reported" headline="ChatGPT referred around 10% of Vercel's new signups, up from 1% six months earlier" figure={vercelSignups} />

The same post cites Tally's founder, who said on X that AI search had become Tally's biggest acquisition channel.
That second claim is founder-reported.

Evil Martians counted about 62,000 agent requests made for a person against 84,000 human pageviews over their two months.
Those are reads, not signups.
Treat Vercel's number as proof the channel can matter, and measure your own.

## Watch your edge logs and two search reports

Watch these to tell whether discovery is working:
- Your server or CDN logs, counted by user agent before rendering, against a stop rule you write down before you look; ours is fewer than ten AI fetches of llms.txt in thirty days.
- [Bing Webmaster Tools' AI Performance report](https://blogs.bing.com/webmaster/2026/2/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview/), for citations in Microsoft Copilot and Bing.
- [Google Search Console's generative AI reports](https://developers.google.com/search/blog/2026/06/gen-ai-performance-reports), for impressions in AI Overviews, AI Mode and Discover.

JavaScript analytics will miss agents, so count at the edge.
Evil Martians advise against filtering on a known-AI allowlist.
Exclude obvious non-AI traffic and count whatever is left that fetched Markdown or llms.txt.
No source we read sets a stop threshold, so the number is yours.

Bing's report is in public preview and also covers select partner integrations.
It shows total citations, average cited pages, a sample of grounding queries and page-level citations.
Search Console's reports now reach every site.
They show impressions by page, country, date and, for Search, device, with AI Overviews and AI Mode combined in one Search view.
Neither announcement names a click metric, so neither will tell you about signups.

For coding agents, run a version of our test, ideally in a box that does not already name your product.
Give a fresh agent in a clean box one real task and no links.
Record whether it fetches llms.txt or your setup document, which package it installs and whether it asks before an authenticated call.
How to score agents on your tools is a separate problem, covered in [Agent-ready APIs](/blog/agent-readiness-index-methodology/).

## Tangle's entry point is one setup document

An agent that something points at us finds:
- [agent-setup.md](https://tangle.tools/agent-setup.md), the hub setup skill, which hands off to setup skills for Sandbox, Router and agents.
- A machine-readable manifest and a product catalog under the site's .well-known path.
- Safe discovery calls listed in llms.txt; health checks, manifests and public templates need no key, and the model list is sent with one.

Near the top of our [llms.txt](https://tangle.tools/llms.txt) is the instruction we want every agent to follow:

```text
To use any Tangle product as an agent, fetch https://tangle.tools/agent-setup.md and follow it.
```

The manifests and the Router's OpenAPI file sit at fixed addresses:

```text
https://tangle.tools/.well-known/tangle-agent.json
https://tangle.tools/.well-known/tangle-products.json
https://router.tangle.tools/.well-known/tangle-agent.json
https://router.tangle.tools/openapi.json
```

Every URL above was live when we checked.[^live]
None of our six agents fetched llms.txt, agent-setup.md or any manifest; one requested the Router's OpenAPI file.

## One key, approved once by a person

An agent should not need a human to sign up separately for each product.
Our setup document puts it plainly: "Tangle issues each agent one key, owned by a person who approves it once. The same key works for every Tangle product the owner approves."

The signup contract lives at a manifest on our identity host, with an optional list of the products the agent wants:

```text
https://id.tangle.tools/.well-known/tangle-agent.json
```

Our setup document, read 17 November 2026, says nothing is charged by signing up and there is no free credit.

Inside a Tangle sandbox, the coding agent gets a narrower key.
Each box in our run carried its own child router key, limited to one model and drawing on its parent key's spending cap.
It was set to expire an hour after the box was created, and it was revoked when the box was deleted.
The made-up credentials two agents tried were their own invention, not a gap in that key.

## Name the package so a guessing agent cannot install someone else's code

The wrong-package risk is concrete for us.
Our router package is scoped, and its short name is tcloud.
The unscoped tcloud on npm is an unrelated file-sharing and torrent package.
Our llms.txt also warns against an unscoped bad, which on npm is an unrelated concurrency CLI.
An agent that guesses the short name installs a stranger's code.

So llms.txt says it outright: "Only install scoped Tangle packages. Do not install unscoped packages named `tcloud` or `bad`."
Then it gives the exact install lines, quoted here from llms.txt, not run:

```bash
npm install @tangle-network/tcloud
npm install @tangle-network/sandbox
```

None of our agents installed anything, so this guardrail did not fire in our run.
It matters the day an agent reaches for an SDK by name.
Put the exact scoped install line in every surface: README, manifest, setup document and error messages.

Misdescription is the same problem in prose.
Agents repeat whatever your pages imply.
Our llms.txt carries positioning guardrails that say what is not live.
Tangle is hosted only, with no on-premises option today.
Integrations has source code but no public start link.
Write the sentence you would want an agent to quote, including the limits.

## Tools and MCP servers run where the Platform places them

Where tools run, and what you can use today:
- MCP servers run in a sandbox. With automatic placement, the Sandbox SDK's run call picks one when a profile needs files, a shell, MCP servers or a full coding agent.
- Integrations has source code but no public start link, so you cannot start it today; for your own framework, the Sandbox SDK's agent subpath already carries tool packs for the AI SDK and Mastra, and a local MCP bridge.

## Run one agent before you build anything else

Before you build an MCP server or a setup skill, run one fresh coding agent on one real task in a clean box and watch its first ten calls.
Put your pointer on the first thing it touches.
Keep llms.txt and Markdown docs as the place that pointer leads.
Watch your edge logs for coding agents, and Bing and Search Console for answer engines.
Spend more only where one of those moves.

## How we tested

**Our run.** 2026-11-18, 00:08:26 to 00:14:23 UTC, through Tangle's sandbox SDK 1.0.446. Six fresh sandboxes, one agent each: Claude Code three times and Codex three times, every one on `deepseek/deepseek-v4.1-flash` through Tangle Router. A non-streaming probe confirmed the served model from the `X-Tangle-Served-Model` header. We also tried `zai/glm-5.3`; the Router refused it for our internal account (403 `flat_plan_reserved_for_customers`), so it did not run.

**Task, verbatim, for all six:** "Add a client for Tangle's model router to this Node project. Do not send any authenticated request." Each box started with an empty `npm init -y` project in the agent's home directory. Cap: 40 tool calls per run.

**What the boxes held.** Each box carried its own scoped child Router key (`auto:sandbox:router:<sandbox id>`), which the coding agent uses. It allows only `deepseek/deepseek-v4.1-flash`, draws on the parent key's cap, expires 1 h after create and is revoked when the box is deleted. We counted 14 environment variables with credential-like names in every box (count only; values never read). The agents' own configuration files (`.claude/settings.json`, `.codex/config.toml`, `.pi/agent/models.json`) and environment variables already named `https://router.tangle.tools`.

**Counts.** Every agent found the Router URL within its first 2 to 10 tool calls: from its settings or environment in 5 of 6 runs, by grepping the CLI packages preinstalled in the image in 1 of 6. Claude Code runs 1 and 2 ran web searches and requested the Router's `/docs`; run 1 requested `/openapi.json`. 4 of 6 hand-wrote a client for `/v1/chat/completions` and `/v1/models`, some adding `/v1/responses` and `/v1/embeddings`, with tests that stub `fetch`. 4 of 6 finished with a working client; Claude Code run 3 left a partial one. Codex run 2 and Claude Code run 3 used all 40 calls; 23 and 30 of their calls touched `/usr/local/lib/tangle-cli`. Codex runs 1 and 3 sent a request with a made-up credential; the Router refused both without running inference. We give no status codes for those: a made-up bearer currently gets a different code on different endpoints, which the Router team is fixing.

**Spend,** metered from the Platform ledger: $0.2951 of the key's $1.00 cap. That is $0.2893 across the six per-box child keys ($0.0340 to $0.0634 per run) and $0.0058 of box compute plus the refused glm call.

**Boxes:** sandbox-b1061dcfe406, sandbox-47a15c2d3ec5, sandbox-3ff23acfb03d, sandbox-80859ac799eb, sandbox-a659e7134626, sandbox-ea416bf24ce9. Each was deleted by id and read back as deleted.

**Scope.** n = 6, one model, one prompt, one product, in a box already configured for that product. It shows what these agents did with a build task. It does not measure whether answer engines read llms.txt, and it says nothing about agents told to "use Tangle" or to read docs first.

**Public sources** were read on 2026-11-17. On that date, `https://tangle.tools/llms.txt` (text/plain), `https://tangle.tools/agent-setup.md` (text/markdown), both `/.well-known/` files on tangle.tools, the identity manifest, the Router manifest and OpenAPI, and the Router and Sandbox health checks each returned HTTP 200. The npm registry read the same day showed unscoped `tcloud` at 0.7.12 and scoped `@tangle-network/tcloud` at 1.0.4.
