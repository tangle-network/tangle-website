Ask an AI coding assistant to “have three specialists work in parallel, compare their patches, and stop the losing attempts.”
The sentence sounds precise.
The assistant may still make one model call, mention three imaginary specialists, and return the first patch it wrote.

The deciding fact is whether the software running the agent can create those actions.

An **agent runtime** is the software that starts an agent, gives it tools, records its work, and decides when the run ends.
A **worker** is one running copy of that agent.
The runtime’s **execution shape** is the order and relationship of those actions: one worker after another, several workers at once, a review step, a retry, or a human approval.

This post argues for one simple rule: a prompt can request a behavior, but the runtime must own any behavior that needs to be enforced, measured, or repeated.

## A request is not an action

Consider the phrase “work in parallel.”
For a person, it means several independent runs, a limit on how many run at once, separate state, a way to collect results, and a rule for choosing among them.

For software, those are separate capabilities:

| Desired behavior | Runtime must provide |
| --- | --- |
| Start several attempts | A way to create independent workers |
| Prevent conflicts | Separate files, memory, or other mutable state |
| Limit spending | A shared limit for calls, tokens, time, or money |
| Compare results | A checker and a visible scoring rule |
| Choose a winner | A decision that the runtime follows |
| Stop losing work | Cancellation that reaches every child worker |
| Learn from the run | A record containing each branch and its result |

If the runtime has none of those controls, the prompt can only ask the model to pretend.
That may produce a convincing explanation, but it does not create parallel execution.

## What execution shape means

The word **topology** is useful here only as shorthand for the execution shape of the work.
It answers four questions:

- which agent or tool runs
- in what order or at the same time
- what state each run can see
- what condition ends the work

One simple run has one worker and one result.
A refinement run repeats the same task after a checker rejects the previous result.
A fanout run starts several attempts, checks each result, and applies a winner rule.

The important object is not the worker’s persona.
It is the control structure that determines what happened.

## Why prompts cannot provide runtime authority

A prompt cannot create an operating-system process.
It cannot reserve a separate worktree, cap the number of simultaneous requests, guarantee that every child record is saved, or resume a run after the host dies.

It also cannot make a checker’s decision final if the loop ignores that decision.
The model can be asked to stop after a pass, while the runtime continues making calls.
The model can be asked to ask for approval, while the tool remains available without approval.

Those are control failures, not wording failures.

## The smallest useful runtime model

A runtime needs a few explicit pieces:

| Piece | Plain-language job |
| --- | --- |
| Loop | Start work, receive a result, and decide whether another step is needed |
| Worker description | State which model, tools, instructions, and resources one run receives |
| Checker | Turn a result into a pass, fail, or explained score |
| Execution shape | Choose refinement, fanout, handoff, retry, or another flow |
| Budget | Limit time, model calls, tools, tokens, or dollars |
| Record | Preserve inputs, events, decisions, outputs, and failures |
| Cancellation | Stop work that no longer matters |

Changing the execution shape should not require rewriting the model prompt.
That separation lets a team compare one worker with a refinement loop while holding the model, tools, and task constant.

## What the public runtime exposes

The public [agent-runtime repository](https://github.com/tangle-network/agent-runtime) contains a loop that can run repeated attempts and bounded parallel attempts.
Its public design separates the loop, the execution-shape choice, the checker, the worker description, and the output parser.

In plain language, the source describes two useful flows:

| Flow | What it does |
| --- | --- |
| Refinement | Try one result, check it, and try again until it passes or reaches a limit |
| Fanout and vote | Run several attempts, check each, and return the highest-scoring valid result or report that none passed |

The public repository is the authority for which interfaces and releases exist.
This article does not turn a conceptual idea such as durable replay or nested supervision into a shipped API.

## Compare execution shapes at equal cost

An eight-worker design can beat a one-worker design because it spent eight times as much, not because its control structure was better.
That can still be the right product choice, but the comparison must say what was purchased.

For each run, record:

- number of workers
- model calls and tool calls
- input and output tokens
- wall-clock time
- failed and cancelled branches
- human approvals
- total cost
- final quality score

Then compare the right question:

| Question | Evidence needed |
| --- | --- |
| Is the result better at the same budget? | Paired tasks with equal limits |
| Is the result cheaper at the same quality? | Cost and score together |
| Is the result faster at the same quality? | Latency and score together |
| Is the result safer? | Failure, approval, and policy records |

Without those columns, “more agents” is not an improvement claim.

## A checker and a winner rule are different

A **checker** asks how well one result satisfies a task.
A **winner rule** decides which result the runtime returns or which branch continues.

The checker may report a score, but the winner rule also needs to account for cost, safety, deterministic failures, and missing evidence.
If the runtime returns the first result regardless of the checker, the checker is decoration.

Keeping the two decisions separate makes the system easier to test.
The checker can be calibrated on examples.
The winner rule can be tested against budgets, timeouts, failed branches, and approval requirements.

## What a real multi-worker record must show

If a runtime claims to have used several workers, the record should let a reader answer:

- which workers were created
- what each one received
- which tools each one used
- what state was shared or isolated
- which checks ran
- why one result won
- which branches were cancelled
- how much time and money the run used
- whether the control path can be replayed

Without that record, a successful result does not show whether the extra workers helped, whether one worker did all the work, or whether the winner rule was ignored.

## The practical decision

Keep coordination in a prompt when it is advice the model may follow.
Move it into the runtime when it must be enforced, measured, or repeated.

Use a single worker when the task is small and the cost of extra attempts is not justified.
Use refinement when a result can be checked and improved.
Use fanout when independent attempts provide useful diversity and the winner rule can be explained.

Do not call a system self-improving because it changes prompts after a run.
It is improving its execution shape only when it can propose, run, compare, and retain a different control structure with the same evidence standard.

## Questions readers usually ask

### Can a better prompt create true parallelism?

No.
It can ask the model to imitate parallel work, but real parallelism requires the runtime to start and track several independent workers.

### Does several workers always improve quality?

No.
It may increase cost, latency, disagreement, and cleanup work.
Compare execution shapes under the same budget before calling one better.

### What happens when one branch fails?

The runtime needs an explicit policy: retry, ignore, stop, or ask for human review.
The policy and the failed branch should remain in the run record.

### Is a score enough to choose a winner?

No.
The winner rule also needs cost, safety, completeness, and deterministic-failure policy.

### What should be built next?

The next useful primitive is a small, durable run record that preserves child attempts, budgets, cancellation, and replay boundaries.
That evidence should come before a larger menu of coordination patterns.
