When an automated program runs for several minutes, silence is not a useful status.
The person or program waiting for it needs to know whether it is thinking, using a tool, waiting on a remote service, or already finished.

The shared agent path used to expose none of that for runs behind the shared connection.
It now exposes live progress and the tool requests that arrive over the stream, while leaving completion and duration unknown when the remote service never reports them.

That last part is important.
An honest record can say “the model requested this tool” without pretending that the tool succeeded.

This is the third post in the repaired [runtime infrastructure series](/blog/agent-profile-materialization-contracts).
The [runtime deletion post](/blog/agent-runtime-generic-executor-deletion) explains why the same shared path now serves the coding-agent program that previously had its own route.

## The words in this story

An **agent** is software that uses a language model and tools to complete a task.
A **worker** is one running copy of that software.
A **parent** is the program that starts a worker and decides whether to wait, steer, stop, or restart it.
A **bridge** is the shared connection that sends the worker's requests to a remote model service.
A **trace** is the record of what happened during a run.

The bridge's problem was not that the worker could not finish.
The problem was that the parent had no reliable view of the work while it was happening.

## Two missing signals created two bad decisions

Before the change, the bridge implemented neither live progress nor a source for the worker's tool requests.
The parent therefore had to make decisions from silence:

| Missing information | Decision made without it |
| --- | --- |
| Current activity | Whether to wait, steer, stop, or restart the worker |
| Tool requests | Which tools the worker asked to use and what it asked them to do |

A quiet interval could mean model work, a disconnected service, a cancellation, or a run that had already ended.
The parent could not tell those cases apart.

## Read local activity immediately, refresh remote status separately

The fix keeps a local record of events as they arrive.
That record includes the turn number, current tool activity, steering activity, queued steering messages, and the model selected for the run.

The progress read returns those local facts immediately.
It does not wait for another network request.

The remote service owns one fact the local record cannot know on its own: whether the run has become terminal.
The bridge refreshes that remote state no more than once per second and updates the local record when the answer arrives.
If the remote run has ended, the bridge removes the stale “still running” state instead of repeating it forever.

This split keeps a status read from becoming another way to hang the worker.
Local activity is available now.
Remote status is refreshed later and labeled as such.

## Record every requested tool, but not a result that never arrived

A **tool call** is a request from the model to use a function or external tool.
The bridge now records each tool call from the stream as it arrives.

The stream reports the model's request, but it does not report the tool finishing.
The trace can therefore record the input event and its arguments, but it must leave the outcome and end time blank.

| Field | What the bridge can say | What it must leave unknown |
| --- | --- | --- |
| Tool name | Which tool the model requested | Whether the tool completed |
| Arguments | The arguments included in the request | Whether the tool accepted them |
| Start time | When the request arrived | The true completion time |
| Result status | Not supplied by this stream | Success, failure, or cancellation |

The bridge does not mark every request as successful.
It does not create a zero-millisecond duration.
Those values would turn missing evidence into a false result and would corrupt any later success-rate or latency calculation.

The [OpenAI tool-call documentation](https://platform.openai.com/docs/api-reference/chat/create) describes the request event.
It does not supply a completion event that the bridge never received.

## What changed for a parent program

With the new information, a parent can make narrower decisions:

- wait when the local record shows an active turn or tool request
- stop or restart when the remote run is terminal
- include requested tools in the settled trace
- refuse to calculate success or latency from fields the stream did not send

The runtime supplies the facts and their limits.
Product policy still decides how long to wait, when to interrupt, and whether an incomplete trace is acceptable.

## Why this made one shared path possible

The follow-up removal of the special Pi execution path made that coding-agent program use the same bridge as other workers.
The deletion removed 3,360 lines in 16 files, including 880 lines of special executor code, 534 lines of special tool-connection code, and their tests.
The [deletion post](/blog/agent-runtime-generic-executor-deletion) lists the capabilities gained and the behaviors intentionally left behind.

The shared path now exposes the same progress and trace entry points for those workers.
It still cannot report tool completion when the remote protocol reports only the request.
That is a limit of the information sent over the connection, not a missing default value.

The public [observability change](https://github.com/tangle-network/agent-runtime/commit/76db51d37bc9885f985a2ff060fcdbb6970a8dee) records the implementation and its live check.

## The practical decision

Expose the information a parent needs to decide whether to wait, steer, stop, or restart.
Preserve unknown fields as unknown when the remote service does not send them.
If a product needs tool success or duration, measure those events at the tool boundary rather than inferring them from the model's request.

That is the difference between showing activity and claiming an outcome.

## Questions readers usually ask

### Does the bridge now report successful tool execution?

No.
It reports the model's tool request and arguments.
The bridge connection does not report tool completion, so status and duration remain unknown.

### Why not mark every observed request as successful?

Because a requested tool can fail, be cancelled, or never start.
Marking it successful would turn missing evidence into a false result.

### Can a progress read block the worker?

The local record is read immediately.
The remote status refresh runs separately and is limited to one request per second.

### Does the shared path preserve every feature of the old special path?

No.
The generic connection has no channel for some backend-specific arguments and environment overrides.
The [deletion record](/blog/agent-runtime-generic-executor-deletion) names those losses beside the shared capabilities.
