The fastest way to make an API agent-ready is also a common mistake: turn every endpoint into a tool.
Agents do better with a few distinct, namespaced tools shaped around the jobs your users do, because too many or overlapping tools distract them, described the way you would brief a new hire.
Generate them from an OpenAPI spec you have repaired first.
Then prove it with real multi-step tasks against your product: check each outcome, record accuracy, runtime, tool calls, tokens and errors, read the transcripts, and keep a held-out set you never tune against.
A score for your docs or your spec cannot tell you whether an agent finishes the job.

An earlier version of this page described an "Agent Readiness Index" as if we ran it.
We never built it, and there are no results behind the name.

This post starts after an agent has found you.

## Build one tool per job your customers do

Anthropic's team calls endpoint wrapping "a common error" in their guide to [writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents).
The reason is context: agents do better with a few distinct, namespaced tools, and too many or overlapping tools distract them.
Your server can page through ten thousand contacts for free.
An agent pays for every token it reads, so a list-everything tool burns its attention on rows it never needed.

Their advice is to build "a few thoughtful tools targeting specific high-impact workflows".
One tool can make several API calls underneath and return only what the agent needs next.
Their own examples make the shape clear:

```text
One tool per endpoint                 One tool per job
-----------------------------------   ------------------------------------------------
list_users, list_events,              schedule_event
create_event                            finds a free slot and books it
get_customer_by_id,                   get_customer_context
list_transactions, list_notes           the customer, recent transactions and notes
read_logs                             search_logs
                                        matching lines with surrounding context
list_contacts                         search_contacts
```

Most published servers still wrap.
A study of 116 official MCP servers found that 92% expose tools as bare API wrappers.[^v4]
The same servers expose a median of only 19% of their API's operations.
So vendors already leave most operations out, and the tools they keep still mirror endpoints.
When the authors filtered and regrouped operations, the median tool count per API fell by a third.
We read that as room to cut further.

Give each tool one distinct purpose and a namespace; Anthropic found that too many or overlapping tools distract agents.
Name tools so an agent can tell yours from everyone else's.
Anthropic groups related tools under a shared prefix, by service (asana_search) or by resource (asana_projects_search).
They found that putting the namespace at the front or the back changed their eval results, and the better choice varied by model.
We would pick one scheme and let the eval below decide.

Our rule is to start from the tasks you will test with and write one tool per family of tasks.
Add a tool only when a task fails without it.

## Write descriptions, responses and errors as prompts

Every tool description and parameter spec is loaded into the agent's context.
We treat them as prompts, because that is how the agent reads them: explicit descriptions, parameter names that leave no room for a guess, and strict schemas for inputs and outputs.
Anthropic's test is to describe the tool the way you would explain it to a new hire.
Spell out the query formats, the niche terms and how your resources relate, because the agent knows none of it.

Parameter names should leave no room for a guess.
Anthropic's example is a parameter called "user".
We would rename it to say user ID, so the agent never has to guess what goes in it.
Anthropic also says to enforce the expected inputs and outputs with strict data models. We read that as: a malformed call is refused with a clear message instead of running.

Responses should carry meaning rather than plumbing.
Return names an agent can reason about, not opaque UUIDs it has to copy around.
Anthropic found that resolving UUIDs to readable names made Claude noticeably more precise in retrieval tasks.
When an agent needs both, give it a switch between concise and detailed output.
In their example the concise response was 72 tokens against 206 for the detailed one.

Long responses need defaults that keep them short.
Paginate, filter or truncate, and tell the agent how to ask for more.
Claude Code restricts tool responses to 25,000 tokens by default, and we design for well under that.[^cap]

Errors are prompts too.
An error code with no explanation leaves the agent to guess and retry.
An error that names the bad field and the fix gives the agent what it needs to get the second call right.
Here is the difference, in an example we wrote:

```text
Unhelpful
  {"error": "INVALID_REQUEST"}

Helpful
  {"error": "start must be a date like 2026-11-17, got 'next tuesday'.
             Resolve relative dates before calling schedule_event."}
```

## A generated MCP server inherits every gap in your spec

If you have an OpenAPI spec, generating an MCP server from it is a reasonable first draft.
Mastouri and colleagues measured exactly that.
In the paper's third version, the source of the widely repeated 99.9%, about three in four generated tool calls worked as generated.
Every failure traced back to something missing or inconsistent in the spec.

<Figure n={1} figure={openApiToMcp} kicker="arXiv 2507.16044 · OpenAPI to MCP" headline="About 76% of sampled calls (v3) or tools (v4) worked as generated, before the spec was repaired" />

Fixing the specs by hand, about 19 lines per API, took that version to 99.9%.
That number gets quoted without its condition.
It needed a person to find and fix each spec, and it comes from the paper's earlier version.
The latest version studies more APIs and repairs the spec automatically, and reports 94.2%.

We read two things from this.
Your spec is the real interface, so fix its omissions before you generate anything.
And the generator in v3 (AutoMCP) produced one tool per endpoint (5,066 endpoints, 5,066 tools), the shape the previous section warns against.
Its success rates measure whether a generated tool could be called correctly, not whether an agent completed a user's job with it.

So generation is enough to get a server running, and every failure traced to the spec.
It is not enough to call your API agent-ready: in v3 only 76.5% of generated calls worked until about 19 lines of spec fixes per API raised that to 99.9%.
Generate from a repaired spec, then consolidate the operations agents actually chain into job-shaped tools.

## Agent readiness is a task the agent finishes

Readiness scores already exist, and they are cheap to run as a first check.
For example, [Fern's Agent Score](https://labs.buildwithfern.com/) checks your docs and grades them from 0 to 100.
We think of them as a lint pass.

They score documents.
We want to know whether an agent, handed a real multi-step job with a verifiable outcome, gets it done with your tools.
That needs the method Anthropic describes: realistic tasks, a checkable outcome for each, and a record of how the agent got there.

### Write tasks the way customers ask

A good task reads like a support ticket and needs several tool calls.
A weak one tells the agent which call to make.
These two tasks are from Anthropic's lists of strong and weak tasks:

```text
Strong
  Customer ID 9182 reported that they were charged three times for a single
  purchase attempt. Find all relevant log entries and determine if any other
  customers were affected by the same issue.

Weak
  Search the payment logs for purchase_complete and customer_id=9182.
```

The weak task tests whether the agent can type a query.
The strong one tests whether your tools let it work out which query to type.

### Check the outcome, not the agent's account of it

Pair every task with a result you can verify.
For an API that usually means reading the state afterwards: one refund exists, the meeting is on the calendar, the right log lines came back.
A string match against a known answer is fine when the answer is text.
Keep the check loose enough to accept a correct answer phrased differently.

We do not let the agent grade itself.
Its summary is a claim, and the state of your system is the evidence.
The check runs outside the agent, against the system it changed.

### Record more than pass or fail

We treat accuracy as the headline, but it hides the reason.
Anthropic also recommends collecting runtime per tool call and per task, the number of calls, total tokens and tool errors.
Those point at the fix.
Many redundant calls suggest your pagination or limits are wrong.
Many invalid-parameter errors suggest a description needs work.

We read the raw transcripts too.
Agents often leave things out when they explain themselves, and the raw transcript shows what they actually did.
Anthropic's example is Claude appending the year to its web search queries, which a better tool description fixed.

### Keep a set of tasks you never tune against

Once you start editing descriptions to pass tasks, you will overfit them.
Anthropic kept held-out test sets for exactly this reason.
We would split the tasks before the first run and only look at the held-out score when deciding to ship.

## Run each task in a sandbox and gate on the baseline

Here is that loop in our own Sandbox SDK and eval package.
Each task gets a fresh sandbox with a coding agent in it.
The check is a command we run after the agent's turn, and its exit code is the score.
The candidate has to score at least as well as the shipped version or the build fails.

<Example path="evals/regression-gate" title="Score each task by a command the caller runs, and fail on a regression" />

The tasks here fix failing tests, not API integrations.[^example]
For your API, we would swap the task text and the check.
The task becomes a customer request against a test account.
The check becomes a query against that account's state after the agent finishes.

## Ship the next tool only when tasks say so

Before you build another tool, write a few dozen tasks from real customer requests, each with an outcome you can check.
Split off a held-out set.
Run them against what you have today, whether that is raw endpoints or a generated server.
Then change one thing at a time: consolidate a family of endpoints, rewrite a description, fix the spec, sharpen an error.
Keep the change if the held-out pass rate goes up and the errors and token counts go down.

## How we tested

We did not run an Agent Readiness Index, and none exists. A search of our GitHub organization's code and our internal project index on 17 Nov 2026 found the name only in the earlier version of this post. The method above is how we would measure, and no results are claimed.

Every outside claim was checked against its source on 17 Nov 2026:

- Tool design, response, error and evaluation guidance: Anthropic, [Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents). The 206- and 72-token responses, the 25,000-token Claude Code default, the namespacing result and the held-out sets are all from that post.
- OpenAPI-to-MCP results: Mastouri et al., arXiv 2507.16044. Version 3, posted 10 Sep 2025, reports 50 APIs, 5,066 endpoints, 1,023 sampled tool calls, 76.5% out of the box, and 99.9% after manual spec fixes averaging 19 lines per API. Version 4, posted 6 Apr 2026, reports 80 OpenAPI contracts, 76% baseline and 94.2% after automated repair, plus the 116 official MCP servers, 92% bare wrappers, 19% median operation exposure and the one-third tool-count reduction. Quote the version with its number.
- Readiness scorers: Fern Agent Score grades docs from 0 to 100. We list it for comparison. We have not run it or compared its scores with task outcomes.
- The recorded example, regression-gate, ran on production on 2 Nov 2026 with exit 0 and $0.1818 of reported usage. It is a code-fix task, not an API-integration task.
