A Tangle Blueprint is a public service definition.
It tells the person or service running it what to run, and that runner is called an **operator**.
It also tells a buyer what can be requested.
The definition should specify the job inputs and outputs, the program and runtime requirements, the payment rule, the evidence returned, and what happens when execution fails.

This is different from a product landing page.
A landing page describes a service to a human.
The Blueprint's job schema, runner entrypoint, and install, upgrade, and health-check instructions let independent operators run the same service.

The article assumes you have never used Tangle.
Tangle is a network for services that can be run by independent operators.
An **operator** supplies the machine and keeps the service available.
A **service instance** is one running copy of that service.
A **job** is one request sent to the instance.

## Start with the job, not the brand name

Suppose you want to offer a paid document classifier.
The useful first sentence is “a caller submits a document and receives a list of labels, confidence values, and a reference to the model version used.”

That sentence gives a developer something to implement and gives an operator something to run.
It also exposes questions that a slogan hides:

- What file types are accepted?
- What is the maximum document size?
- What does a malformed file return?
- How long may a job run?
- Does the result include the input checksum and model version?
- Is the caller charged for a rejected request?

Write those answers down before choosing a network or payment rail.

## The Blueprint contract

The contract has five parts.

| Part | What to specify |
| --- | --- |
| job interface | names, inputs, outputs, limits, and error codes |
| runtime | source artifact, dependencies, environment variables, ports, and hardware |
| operator work | how to install, start, upgrade, health-check, and stop the service |
| payment | fixed price, quote, payment challenge, refund, and expiry behavior |
| evidence | result format, request ID, service version, timing, and any quality check |

The word “verification” needs care here.
For a document classifier, the network can record which operator ran which version.
That does not establish that the labels are correct.
Correctness may require a test set, a second model, or human review chosen by the service owner.

## A small public SDK runner

The public [Blueprint SDK](https://github.com/tangle-network/blueprint) gives a Rust service a runner and a router.
The router maps a job number to the function that handles it.
The runner supplies the operator-facing process that receives jobs and returns results.

This is the smallest runner shape documented in the repository:

```rust
use blueprint_sdk::Router;
use blueprint_sdk::runner::BlueprintRunner;
use blueprint_sdk::runner::config::BlueprintEnvironment;

async fn classify() -> &'static str {
    "labels:invoice,confidence:0.94"
}

let environment = BlueprintEnvironment::default();
let router = Router::new().route(0, classify);

BlueprintRunner::builder((), environment)
    .router(router)
    .run()
    .await?;
```

The return value is deliberately tiny.
The example is there to show the public boundary, not to pretend that a string is a production classifier.
In a real service, the function would validate an input, call the classifier, return a typed result, and map failures to documented error codes.

Check the repository's current version and setup instructions before compiling this example.
The public [Tangle documentation](https://docs.tangle.tools) is the source for current network and operator steps.

## Make invalid input visible

An operator needs to know whether a job failed because the service was unhealthy or because the caller sent something the Blueprint forbids.
Those cases should not look identical to the buyer.

For the classifier example, the contract could define:

```text
valid PDF under 20 MB -> classify and return labels
unsupported MIME type -> reject before payment is captured
oversized file -> reject with max_size
model timeout -> return retryable_timeout and request ID
provider error -> return upstream_failure and operator evidence
```

This is a product decision, not a protocol default.
Write the behavior in the public service contract and test each branch locally before an operator deploys it.

## Publish the artifact an operator can run

The operator should not have to reconstruct the service from a blog post.
Publish a versioned artifact, its source or source reference, required configuration, and a health check.
If a model or prompt changes the output, include that version in the service record.

The public SDK repository documents a deployment flow based on a Blueprint definition and a metadata source.
A representative public command is:

```bash
cargo tangle blueprint deploy tangle \
  --network testnet \
  --definition ./definition.json
```

The command and manifest fields can change, so use the current [deployment documentation](https://github.com/tangle-network/blueprint) as the authority.
The point of the command is that an operator receives a named definition rather than a private set of instructions.

Do not put credentials, private filesystem paths, internal commit inspection, or incident notes in a public Blueprint.
The operator needs the public artifact and the public runbook.

## What an operator checks before accepting

An operator should be able to answer these questions from the published materials:

| Check | Reason |
| --- | --- |
| What artifact is running? | prevents silent code or model drift |
| What inputs are allowed? | avoids unsafe or unbillable work |
| What hardware is required? | prevents jobs from landing on an unsuitable machine |
| How is health measured? | separates a live process from a useful service |
| How does payment work? | prevents unpaid or ambiguous jobs |
| How are failures reported? | gives the operator a supportable incident path |
| How is an upgrade rolled back? | limits damage from a bad release |

If the answer exists only in a private chat with the developer, the service is not ready for independent operation.

## Keep the user contract shorter than the runbook

A buyer should not need to learn operator key management or deployment internals to call a job.
The user-facing page should show the job name, input schema, output schema, price or quote rule, expected latency, failure codes, and returned evidence.

The operator runbook can contain more detail.
It may describe keys, ports, disk requirements, log retention, and the upgrade sequence.
Both documents should refer to the same Blueprint version.

Pinning both documents to one Blueprint version makes an interface mismatch detectable before an operator accepts a buyer's request.

## What the protocol does not decide for you

The protocol coordinates registration records, job requests, payment states, and the evidence attached to each result.
It does not choose a useful model, write a safe prompt, guarantee uptime, or determine whether a classification is correct.

Those responsibilities belong in the service definition and the operator's runbook.
If the service needs a second pass, a fixed test set, or a human approval, say so.
Do not replace that requirement with a generic “verified” badge.

## Decision rule

Use a Blueprint when more than one operator should be able to run the same service and the job contract can be written precisely.
Keep the service in a normal application backend while the interface, failure behavior, or operating requirements are still changing every day.

Start with one input, one output, and one evidence path that a local test can execute in one sitting.
Once that path works, add payment, operator choice, and more demanding workloads one at a time.

## FAQ

### What is a Blueprint protocol?

It is Tangle's model for publishing a reusable service definition that independent operators can run.

### Is a Blueprint the same as Blueprint Agent?

No.
Blueprint Agent is a developer workbench.
A protocol Blueprint is the service definition and job contract that an operator runs.

### What should a Blueprint include?

It should include the job interface, runtime requirements, artifact source, payment behavior, evidence, failure codes, and operator runbook.

### Does a Blueprint guarantee service quality?

No.
It makes the service contract and operating responsibilities explicit.
Quality still depends on the code, operator, monitoring, and service-specific checks.
