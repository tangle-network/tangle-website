When a company buys compute from an unknown operator, the price is only half the problem.
The buyer also needs to know what was promised, whether the work happened, and what happens when the result is wrong.

An **RFQ**, or request for quote, is a process where a buyer asks for a price and an operator returns a time-limited offer.
An **operator** is the person or team providing the machine and doing the work.
A **consumer** is the person or application paying for the job.

Tangle adds three checks to that ordinary exchange:

1. the price is a signed promise that can be checked later
2. the result can be checked with a mechanism chosen for the job
3. an operator can lose staked collateral when the agreed failure condition is proven

Signed quotes, job-specific checks, and staked collateral address different risks.
No one mechanism independently verifies every computation, so the promise, evidence, and consequence must stay explicit enough for a consumer to choose a risk level.

This post explains the design and its limits.
The [Blueprint explanation](/blog/how-blueprints-work) introduces the service model, and the [Tangle verification overview](/blog/how-tangle-verifies-work) describes the wider result-checking system.

## Two different things need a price

Tangle describes two quote types because a long-running service and one job ask different pricing questions.

| Quote type | What it prices | Example |
| --- | --- | --- |
| Service quote | Keeping resources reserved for a period | A GPU service running for a defined lifetime |
| Job quote | One unit of work on an existing service | One inference or data-processing request |

A service quote can use resource rates for CPU, memory, GPU time, and duration.
A job quote can be a direct price for a particular job on an already-running service.

The distinction prevents a common mistake: treating “how much does it cost to keep this capacity available?” and “how much does this computation cost?” as the same number.

## A quote is more than a dashboard number

The quote is signed with [EIP-712](https://eips.ethereum.org/EIPS/eip-712), a standard format for signing structured data on Ethereum-compatible networks.
The signed data includes the service, job, price, creation time, and expiry.

The signature binds the operator to those fields.
Changing the price, job, chain, or receiving contract breaks the signature.
The source reports a default quote lifetime of 300 seconds, with a one-hour maximum age.
After submission, the on-chain record marks the quote as consumed so the same offer cannot be used twice.

That gives the consumer four properties to check:

| Property | Why it matters |
| --- | --- |
| Signed fields | The operator cannot change the offer after the consumer accepts it |
| Expiry | A consumer cannot hold an old price forever |
| Chain and contract binding | A quote for one network cannot be replayed on another |
| Single use | A settled quote cannot pay for two jobs |

This is the difference between “the price endpoint says $X” and “the price is a signed offer with a clear lifetime.”

## Stablecoins need a second conversion

Some operators quote in the chain’s native currency but accept a stablecoin through the [x402 payment path](/blog/blueprint-sdk-x402-payments-runnable-jobs).
The gateway converts the quote using the native-currency exchange rate, any operator markup, and the token’s decimal precision.

A reported example: a 0.25 ETH quote at 3,200 USDC per ETH with a 0.5% markup becomes 804 USDC.
That example is arithmetic, not a market forecast.
The operator still needs a policy for how often the rate changes and what happens when the rate source is unavailable.

Keeping the quote and its fingerprint together lets the consumer verify that the payment covered the exact amount offered.

## Results need a job-specific check

No single result check works for every computation.
The SDK describes several mechanisms, and each proves a different property.

| Mechanism | What it can show | Main limitation |
| --- | --- | --- |
| Repeated execution | Several operators produced the same result | Non-deterministic work may disagree even when everyone is honest |
| Cheap correctness check | A small check accepted or rejected an expensive result | Only works when checking is much cheaper than doing the work |
| Hardware attestation | Approved code ran inside a protected environment | It proves code identity, not that the code is correct |
| AI-specific checks | Model identity or behavior matches selected checks | A canary can miss a sophisticated substitution or quality problem |
| Combined checks | Several independent signals agree | More operators and checks increase cost and complexity |

**Attestation** is a signed statement from protected hardware about the code that ran.
A **canary** is a known test input used to see whether a model behaves as expected.

The source review did not find cheap on-chain correctness hooks on every Blueprint.
Check the current release before depending on that mechanism for a specific job.

## Financial penalties make cheating expensive

An operator can stake collateral before accepting work.
If the agreed checking process proves a slashable failure, the protocol can reduce that collateral.
This is called **slashing**.

The deterrence condition is simple: the expected loss from being caught must exceed the profit from cutting corners.

For example, suppose an operator could save $5,000 by running a cheaper model.
If the chance of detection is 80% and the stake at risk is $50,000, the expected loss is $40,000.
That makes the shortcut a bad financial bet under those assumptions.

This is an illustrative calculation, not a measured security guarantee.
The real result depends on detection quality, stake size, false positives, and whether the operator behaves rationally.

## Two speeds of penalty

The source describes two ways to execute a penalty:

| Mode | What happens | Why it exists |
| --- | --- | --- |
| Immediate | The penalty executes in the same transaction that proves the failure | Strong deterrence when the checking rule is mature and well-audited |
| Reviewable | The penalty waits through a veto period | Human review can stop a false positive in a newer or more complex Blueprint |

A new Blueprint may need the reviewable mode while its checking rules collect evidence.
Moving to immediate penalties should be a separate decision based on false-positive history and audit quality.

The penalty monitor also needs to report whether collateral is already at risk.
That is operational information for the operator, not proof that every job result is correct.

## The complete flow

The request-to-result sequence is:

1. A consumer requests a service or job quote.
2. The operator returns a signed offer with a price and expiry.
3. The consumer checks the signature and submits the quote with payment.
4. The on-chain contract rejects an expired or already-consumed offer.
5. The operator performs the work after settlement.
6. The job’s chosen checking mechanism evaluates the result.
7. A proven slashable failure can reduce the operator’s stake.

Each layer handles a different failure.
The signature prevents price changes.
The expiry and single-use record prevent replay.
The result check tests the work.
The stake makes a proven failure costly.

None of those layers makes a vague job specification safe.
The consumer still needs to define what counts as a correct result before asking for a quote.

## The practical decision

Use signed on-chain quotes when price changes, replay, and operator accountability matter enough to justify the transaction and operational complexity.

Choose the result check from the job’s properties.
Use repeated execution for deterministic work, hardware evidence for confidentiality and code identity, and a cheap correctness check when one exists.
Do not use a TEE report as proof of output quality.
Do not use a stake amount as proof that a checking mechanism catches failures.

Start with one job, one quote type, one explicit success condition, and a reviewable penalty.
Add more mechanisms only when the first one produces evidence you can inspect.

## Questions readers usually ask

### Can an operator change a price after I receive a quote?

Not without invalidating the signature.
The signed price remains valid until its expiry, and the consumed record prevents reuse after submission.

### What if operators disagree?

The job’s result rule decides what happens.
A quorum can accept matching results, but non-deterministic work needs a different criterion or a human review path.

### Does staking guarantee honest work?

No.
It gives the system a financial consequence when a checking mechanism proves a failure.
It does not improve a weak checking mechanism.

### Is every checking mechanism already available?

No.
The source describes some mechanisms as shipped integrations and others as future work.
Check the Blueprint and package version before depending on a specific path.

### Why not rely on reputation?

Reputation can inform a choice, but it does not bind a signed price, prevent replay, or automatically return value when a proven failure occurs.
