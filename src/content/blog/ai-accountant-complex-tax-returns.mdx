Suppose Maya is a software founder with a salary, stock sales, a small partnership, crypto transactions, and a move between two states.
She gives an assistant a folder of PDFs, spreadsheets, and wallet exports and asks, “Can you get my return ready?”
The problem is that the folder can be incomplete, the facts can conflict, and a polished answer can hide both failures.

An **AI accountant for complex tax returns** should turn that request into an inspectable preparation packet, not a confident summary.
It should build a source index, extract facts with page references, reconcile contradictions, run repeatable calculations, and produce a packet that Maya and her advisor can inspect.

This article describes preparation software, not tax advice.
The taxpayer and a qualified professional must make the final decisions and approve anything submitted to a tax authority.

## What makes a return complex

“Complex” does not mean that a model needs a longer prompt.
It means that the return combines records with different owners, dates, currencies, entities, or filing obligations.

Maya’s folder might contain these files:

| Document | Plain-language meaning | What the software can prepare |
| --- | --- | --- |
| W-2 | An employer’s report of wages and withholding | A wage record tied to the employer and tax year |
| 1099 | A report from a bank, broker, platform, or payer | Interest, dividends, proceeds, or other income candidates |
| K-1 | A partner’s or shareholder’s share of an entity’s reported items | A list of pass-through items and ownership facts to review |
| Brokerage statement | A report of trades and account activity | Candidate sales, proceeds, and basis fields with source pages |
| Wallet export | A record of crypto addresses and transactions | Transfer matches, unknown cost basis, and unresolved events |
| Entity document | An agreement or registration describing ownership or structure | Facts that may affect which forms need professional review |

The software can organize these records without deciding that a disputed fact is true.
That distinction prevents an unverified fact from entering a calculation or draft form.

## Start with a source index

The first output should be an inventory of what arrived, not a draft form.
For each file, record its name, type, tax year, owner, page count, and whether the file opened successfully.

Then give every extracted fact a source reference.
“Maya owns 20% of the partnership” is not a useful fact unless the workpaper points to the agreement or statement that says so.

Here is a small TypeScript model for that rule.
It is ordinary application code, not a tax calculation and not a private Tangle implementation.

```typescript
type SourceRef = {
  document: string
  page?: number
  excerpt: string
}

type ReviewFact = {
  key: string
  value: string | number
  source: SourceRef
  reviewRequired: boolean
}

function fact(
  key: string,
  value: ReviewFact['value'],
  source: SourceRef,
): ReviewFact {
  return {
    key,
    value,
    source,
    reviewRequired: false,
  }
}

const ownership = fact('partnership-ownership', 0.2, {
  document: 'partnership-agreement.pdf',
  page: 4,
  excerpt: 'Maya Stone: twenty percent interest',
})

console.log(ownership)
```

The model may suggest the excerpt, but the application still stores the document and page.
If a fact has no source reference, the application should keep it in a review queue instead of passing it to a downstream form.

## Extract facts without hiding uncertainty

Document extraction turns pages into structured candidates.
It does not turn every sentence into a verified fact.

For each candidate, keep the original value, a normalized value, the source reference, and a status such as `needs-review` or `accepted-by-reviewer`.
Keep the original because a reviewer needs to see whether “1,000” meant dollars, shares, or units.

The agent should also preserve uncertainty.
If a scan is blurry, two documents disagree, or a wallet transfer cannot be matched, the result should say so in plain language.
An empty field is not the same as a confirmed zero.

## Reconcile before calculating

Reconciliation is the step that compares records and asks what does not agree.
It is often more valuable than generating a polished summary.

Imagine these two facts:

| Source | Extracted fact | What the agent should do |
| --- | --- | --- |
| Partnership agreement | Maya owns 20% | Keep the source and date |
| K-1 statement | Maya owns 15% | Flag a conflict and request review |

The agent must not silently choose 20% because it saw that number first.
It should preserve both values, show the source pages, and ask which document governs the return.

The same rule applies to duplicate brokerage transactions, a crypto transfer that appears in two wallets, or a foreign account whose currency conversion date is unclear.
The system’s job is to surface the disagreement while the facts are still visible.

One simple conflict record can make that decision explicit.

```typescript
const ownershipConflict = {
  field: 'partnership-ownership',
  values: [
    { value: 0.2, document: 'partnership-agreement.pdf', page: 4 },
    { value: 0.15, document: 'k1-statement.pdf', page: 2 },
  ],
  status: 'needs-review',
}

console.log(JSON.stringify(ownershipConflict, null, 2))
```

The review queue can show both excerpts beside this record without selecting a winner.

## Calculate from structured inputs

After review facts are structured, deterministic code can calculate totals.
The calculator should receive fields such as wages, interest, proceeds, basis, and ownership rather than a paragraph written by the model.

```typescript
type CalculationInput = {
  wages: number
  interest: number
  reportedProceeds: number
  reportedBasis: number | null
}

function summarize(input: CalculationInput) {
  const gainCandidate = input.reportedBasis === null
    ? null
    : input.reportedProceeds - input.reportedBasis

  return {
    ordinaryIncomeCandidates: input.wages + input.interest,
    gainCandidate,
    needsBasisReview: input.reportedBasis === null,
  }
}

console.log(summarize({
  wages: 180_000,
  interest: 2_400,
  reportedProceeds: 25_000,
  reportedBasis: null,
}))

const example = summarize({
  wages: 180_000,
  interest: 2_400,
  reportedProceeds: 25_000,
  reportedBasis: null,
})
console.assert(example.gainCandidate === null)
console.assert(example.needsBasisReview)
```

This example deliberately stops short of a tax liability.
A missing basis value is a review question, not permission to invent a number.
Production software must pin a named rule set and tax year, such as the 2025 IRS instructions for Form 8949 plus an internal rule ID, record which rule produced each value, and run regression tests against reviewed fixtures.

## Build a review packet, not a final answer

The useful deliverable is a packet with enough context for another person to work through the decisions.
For Maya, that packet could contain:

- **Source index:** file status, tax year, owner, and page count.
- **Fact model:** a source reference for every important field.
- **Calculations:** inputs, units, assumptions, and the rule version used.
- **Reconciliation report:** duplicate transactions and conflicting ownership percentages.
- **Missing-document list:** what each missing document would resolve.
- **Issue list:** high-impact questions such as missing cost basis or undefined ownership.
- **Draft schedules:** marked `unapproved` until a reviewer accepts them.
- **Correction log:** each change and the reviewer who made it.

The packet should make the human decision visible.
An item can be `needs-review`, `accepted`, `rejected`, or `superseded` without erasing the earlier value.

## Keep filing behind explicit approval

Preparation and submission are different actions.
The preparation workflow can create a draft package, but submitting it should require an explicit approval event tied to a person, timestamp, version, and list of reviewed artifacts.

That boundary matters when the return includes questions about foreign companies or passive foreign investment companies.
The IRS pages for [Form 5471](https://www.irs.gov/forms-pubs/about-form-5471), [Form 8621](https://www.irs.gov/forms-pubs/about-form-8621), and [Form 8949](https://www.irs.gov/forms-pubs/about-form-8949) describe the forms themselves.
The [foreign tax credit guidance](https://www.irs.gov/individuals/international-taxpayers/foreign-tax-credit) explains why source facts and professional review matter.

The software can identify that a document mentions a foreign corporation or a potential investment fund.
It should not turn that signal into a filing decision without the facts and approval required for the taxpayer’s situation.

## What an AI accountant does not prove

An AI accountant can reduce document handling and make review questions easier to find.
It cannot prove that a tax position is correct, that a source document is authentic, or that an untested edge case is safe.

The system should be judged by the quality of its workpapers and the clarity of its unresolved questions.
Confidence in the final prose is not a substitute for a source reference.

## The decision rule

Use an AI accountant for complex tax returns only when it can show the source, assumption, calculation input, and review state for each important output.
If it cannot produce those artifacts, treat it as a chatbot that may be useful for explanations but is not ready to prepare a complex return.

## Questions readers usually ask

### What is an AI accountant?

It is software that organizes financial records, extracts facts, performs controlled calculations, drafts preparation artifacts, and surfaces questions for a human reviewer.

### Can an AI accountant replace a CPA?

No.
It can reduce preparation work and create review materials, but complex tax decisions still belong with the taxpayer and qualified professionals.

### What is the difference between an AI accountant and a chatbot?

An AI accountant keeps source-linked workpapers, structured calculations, missing-fact lists, and review states.
A chatbot can explain a concept but may not preserve the evidence behind an answer.

### How should I review AI accountant output?

Open the source document for every high-impact fact, check the assumptions and units, inspect unresolved conflicts, and review the correction log before relying on the draft.
