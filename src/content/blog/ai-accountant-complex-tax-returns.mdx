OpenAI and Thrive say the real challenge in their self-improving tax agent was making production failures visible.
The Codex loop gets the attention, but what we'd build first sits underneath it: a record, for every extracted field, of its source, what the agent proposed and what the practitioner filed.
That record turns corrections into evals.
It lets you report whole returns, and those are what clients see.
On the public benchmark's TY24 set, the best models scored about 90% of lines but got only 63% of returns right.
It is also how a firm documents AI use and review, which the IRS's new AI alert asks for.
If you are building an agent for K-1s, Schedule E and trusts, build the record before you compare models.

We don't sell tax software.
We build the sandboxes, router and eval tooling agents like this run on, and we ran the public tax benchmark on five setups.

## Record every field so a practitioner can approve it

OpenAI and Thrive describe one path for each value.
Documents are classified and split, fields are extracted with citations back to the source, values are mapped into the tax engine, and a practitioner may correct them before filing.
Their rule is that the system must keep enough evidence for a practitioner to approve or correct the result.

We'd write each stage's output onto the field and never overwrite it.
Here is the shape we'd start from (a sketch; we have not run it):

```ts
// One row per extracted field. Each stage writes its own column; nothing is overwritten.
type FieldRecord = {
  returnId: string;
  field: string;                // tax-engine field, e.g. Schedule E rents received, property 2
  source: { file: string; page: number; quote: string }; // the citation a practitioner checks
  classifiedAs: string;         // what the splitter decided this document was
  extracted: string | null;     // what the extractor read
  mapped: string | null;        // what the mapper sent to the tax engine: the draft value
  filed: string | null;         // what went into the filed return
  verdict: "approved" | "corrected" | "unreviewed";
  reviewer: string;             // who approved or changed it
  tool: { name: string; model: string; version: string }; // what produced it
};
```

The per-stage columns are what let you place a failure.
When a filed value differs, Codex in their loop decides whether it was an unsupported field, a missed extraction pattern, a source-selection problem, a mapper gap or a grader issue.
That diagnosis is only possible if each stage left its output behind.
A record that holds only the final value tells you the return was wrong and nothing about where.

The reviewer and tool columns look like bookkeeping.
They are what the compliance section below needs, so record them from day one.

## A correction becomes an eval only after it repeats

A practitioner's edit is not proof the agent erred.
OpenAI and Thrive list the other causes: a practitioner preference, a value carried forward from last year's return in the tax engine, or a change made elsewhere in the filing workflow.
Count every diff as a failure and your eval set fills with noise.

We'd copy their process.
Capture review rows with the expected value, the predicted value and whether the difference looks actionable.
Group related rows so recurring failures separate from workflow noise.
Their groups were concrete: missed fair-rental-days fields, mishandled "other expenses", and rental properties confused within one package.
Only a reviewed, repeated group becomes a bounded task with a success condition.

That last rule is what keeps the loop honest.
One odd diff routes to a person; a reviewed group of the same diff becomes an eval.

## Report whole returns, because line accuracy flatters

Line accuracy counts the share of lines that match.
A client cares whether the return is right.
The two numbers sit far apart, because one wrong early line flows into every line computed from it.

<Figure n={1} figure={strictVsLine} kicker="TaxCalcBench · TY24 leaderboard · GPT-5.4" headline="The same runs score 89.8% by line and 62.8% by whole return" />

Column Tax's TaxCalcBench is the only public benchmark for this, and it reports both.
Its paper adds that in its original runs a ±$5 tolerance lifted scores 15 to 20 points, and real tax calculation allows no such tolerance.
Report the strict whole-return number; line accuracy runs higher because one wrong early line flows into every line computed from it.

OpenAI and Thrive report something close: the share of returns at 75%, 90% and 100% correct field completion.
We like that framing, because it maps to how much follow-up a reviewer faces.
Their headline "up to 97% accuracy" is a field-level ceiling, so read it next to those return thresholds.

Consistency is the number most teams skip.
The same return can pass on one run and fail on the next, and TaxCalcBench measures this with pass^k across repeated runs.
Per model, we'd report strict whole-return accuracy, pass^k and cost per return.
Keep line accuracy as a diagnostic.

The harder TY25 edition adds PDF inputs, state returns and more complex cases.
Its best strict scores ran 76% to 86% with web search, at up to $2.70 a return, when we read it.[^ty25]
Check [the live leaderboard](https://taxcalcbench.ai) before you quote it.

Where models fail is consistent enough to design the review gate around.
The benchmark paper finds models use the wrong tax tables, make calculation errors and misjudge eligibility for credits and deductions.
OpenAI and Thrive found production failures piling up in K-1s, rental real estate schedules and values reconciled across several source files.
Point your deterministic checks there: table lookups, arithmetic, eligibility, and cross-document totals.
Failures also vary between runs, so the same return can pass once and fail the next time; gate on repeated runs, not one.

## The fixer may edit code and evals, never the evidence

OpenAI and Thrive's split of what Codex may touch is the part we'd copy exactly.
It can change the scoped product code, the targeted and regression evals, and reusable skills and docs.
It reads the production trace, source documents, the prediction, the filed return and the tax-engine field docs without changing them.
Its output is a candidate pull request, and engineers still own architecture, product decisions and shipping.
Evidence that is ambiguous goes back to the product team instead of through the loop.

Expect it to take weeks.
They started with W-2s and 1099s, then moved to K-1s and schedules.
After those simple forms, rental properties took about six weeks of substantial engineering oversight to reach 90% precision and recall, and the abstractions and eval conventions from that work made Schedule C and Schedule A easier to add.
After launch, the share of returns at 75% field completion went from a quarter to 86% in six weeks.
Those are their figures, from their own pilot of about 7,000 returns, not an independent measurement.[^ot]

## No change ships below the baseline it replaces

Their loop reruns the targeted eval and the broader regression suite before a pull request surfaces.
Make that a build step that fails.
This example scores the shipped prompt and a candidate on the same scenarios with the same judge, and exits non-zero when the candidate scores lower.

The recorded run used code tests from a demo repository, not tax returns.
Both prompts passed both tests, so the gate let the candidate through.
The recorded gate runs each scenario once; a tax gate should score each return over several runs before comparing the two prompts.
For a tax agent, the scenarios are your promoted eval targets: returns with known filed values.
The judge is whole-return match, and each scenario gets a fresh sandbox that is deleted afterwards.

## The IRS now expects firms to document AI use and review

What the system needs, from the alert and de la Fe's checklist: written 7216 consent with a no-AI path, enterprise-approved tools with no-training terms in writing, no reuse of one client's data for another, and a record of which tools touched each return and who reviewed it before filing.

The IRS Office of Professional Responsibility issued Alert 2026-19 in June.
It says practitioners "must strictly handle all client data using only secure, enterprise-approved AI".
They must review every AI-created document before it reaches a client or the IRS.
Firm leaders need compliance procedures with every step documented.
It also warns against cross-client leakage: data generated for one client being repurposed for another, which is why each client gets its own sandbox below.
The alert applies existing Circular 230 duties rather than adding new ones, and it points to the civil and criminal penalties for unauthorized disclosure.

Section 7216 is the open question.
It requires a client's written consent before return information is used or disclosed outside its exceptions.
The IRS hasn't said whether sending return information to an AI tool is such a disclosure.
Steven de la Fe, writing in CPA Practice Advisor, recommends the cautious path: a standalone signed AI consent, worded with counsel.
Consent must be knowing and voluntary, so he says firms need a no-AI way to prepare a return for clients who decline.
This is not legal advice; settle the consent wording with your counsel.

In the pipeline, check a per-client consent flag before any model call, and route declined clients to the manual path.
Use the field record to answer de la Fe's test for any return: "which tools processed this client's information, and who reviewed the output before it went out?"
And get each vendor's retention and training terms in writing.
His rule: "If a vendor won't say in writing that your data isn't used for training, treat that as the answer."

Hold us to the same standard.
Our router offers zero-data-retention routing for enrolled requests, and each model provider's retention follows its own terms.
Not every route is zero-retention.[^retention]

## Give each client their own sandbox, and know what outlives delete

Agents in one sandbox share a broad trust boundary, so separate tenants need separate sandboxes.
We key one sandbox per customer.
The platform keeps it, resumes it and replaces it.

<Example path="products/legal-agent" />

That recorded run reviewed a contract, not a tax return.
The isolation pattern carries over unchanged: swap the profile and the files.

Deleting the sandbox is not the end of the data.
For one-shot runs, delete in a `finally` block, as the regression gate above does, so a failed run still removes its box.
`delete()` answers once the sandbox is dead and billed, then reclaims its container, volume and network.
Pass `until: "removed"` if your retention policy needs to wait for that reclaim.
Snapshots are the part a tax firm must plan for.
Snapshot repositories, including the final snapshot, stay until their owner deletes them.
A stopped sandbox is also kept parked for at least 30 days unless you set `deleteAfterStoppedSeconds`.
For client data, set it, and delete the snapshot repository as part of closing an engagement.

## A return costs cents in model spend; price machine time from the rate card

On our run, model spend ran from under 3 cents to 21 cents per TY24 return.
The harder TY25 cases cost more, up to a few dollars on the leaderboard's top rows.
Machine time is priced per CPU-core-hour, memory and disk on [the sandbox rate card](https://sandbox.tangle.tools/v1/pricing/sandboxes), with a minimum hourly charge.
When we compared them on 17 November 2026, a short sandbox at that minimum cost less than a frontier harness's tokens for one return.
Redo that arithmetic with today's rates and your own return length before you budget.

In our judgment, the bigger cost is the practitioner's review time: OpenAI and Thrive saved about a third of preparation time, so most of it remains. That is why the record matters more than the model.
Before you compare models, make sure you can say, for any return, which fields are wrong and who signed off on them.
If you can't, build the record first; the evals, the gate and the compliance file all read from it.
