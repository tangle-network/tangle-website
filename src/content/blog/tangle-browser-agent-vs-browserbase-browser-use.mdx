Browser Use, Browserbase and agent-browser are three different kinds of tool.
agent-browser, from Vercel Labs, is a browser CLI that your coding agent drives one command at a time. It has no model of its own.
Browser Use is an agent: you give it a task, and its model picks every step.
Browserbase runs the browser in the cloud, as do Steel and Anchor. Any of these tools can run on them.
Stagehand, from Browserbase, adds AI steps to your own script.
So the choice for a QA lead is which one to trial for E2E tests, and what a green run must prove before CI trusts it.

We ran agent-browser, Browser Use, Stagehand and our own Tangle Browser Agent on the same login, checkout and to-do tests, five times each, on one model.
Code outside the agent checked each end state.
agent-browser and Stagehand passed 15 of 15. Browser Use 0.13 passed 14. Browser Use 1.0, on a model it does not default to, passed 2.
Our own agent passed 8, and on 6 of its 7 failures it reported success.
A green run must prove the end state, checked outside the agent. An agent saying "done" is not a test result.

We build Tangle Browser Agent. The runs are from 2026-11-16. The check, the loop we wrote around agent-browser, and each tool's call are printed below.

## Pick by the job

| You want | Start with | What we measured |
|---|---|---|
| Your coding agent (Claude Code, Codex, Cursor) to drive a browser while it builds and debugs | agent-browser | 15 of 15, the fastest runs, the most tokens on the long flow |
| An agent inside a TypeScript test that takes a task in plain English | Stagehand 3.x `agent()` | 15 of 15 |
| The same in Python | Browser Use | 0.13: 14 of 15, the slowest on checkout. 1.0 on our model: 2 of 15. Run 1.0 on its own model, or test yours first. |
| Steps written in code, with a model only where the page needs judgment | Stagehand 4 | Not measured. Version 4 removed `agent()`. |
| Cloud browsers: stealth, proxies, CAPTCHA solving, saved logins, session replay | Browserbase, Steel or Anchor | Not measured. Their documented features are below. |
| A hosted run per pull request with a recording, a trace, a verdict and cheap reruns | Tangle Browser Agent | 8 of 15, the fewest tokens, six false passes. Do not trust its verdict yet. |

## What each one is

| Tool | Layer | Model loop of its own | Open source | Runs on your machine | Browser by default |
|---|---|---|---|---|---|
| [agent-browser](https://github.com/vercel-labs/agent-browser) (Vercel Labs) | Browser CLI your agent drives | No. The calling agent decides. | Yes, Apache-2.0 | Yes | Chrome for Testing, local |
| [Browser Use](https://github.com/browser-use/browser-use) | Agent library, CLI and cloud API | Yes | Yes, MIT | Yes | 1.0: a Browser Use Cloud browser unless you pass a local one |
| [Stagehand](https://docs.stagehand.dev) (Browserbase) | AI steps for your script | 3.x: `agent()`. 4.x: none. | Yes, MIT | Yes | Local Chrome or a Browserbase session |
| [Tangle Browser Agent](https://browser.tangle.tools) (`bad`) | Agent and test runner, plus a hosted CI API | Yes | Yes, MIT or Apache-2.0 | Yes | Local Chromium |
| [Browserbase](https://www.browserbase.com) | Cloud browsers | No | No | No | Hosted |
| [Steel](https://steel.dev) | Cloud browsers | No | The browser API is ([steel-browser](https://github.com/steel-dev/steel-browser)) | Yes, self-hosted | Hosted or self-hosted |
| [Anchor](https://anchorbrowser.io) | Cloud browsers, plus natural-language tasks | Tasks only | No | No | Hosted |

The layers mix.
agent-browser attaches to any Chrome over CDP and has providers for Browserbase, Browser Use, Kernel, Browserless and AgentCore (`agent-browser -p browserbase`).
Browser Use and Stagehand take a CDP URL, so they also run on Steel or Anchor sessions.
Tangle Browser Agent takes a CDP URL too, and its `SteelDriver` runs it on a Steel session with Steel's proxies and CAPTCHA solving.

## The test

Three public demo apps, each with an end state that code can check without a model:

| Flow | Site | Pass when |
|---|---|---|
| Login | [the-internet.herokuapp.com/login](https://the-internet.herokuapp.com/login) | The page is `/secure` and shows "You logged into a secure area!" |
| Checkout | [saucedemo.com](https://www.saucedemo.com/) | The page is `/checkout-complete.html` with "Thank you for your order!", and the cart held exactly the Backpack and the Bike Light |
| To-do list | [demo.playwright.dev/todomvc](https://demo.playwright.dev/todomvc/) | Three todos stored, only "write report" done, the Active view showing the other two |

Every tool got the same instruction. The to-do one:

```text
Add three todos, in this order: 'buy milk', 'write report', 'call Ana'. Mark 'write report'
as completed. Then switch the view so it shows only the Active todos, and stop there.
```

The checkout instruction also asks for the item total on the overview page. For the right two items it is $39.98.

The check runs outside the agent.
A watcher attaches to the same Chrome over CDP, follows every tab the tool opens, and evaluates the end state every 500 ms and once more after the tool exits.
That final state is the result. The to-do check as it ran:

```js
const shown = [...document.querySelectorAll('.todo-list li')].map(li => li.innerText.trim());
const stored = JSON.parse(localStorage.getItem('react-todos') || '[]');
const done = stored.filter(t => t.completed).map(t => t.title);
const ok = location.hash === '#/active' && shown.length === 2
  && shown.includes('buy milk') && shown.includes('call Ana')
  && stored.length === 3 && done.length === 1 && done[0] === 'write report';
```

Before trusting it, we ran scripted controls through the same runner, two runs each: a correct Playwright script per flow, and scripts that make one plausible mistake (a wrong password, stopping on the checkout overview without pressing Finish, completing the wrong todo).
Every correct script passed and every mistaken one failed.

The checkout page check cannot see which items were bought, and three of our own tool's runs reached the order page with the wrong item.
So the items count too. Our tool's report records the cart page of every run. The other tools reported the total from the overview page, and on that site $39.98 is the total of the two requested items and of no other cart.

Conditions:

- **Model:** `gemini-2.5-flash` for every tool, through one OpenAI-compatible endpoint. Every other setting at its default.
- **Browser:** a fresh headless Chromium 156 with an empty profile for each run. Every tool attached to it over CDP, so none used its own browser, stealth or cloud.
- **Versions:** agent-browser 0.43.0, Browser Use 1.0.6 and 0.13.14, Stagehand 3.7.3, `bad` 0.37.0.
- **Limits:** 30 steps and 300 s per run.
- **Machines:** Linux sandboxes with 4 vCPUs, one run at a time per machine.
- **n:** 5 runs per tool per flow, after one uncounted warm-up run each.
- **Time:** from process start to exit, as a CI job sees it, including the tool's start-up.
- **Tokens:** input plus output, as each tool reports them.
- **No caching:** each run's instruction ended with a random tag, because our model gateway caches repeated requests sent at temperature 0. Our first batch got cache hits that made our own tool look three to ten times faster. We threw that batch away.

What went wrong, run by run:

- **Tangle Browser Agent, checkout, 5 of 5 runs:** it put the Bolt T-Shirt in the cart instead of the Bike Light. It planned both clicks from one page snapshot, and its references to identical "Add to cart" buttons are positional: once the first button turned into "Remove", the second click landed on the next product. It then reported the wrong cart's total, $45.98. Two runs placed that order and reported success. Two stopped on the overview page and reported the order placed. One placed it and reported failure, because it had not read the total first.
- **Tangle Browser Agent, to-do, 2 of 5:** it marked "call Ana" done as well, once after adding duplicate todos, and described the result as correct.
- **Browser Use 1.0, 13 of 15:** `gemini-2.5-flash` mostly could not write working Python against the 1.0 browser API. In 11 failures the agent said it could not drive the browser. In 2 to-do runs it reported the task done without changing the page, and its judge agreed both times.
- **Browser Use 0.13, checkout, 1 of 5:** it placed the order without reading the total first, then ran out of its 30 steps trying to recover. It reported the failure.
- **agent-browser and Stagehand:** no failures. Both reported the right total, $39.98, in all five checkouts.

## How each one ran

### agent-browser

agent-browser is a CLI, so something has to drive it.
In practice that is Claude Code or Codex calling it through a shell tool.
To hold the model constant, we wrote the smallest loop that does the same: the model reads agent-browser's own guide (`agent-browser skills get core`), then calls one tool that runs an agent-browser command, until it calls `done`.

```js
const ab = (args) => execFileSync('agent-browser', ['--cdp', port, ...args], { encoding: 'utf8' });
const tools = [
  { type: 'function', function: { name: 'agent_browser', description: 'Run one agent-browser command',
    parameters: { type: 'object', properties: { args: { type: 'array', items: { type: 'string' } } } } } },
  { type: 'function', function: { name: 'done', description: 'Finish the task.',
    parameters: { type: 'object', properties: { success: { type: 'boolean' }, summary: { type: 'string' } } } } },
];
while (steps < 30 && !done) {
  const r = await client.chat.completions.create({ model, messages, tools });
  // run each agent_browser call with ab(args) and append its output; stop on done
}
```

A typical login: `snapshot -i`, `fill @e2 "tomsmith"`, `fill @e3 "SuperSecretPassword!"`, `click @e4`, `get url`.
It was the fastest tool on every flow, because the model makes one short call per command and agent-browser's snapshots are compact.
It used the most tokens on checkout: the loop resends the whole conversation, snapshots included, on every call. A coding agent that compacts its context pays less.

### Browser Use

```python
from browser_use import Agent, Browser, ChatOpenAI

llm = ChatOpenAI(model='google/gemini-2.5-flash', base_url=BASE_URL, api_key=KEY)
agent = Agent(task=goal, llm=llm, browser=Browser(cdp_url='http://127.0.0.1:9222', keep_alive=True))
result = await agent.run(max_steps=30)
```

Browser Use 1.0 replaced its engine.
The agent now writes Python in a persistent session against the browser's DevTools Protocol, and by default it runs on a Browser Use Cloud browser with Browser Use's own model ([migration guide](https://github.com/browser-use/browser-use/blob/main/MIGRATING.md)).
Most comparison pages describe the 0.x engine, which picks one action per step from the page, so we ran both: 1.0.6, and 0.13.14 (`pip install 'browser-use<1'`).
Browser Use 0.13 was the slowest on checkout and the most token-hungry, and it reported its one failure honestly.
Browser Use 1.0 is built for its own model; our results say nothing about that pairing, only that a general model may not drive its Python API well.

### Stagehand

Stagehand 4 has no `agent()`. Its [migration guide](https://docs.stagehand.dev/v4/migrations/v3.md) says to write the steps in code, or run your own tool-calling loop.
To compare like with like, we ran 3.7.3, the last version with the autonomous agent:

```js
const stagehand = new Stagehand({ env: 'LOCAL', localBrowserLaunchOptions: { cdpUrl }, model });
await stagehand.init();
const result = await stagehand.agent({ model }).execute({ instruction: goal, maxSteps: 30 });
```

Stagehand matched agent-browser on reliability with a little over half its tokens on checkout, and took about 50% longer per run.

### Tangle Browser Agent

```bash
bad run --goal "$GOAL" --url https://www.saucedemo.com/ --cdp-url "$CDP_URL" \
  --provider openai --model google/gemini-2.5-flash --base-url "$BASE_URL" --sink ./out
```

`bad` plans steps with one model call, runs them, and falls back to one decision per step when the page surprises it.
It then checks the goal against the page and writes `report.json` with the verdict, the turns, the tokens and the screenshots.
It used the fewest tokens on every flow, because it plans several steps per model call.
That same batching caused its checkout failures, and its verifier, running on the same model, accepted every wrong result.

## What a run leaves for CI

What each tool wrote or returned after a checkout run, at default settings:

| Tool | Verdict | Record of the steps | Screenshots | Video or trace |
|---|---|---|---|---|
| agent-browser | The calling agent's own word | The calling agent's transcript | When the agent runs `screenshot` | When the agent runs `record start` or `trace start` |
| Browser Use 1.0 | `result.success`, plus an LLM judge's verdict in `result.judgement` | Each Python cell's output in the workspace folder; full messages in memory | Sent to the model, none saved | No |
| Browser Use 0.13 | `history.is_successful()` | The history object; `save_to_file` wrote 168 KB for one checkout | With `generate_gif=True` | No |
| Stagehand 3.7.3 | `result.success` and a message | `result.actions` | No | No locally; Browserbase sessions are recorded |
| Tangle Browser Agent | `report.json`: the agent's claim, the verifier's result, the verdict | `events.jsonl`: page state, action and reasoning for every turn | JPEGs at key turns | `bad view` replays the run; hosted runs add a recording |
| Browserbase, Steel, Anchor | None. They run the browser, not the test. | Session logs | Session replay | Session recording |

A cloud browser's replay shows what the browser did. It does not say whether the test passed.

Two of these verdicts were wrong in our runs.
Tangle Browser Agent's verifier accepted six wrong end states, and Browser Use 1.0's judge accepted two.
A recording or a trace tells a person why after the fact. Only a check you wrote stops a wrong pass in CI.

## What reruns cost

A live agent run pays for model calls every time.
On a suite that runs on every pull request, that is the cost to plan for.

Tangle Browser Agent can replay a passing run, which is the cheap rerun a CI suite needs.
A replay makes no decide calls, costs about 10 to 20% of a live run's model cost by `bad`'s docs, and falls back to the live agent on any mismatch ([replay recipe](https://github.com/tangle-network/browser-agent-driver/blob/main/examples/replay-cache-ci.md)).
It repeats the recorded steps, then makes one model call to check the goal.
Turn it on with `--replay`, which is off by default, and keep the memory folder (`BAD_MEMORY_DIR`) between CI runs.

We ran each flow once live to record it, then five more times with replay on:

| Flow | Recording run | Replayed runs |
|---|---|---|
| Login | 3 model calls, 10k tokens, 11 s of agent time | 5 of 5 replayed both steps with one model call, the goal check, in 9 s, and passed |
| Checkout | 17 model calls, 98k tokens. It bought the wrong items and reported success. | 3 of 3 stopped replaying after 4 of 15 steps and handed back to the live agent: 57k to 87k tokens, wrong items again |
| To-do | 8 model calls, 34k tokens. It reported success and failed our check. | 5 of 5 stopped replaying after 3 of 6 steps and handed back to the live agent |

Our model budget ran out after three checkout replays, so that row has three runs.
Where the recorded run was right, replay cut the model calls from three to one.
Where it was wrong, replay saved nothing, because it had only a wrong run to repeat.
Record only from runs your own check passed.

Stagehand can cache `act()`, `observe()` and `extract()` results, but only on Browserbase's servers, only after Browserbase turns it on for your project, and only for pages that show every run the same content with no personal data ([caching docs](https://docs.stagehand.dev/v4/best-practices/caching.md)).
Browser Use Cloud can save a working script and run it again on later tasks ([docs](https://docs.browser-use.com/cloud/agent/scripts)).
agent-browser has no cache; the calling agent decides what to repeat.

## What it costs

The open-source tools are free: agent-browser, the Browser Use library, Stagehand and the `bad` CLI.
You pay for model tokens, measured per run above, and for cloud browsers if you use them.

On every vendor's price page, browser time is the small line: [Browserbase](https://www.browserbase.com/pricing), [Browser Use](https://browser-use.com/pricing), [Steel](https://docs.steel.dev/overview/pricinglimits), [Anchor](https://docs.anchorbrowser.io/pricing).
Proxy traffic is billed per GB, and CAPTCHA solving is plan-gated.
Browserbase's free plan has no CAPTCHA solving. Steel's entry plan turns on CAPTCHA solving and its proxies only after a paid deposit. Anchor's free plan has no CAPTCHA solving or saved logins.
For a test suite against your own staging app, you need neither, and tokens are the bill.

Hosted runs on [browser.tangle.tools](https://browser.tangle.tools/llms.txt) are billed to prepaid credit. The `bad` CLI on your own machine costs only the tokens of the model you point it at.

## Bot detection, CAPTCHAs and logins

None of our demo sites block bots, so this test says nothing about stealth.
From the vendors' own documentation, not measured here. None of these documents promises to solve every CAPTCHA.

- **Anchor** is built around logins that survive across runs: applications and identities with MFA, profiles, and Cloudflare Web Bot Auth ([managed authentication](https://docs.anchorbrowser.io/essentials/managed-authentication.md)). CAPTCHA solving and authenticated browsers start on its first paid plan; full stealth and Cloudflare-verified agents on the plan above it ([pricing](https://docs.anchorbrowser.io/pricing)).
- **Browserbase** has saved contexts for logins, basic stealth on paid plans, advanced stealth on its top plan, and CAPTCHA solving above the free plan ([pricing](https://www.browserbase.com/pricing)).
- **Steel** has residential proxies, CAPTCHA solving and persistent profiles. Its stealth browser is an Enterprise feature ([pricing and limits](https://docs.steel.dev/overview/pricinglimits)).
- **Browser Use Cloud** browsers include stealth and CAPTCHA solving, and Browser Use says no setup solves every CAPTCHA.
- **Tangle Browser Agent** runs system Chrome with a hardened fingerprint and solves reCAPTCHA v2 and Cloudflare Turnstile by default. `BAD_PROXY_URL` sets a proxy, and `SteelDriver` gives it Steel's proxies.
- **agent-browser** drives the browser you give it. Its `-p` providers bring the provider's stealth.

No vendor guarantees a CAPTCHA. For your own app, allowlisting the test runner beats any bypass.

## Open source, local, and hosted

- **Open source, runs on your machine or CI runner:** agent-browser, the Browser Use library, Stagehand, the `bad` CLI, and Steel's browser API.
- **Watch the default:** Browser Use 1.0's `Browser()` is a Browser Use Cloud browser unless you pass a local one or a CDP URL, as we did.
- **Hosted only:** Browserbase, Anchor, Browser Use Cloud, and hosted runs on browser.tangle.tools.

## Models and keys

- **agent-browser:** no model. The coding agent that calls it brings its own, so the model cost is whatever that agent already costs you.
- **Browser Use 1.0:** its own models on the Browser Use gateway by default, where one key pays for model and browser. It also takes `ChatOpenAI`, `ChatAnthropic`, `ChatGoogle`, any Pydantic AI model, or a local model, with your own key.
- **Stagehand:** a provider and model name, such as `openai/...` or `google/...`, with your own key.
- **Tangle Browser Agent:** your own key, and a different model per role if you want: the planner, executor and verifier route separately. Its published bench uses `gemini-2.5-flash`, the model we used here. It reads `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` or `GOOGLE_GENERATIVE_AI_API_KEY`; with no provider set it uses OpenAI when that key is present, and otherwise the `claude-code` provider, which runs on a Claude Code login with no API key.

## Where Tangle Browser Agent fits

Tangle Browser Agent is not agent-browser.
It is the open `bad` CLI and SDK ([browser-agent-driver](https://github.com/tangle-network/browser-agent-driver)): a goal-driven loop that plans, acts, recovers, checks the goal and returns a structured result.
On top of it, [browser.tangle.tools](https://browser.tangle.tools/llms.txt) is a hosted CI API: send a walkthrough or a test suite, get back a recording, a trace, screenshots, logs and a verdict, and wire it into pull requests.
Today the hosted service runs only the `bad` engine. Running Browser Use and other engines there is on the roadmap.

On these three flows, our loop used the fewest tokens and was the least reliable of the TypeScript tools.
Six of its seven failures were false passes: it bought the wrong second item in every checkout, and it completed an extra todo twice.
Its own verifier ran on the same model and accepted each one.
We filed the positional-reference bug as [issue 177](https://github.com/tangle-network/browser-agent-driver/issues/177).
Until it is fixed, do not take its verdict as your test result.

## Wire it into CI

With `bad`, a suite is a JSON file of cases:

```bash
bad run --cases ./e2e-cases.json --concurrency 4 --sink ./bad-results
```

Defaults such as the model, headless mode, the turn limit and the output folder go in `bad.config.ts`.
The GitHub Action in the repo runs design audits on a preview URL and comments on the PR. It does not run E2E cases; run the CLI in your own job for those.
For hosted runs, send the suite to the browser.tangle.tools [API](https://browser.tangle.tools/api/docs) instead: each run comes back with a recording, a trace and a verdict to attach to the pull request.

agent-browser, Browser Use and Stagehand need a runner of your own to act as a test suite: a list of cases, a loop, and a check you trust.
Whatever you pick, keep the deterministic check. The agent gets the browser to the state; your code decides whether it is right.

## Run it yourself

Two pieces decide the numbers on this page: the watcher that checks the end state, and the loop that drives agent-browser. Both are below in full, as they ran. Each run starts a fresh headless Chrome with `--remote-debugging-port`, starts the watcher, runs the tool against the same port, then stops the watcher with SIGTERM and reads its result.

<details>
<summary>The end-state watcher (37 lines)</summary>

```js
// End-state watcher, run by our runner, not the tool. It attaches to every page target in the browser over raw CDP
// (all browser contexts, including ones a tool creates and later closes), evaluates the task's end-state predicate every
// 500 ms, and keeps each page's last observed state. On SIGTERM (sent after the tool exits) it polls once more and
// writes the result. The agent's own success claim plays no part.
import { writeFileSync } from 'node:fs';
const [port, task, outFile] = process.argv.slice(2);
const preds = {
  login: `({ok: location.pathname === '/secure' && document.body.innerText.includes('You logged into a secure area!'), url: location.href})`,
  checkout: `({ok: location.pathname === '/checkout-complete.html' && document.body.innerText.includes('Thank you for your order!'), url: location.href})`,
  todo: `(() => { const shown = [...document.querySelectorAll('.todo-list li')].map(li => li.innerText.trim());
    let stored = []; try { stored = JSON.parse(localStorage.getItem('react-todos') || '[]'); } catch {}
    const done = stored.filter(t => t.completed).map(t => t.title);
    const ok = location.hash === '#/active' && shown.length === 2 && shown.includes('buy milk') && shown.includes('call Ana')
      && stored.length === 3 && done.length === 1 && done[0] === 'write report';
    return { ok, url: location.href, shown, stored: stored.map(t => t.title + (t.completed ? ' [done]' : '')) }; })()`,
};
const expression = preds[task];
const v = await (await fetch(`http://127.0.0.1:${port}/json/version`)).json();
const ws = new WebSocket(v.webSocketDebuggerUrl);
let id = 0; const pending = new Map(); const sessions = new Map(); const attached = new Set(); const last = new Map();
const send = (method, params = {}, sessionId) => new Promise((res, rej) => { const i = ++id; pending.set(i, { res, rej }); ws.send(JSON.stringify({ id: i, method, params, ...(sessionId ? { sessionId } : {}) })); setTimeout(() => { if (pending.has(i)) { pending.delete(i); rej(new Error('timeout')); } }, 3000); });
ws.onmessage = async (ev) => {
  const m = JSON.parse(ev.data);
  if (m.id && pending.has(m.id)) { const p = pending.get(m.id); pending.delete(m.id); m.error ? p.rej(m.error) : p.res(m.result); return; }
  if (m.method === 'Target.targetCreated' || m.method === 'Target.targetInfoChanged') {
    const ti = m.params.targetInfo;
    if (ti.type === 'page' && !attached.has(ti.targetId)) { attached.add(ti.targetId); try { const r = await send('Target.attachToTarget', { targetId: ti.targetId, flatten: true }); sessions.set(r.sessionId, ti.targetId); } catch {} }
  }
  if (m.method === 'Target.detachedFromTarget') sessions.delete(m.params.sessionId);
};
```

## Limits of this test

- Three flows on demo apps with stable markup and no bot protection. Real apps are harder, and flakier.
- Five runs per tool per flow. A difference of one run in five is noise.
- One model, `gemini-2.5-flash`. A stronger model would change every number, and Browser Use 1.0 is built for its own.
- agent-browser ran inside our 33-line loop. Claude Code or Codex drive it with more context and a stronger model.
- Stagehand 3.7.3 is not the current major version.
- No cloud browsers. Browserbase, Steel and Anchor were not run, so nothing here measures stealth, proxies or session start time.
- Checkout items for agent-browser, Stagehand and Browser Use come from the total each reported, not from the cart itself.
- We build one of the tools.

## The decision

- **Your coding agent writes and fixes the tests:** give it agent-browser. It passed every run here, it was the fastest, and the model behind it is the one you already pay for.
- **Plain-English steps inside a TypeScript test:** Stagehand. Its 3.7 agent passed every run here. Version 4 drops that agent: you write the steps and call `act()` where the page needs judgment, which we did not test.
- **Python:** Browser Use. 0.13 was reliable and slow here. On 1.0, use its own model or measure yours first.
- **Stealth, proxies or saved logins at scale:** put Browserbase, Steel or Anchor under whichever tool you picked.
- **Every option:** assert the end state in code. Six of the eight false passes here came from our own tool.
