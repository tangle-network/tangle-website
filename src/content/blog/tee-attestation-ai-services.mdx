At 9:12 on a Monday, a legal team has a contract that needs a quick summary and a reason to keep the document private.
At 9:16, a vendor offers an attractive answer: upload the file, wait a few seconds, and receive a summary from an AI service running in protected hardware.
At 9:20, the lawyer reviewing the vendor asks the question that changes the whole integration: “How do we know which program saw this contract?”
The invoice shows that the request was paid, but a receipt cannot answer that question.

The team still has two unanswered questions.
Which program handled the contract, and what evidence connects the returned summary to that program?

That is the problem behind a protected execution boundary.
A **TEE** is a trusted execution environment that provides such a boundary.
A **TEE attestation report** is a signed statement about the program and hardware that started the workload.
The evidence can identify a program and the protected machine boundary where it started.
It cannot certify that the program understood the contract or that the summary is safe to use.

Those promises are easy to collapse into one reassuring word such as “private” or “verified.”
They are separate engineering decisions.
This article follows one private summarization job from request to result so the difference stays visible.
It is written for the person who has to decide whether a secret can leave an application, not for someone who already knows the vocabulary of confidential computing.

## Separate confidentiality, execution identity, and quality

An AI service can make at least three different promises about a job.

| Promise | The question it answers | Evidence it needs |
| --- | --- | --- |
| Confidentiality | Could the machine owner read the input while the job ran? | A protected execution boundary, a secret-release policy, and provider-specific security controls |
| Execution identity | Did the approved program start in the expected protected environment? | A signed attestation report, an approved code measurement, and a caller-side policy check |
| Output quality | Is the returned answer correct and safe for this application? | Tests, comparisons, validation rules, human review, or another workload-specific check |

Payment is a fourth concern.
A receipt can prove that a request was authorized and paid.
It does not prove any of the three technical promises above.

The rest of this article is about the second row, with enough context to show where the other rows begin.

## The terms in ordinary language

A **trusted execution environment**, or **TEE**, is a protected area provided by a processor and its supporting software.
The goal is to keep a workload's memory and data separated from the ordinary operating system that controls the machine.
The exact protection depends on the hardware, cloud provider, configuration, and code running inside the protected area.

**Attestation** is the signed report produced for that workload.
The report describes claims such as the hardware platform, the program measurement, the report freshness, and whether the environment is running in a debug mode.

A **measurement** is a fingerprint of the code and configuration that the protected environment loaded.
If an approved build has a known measurement, a caller can compare the report with that value before releasing a secret.

An **operator** is the person or service that runs the workload.
On Tangle, a **Blueprint** is a public service definition that describes the jobs an operator can run, their inputs and outputs, and the requirements for running them.

The words sound specialized because the evidence has to be precise.
The useful claim is still simple: a checked report can identify a particular program running inside a particular protected environment at a particular time.

The [Confidential Computing Consortium](https://confidentialcomputing.io/) describes this family of systems as protecting data while it is in use.
Provider details remain important because [AWS Nitro Enclaves](https://docs.aws.amazon.com/enclaves/latest/user/verify-root.html) and [Google Cloud Attestation](https://docs.cloud.google.com/confidential-computing/docs/attestation) expose different report formats, hardware assumptions, and operational controls.

## Follow one private summarization job

Suppose the legal team wants a remote service to summarize a contract.
The team has accepted the service's code measurement in advance.
It has also decided that the result must be checked by a lawyer before anyone relies on it.

The request should move through a sequence like this:

1. The caller records the expected program measurement and the accepted provider families.
2. The operator starts the summarizer inside a TEE and obtains an attestation report.
3. The caller checks the report signature, measurement, debug flag, freshness, and provider policy.
4. The caller releases the contract only after those checks pass.
5. The service computes a hash of the input and records it with the job identifier.
6. The service returns the summary, the input hash, the output hash, and the report reference.
7. The application checks the summary before showing it to the legal team.

The fifth step is an application design choice.
Attestation does not automatically bind arbitrary inputs and outputs to a job.
The service has to include those bindings in its result format or in a signed record that the caller can inspect.

The report is evidence about the execution boundary.
The hashes are evidence about which bytes the service claims to have processed.
The lawyer's review is evidence about whether the summary is usable.

Each piece answers a different question.

## The moment the promise becomes a decision

The useful part of an attestation report is not the word “trusted” printed next to it.
The useful part is the decision it lets a caller make before it releases a secret.

The legal team's client can turn the vendor's broad promise into a small policy:

| Before sending the contract | After receiving the result |
| --- | --- |
| The report is signed by an accepted provider root | The result carries the same job identifier as the request |
| The measurement matches the reviewed summarizer build | The input hash matches the bytes the lawyer selected |
| The report is fresh and not in debug mode | The output is checked for required clauses and routed to review |
| The report's public key is the key approved for release | Payment, execution, and answer quality are shown as separate statuses |

This changes the user interface as well as the server.
Instead of a single green badge that says “verified,” the application can show “execution policy passed,” “payment authorized,” and “human review required.”
That wording tells the lawyer which check passed and which decision still belongs to a person.

The distinction matters during an incident.
If the summary is wrong, the team can ask whether the wrong program ran, the right program received the wrong bytes, or the right program produced a poor answer.
Without separate records for the report, the input hash, and the answer review, those three investigations collapse into an argument about whether the service met its promise, even though no one artifact covers all three claims.

## What a report contains

An attestation report is easier to review when its fields have a job in the decision.

| Field | What it lets the caller check | What it still does not answer |
| --- | --- | --- |
| Signature and certificate chain | Whether the report comes from an accepted hardware and provider root | Whether the provider's broader service is honest |
| Program measurement | Whether the loaded code matches the approved build | Whether the approved build is bug-free |
| Provider and platform | Which hardware and cloud guarantees apply | Whether those guarantees cover every side channel or network log |
| Debug flag | Whether the environment is running in a development mode | Whether the workload's normal code path is correct |
| Timestamp and expiry | Whether the report is recent enough for the request | Whether the workload stayed unchanged after the report |
| Ephemeral public key | Which key a caller can use to encrypt a secret | Whether a key service enforced the report policy |
| Input hash and job identifier | Which request the result claims to represent | Whether the service calculated the hash correctly |
| Output hash | Which returned bytes the service claims to have produced | Whether those bytes are useful or safe |

The caller should know which fields are required before the service is deployed.
If a team decides after a failure that it needed an input hash, the original result may be impossible to investigate.

## A worked artifact for the summarizer

The following object is a small, public data shape for the legal team's job.
It is deliberately boring.
The point is to show the information that travels with the result, rather than to pretend that a made-up object is a provider's wire format.

```json
{
  "jobId": "contract-17",
  "inputHash": "sha256:contract-17",
  "outputHash": "sha256:summary-17",
  "measurement": "sha256:approved-summarizer-v3",
  "provider": "confidential-cloud-a",
  "debugMode": false,
  "reportExpiresAt": "2026-08-03T10:00:00Z",
  "payment": {
    "status": "authorized",
    "receipt": "public-payment-receipt"
  },
  "resultStatus": "needs-human-review"
}
```

The `payment.status` field is intentionally beside the execution fields rather than inside them.
It tells the caller that money moved through the payment path.
It says nothing about the program measurement or the quality of the summary.

The `resultStatus` field is also separate.
The application can accept a protected execution report and still route the summary to a human because the task is high risk.

## The first result is allowed to be a useful failure

The vendor's first test run returns a plausible paragraph, and every execution check passes.
The paragraph still leaves out the contract's termination clause.

That is not a contradiction.
The attestation report answered, “Did the approved program run in the approved boundary for this request?”
The legal review answered, “Can a lawyer rely on the answer?”

The application should preserve both answers instead of overwriting the first with the second:

```text
job: contract-17
execution: accepted
payment: authorized
input-binding: matched
output: returned
quality: needs-human-review
reason: termination clause not found
```

This small record gives the operator a concrete bug to investigate and gives the legal team a safe next step.
It also prevents a common product mistake: treating a technically well-formed response as an answer that is automatically safe to use.

## A small policy check you can run

The following TypeScript is an illustration of the caller's policy.
It is not a Tangle SDK API and it does not replace the provider's certificate and signature library.
It makes the acceptance decision visible without requiring a cloud account or private repository.

Save it as `attestation-policy.ts` and run it with `npx --yes tsx attestation-policy.ts`.

```ts
type AttestationReport = {
  signatureValid: boolean
  measurement: string
  debugMode: boolean
  provider: string
  expiresAt: number
  inputHash: string
  outputHash: string
}

type AcceptancePolicy = {
  expectedMeasurement: string
  acceptedProviders: string[]
  inputHash: string
  now: number
}

function acceptReport(report: AttestationReport, policy: AcceptancePolicy) {
  if (!report.signatureValid) return { accepted: false, reason: 'bad signature' }
  if (report.debugMode) return { accepted: false, reason: 'debug mode' }
  if (!policy.acceptedProviders.includes(report.provider)) {
    return { accepted: false, reason: 'provider is outside policy' }
  }
  if (report.measurement !== policy.expectedMeasurement) {
    return { accepted: false, reason: 'unexpected program measurement' }
  }
  if (report.expiresAt <= policy.now) {
    return { accepted: false, reason: 'report is expired' }
  }
  if (report.inputHash !== policy.inputHash) {
    return { accepted: false, reason: 'report is for a different input' }
  }
  return { accepted: true, reason: 'execution policy passed' }
}

const decision = acceptReport(
  {
    signatureValid: true,
    measurement: 'sha256:approved-summarizer-v3',
    debugMode: false,
    provider: 'confidential-cloud-a',
    expiresAt: 1_800_000_060,
    inputHash: 'sha256:contract-17',
    outputHash: 'sha256:summary-17',
  },
  {
    expectedMeasurement: 'sha256:approved-summarizer-v3',
    acceptedProviders: ['confidential-cloud-a'],
    inputHash: 'sha256:contract-17',
    now: 1_800_000_000,
  },
)

console.log(decision)
```

The example accepts the report because the code, provider, input, freshness, and debug policy all match.
In a real deployment, `signatureValid` comes from a provider-supported certificate chain rather than a Boolean written by the caller.
The expected measurement must come from a reviewed build, not from the report that arrived after the request.

The policy function is intentionally small enough to test with ordinary unit tests.
For example, this table of cases makes the failure behavior explicit:

| Case | Expected decision | Why |
| --- | --- | --- |
| Matching measurement, fresh report, matching input | Release the document | The caller has the evidence it asked for |
| Correct measurement, expired report | Request a fresh report | The caller cannot tell whether the workload restarted |
| Correct report, different input hash | Reject the result | A plausible answer for another file is still the wrong answer |
| Good execution, missing termination clause | Keep the result out of automation | Quality is a separate application decision |

The table is more than documentation.
It can become a test fixture, an operator runbook, and a support response when a customer asks why a request was refused.

## Reject stale or mismatched evidence

Attestation matters at the moment a caller accepts or rejects execution evidence.
The caller needs a response for each failed check.

### An unexpected measurement

The service returns a report for `approved-summarizer-v4`, while the caller approved `v3`.
The caller rejects the request before sending the contract.

The operator may have deployed a legitimate update.
The report may also describe an accidental or hostile replacement.
The caller cannot distinguish those cases from the report alone, so a new measurement requires an explicit approval step.

### A debug-mode report

The service is running inside a protected environment, but the report says the environment is in debug mode.
That mode may expose inspection or development controls that the production policy does not allow.
The caller should refuse to release secrets until a production report arrives.

### An expired report

The report was created yesterday and the policy allows it for one hour.
The caller requests a fresh report or marks the service unavailable.
Reusing an old report can hide a restart or a changed deployment.

### An input mismatch

The output looks plausible, but its input hash does not match the contract the caller sent.
The caller discards the result.
An output that is valid for one input is not evidence about another input.

### A good report and a bad answer

The report passes every execution check, yet the summary omits a termination clause.
The application sends the result to human review and records a quality failure.
The execution checks passed.
The application's quality check still rejected the summary.

### Payment succeeds while execution fails

If the service uses [x402 for paid HTTP requests](/blog/blueprint-sdk-x402-payments-runnable-jobs), the receipt can show that payment authorization succeeded.
The service can still time out, return malformed data, or fail an application check.
The caller needs a separate retry, refund, or dispute policy.
Payment does not choose among those outcomes.

## Debug a dispute with the records in order

Imagine that the lawyer says the returned summary was generated from an older version of the contract.
Do not begin by asking whether the model is trustworthy.
Start with the records that can narrow the dispute:

1. Compare the caller's `jobId` with the service's job record.
2. Recompute the caller's input hash from the exact uploaded bytes.
3. Compare that hash with the input hash in the returned artifact.
4. Check the report's measurement, provider, debug flag, and expiry at the time the secret was released.
5. Compare the output hash with the bytes the application displayed.
6. Only then investigate model behavior, prompt construction, or a missing clause.

If step two fails, the problem is a request-binding bug and the model may be innocent.
If step four fails, the service violated the execution policy before it ever saw the document.
If all six steps pass, the remaining problem is likely answer quality or application handling, which needs a different remedy.

The order saves time because each record rules out a different class of failure.
It also gives a customer a useful explanation instead of a vague promise that the workload “ran securely.”

## What TEE attestation cannot prove

Attestation does not prove that the model's training data is accurate.
It does not prove that the prompt asked for the right task.
It does not prove that the code has no bug.
It does not prove that an operator priced the job fairly.
It does not prove that the returned answer is safe to use.

It also does not describe every system outside the protected workload.
Network logs, request metadata, application logs, billing records, and the service's own output policy may live outside the TEE.
Those surfaces need their own privacy and correctness decisions.

A service can therefore have excellent execution evidence and poor product behavior.
It can also have a useful answer and weak confidentiality.
The two dimensions should be reported separately in the interface that the caller sees.

## Provider differences change the operational story

The TEE label does not describe one universal machine.

AWS Nitro Enclaves run an isolated enclave alongside an EC2 instance and expose an attestation document for the enclave.
Google Confidential Space runs workloads in confidential virtual machines and exposes an attestation token for policy decisions.
Azure Confidential VMs use confidential-computing hardware and Azure's surrounding attestation services.

Those services differ in startup time, supported hardware, report fields, networking, key release, and recovery after a host restart.
The provider documentation is the authority for each boundary.
The [protected execution overview on Tangle](/blog/trusted-execution-on-tangle) explains how the Blueprint-facing choices relate to those provider-specific modes.

Do not write “TEE enabled” as if it were a complete deployment description.
Name the provider family, accepted measurement, report age, secret-release policy, and restart behavior.

## Where Tangle fits

The public [Blueprint SDK](https://github.com/tangle-network/blueprint) gives a service author a place to describe jobs, operators, runtime requirements, and evidence.
The [Tangle documentation](https://docs.tangle.tools/) and the [protected execution explainer](/blog/trusted-execution-on-tangle) describe provider modes and sealed-secret exchange in more detail.

A Tangle service should make the expected measurement, accepted provider family, report age, input binding, output format, and failure behavior visible to callers.
Those details belong beside the service contract because they change the decision a caller can make.

For a caller, that information can be represented as a short acceptance record:

```ts
type JobDecision = {
  jobId: string
  execution: 'accepted' | 'rejected'
  payment: 'authorized' | 'failed'
  inputBinding: 'matched' | 'mismatched'
  output: 'returned' | 'missing'
  quality: 'unchecked' | 'accepted' | 'needs-human-review'
}

const decision: JobDecision = {
  jobId: 'contract-17',
  execution: 'accepted',
  payment: 'authorized',
  inputBinding: 'matched',
  output: 'returned',
  quality: 'needs-human-review',
}

console.log(decision)
```

This is an application-facing shape, not a provider wire format.
Its value is that a dashboard, retry worker, and human reviewer can all see the same boundaries.

The protocol can carry payment and service information.
The application still chooses whether a result is good enough for its users.

## When to pay the complexity cost

TEE attestation is worth the added complexity when all of the following are true:

- the operator should not be able to inspect sensitive data while the job runs;
- the caller can check a report before releasing that data;
- the workload has an approved build whose measurement can be managed; and
- a failure or stale report has a clear recovery path.

For a public, low-risk inference request, ordinary isolation and a result test may be a better fit.
For a high-value contract, private model, or regulated record, the execution boundary may be part of the product promise.

Choose the smallest evidence set that answers the risk in your workload.
Add output checks when correctness matters.
Add payment rules when money moves.
Add attestation when the execution boundary itself is part of the promise.

The design also requires someone to approve new measurements, rotate keys, decide how long a report remains fresh, test a restart, handle a provider outage, and explain a rejected request to a customer.
If the team cannot own those decisions, a simpler service with a narrower promise may be more honest.

## Questions to ask an operator

Before sending a secret to an AI service, ask for direct answers to these questions.

1. Which program measurement does the report cover?
2. Which hardware and provider roots does the caller trust?
3. How does the caller learn that the report is fresh?
4. Is debug mode rejected?
5. How is the input bound to the output?
6. What happens after a host restart or a new deployment?
7. Which logs and metadata remain outside the protected workload?
8. What does the service do when payment succeeds and the result fails review?

If the answer is only “the job runs in a TEE,” the service has named a technology rather than a trust decision.

## FAQ

### What does TEE attestation prove for an AI service?

It can support claims about the approved program, protected hardware boundary, provider policy, debug mode, and report freshness when the caller checks those fields.

### Does TEE attestation prove an AI result is correct?

No.
Correctness needs tests, comparison with an expected answer, an independent execution, human review, or another check matched to the workload.

### Should a caller send secrets before checking the report?

No.
Check the report and its measurement first, then release only the secret that the approved workload needs.

### Does a payment receipt prove that the paid job ran correctly?

No.
Payment records and execution evidence answer different questions.
The application still needs a result policy and a failure path.

### How does a Tangle Blueprint use attestation?

A Blueprint can describe a service that requires or prefers protected execution and can expose the evidence a caller needs.
The current provider and release behavior belongs in the public SDK and provider documentation, so check those sources before relying on a particular mode.
