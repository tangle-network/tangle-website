A loop that turns failed agent runs into shipped changes is only as trustworthy as its checkpoints.
No result we have seen, in our archive or the strict harness paper, shows automated search beating a careful hand edit; to find out for your agent, compare three arms: the unchanged baseline, a direct edit and the optimizer.
We have seen an analyst that a constant guess outscores, and gains that vanish on fresh cases.
So the parts your team will trust are plain ones.
Capture every attempt with its verdict and config.
Have someone other than the analyst decide each finding.
Gate on held-out cases counted as independent incidents.
Put a person between the gate's ship decision and production.
Keep the exact diff so you can undo it.

## Capture what the agent tried, why it was judged wrong, and what ran

A record is ready to replay when it can say what the agent tried, why it was judged wrong and what changed next.
A trace that holds only the final answer cannot do that, so we store every attempt with the fields the agent-eval guide to feedback trajectories lists:[^ft]

- the user's intent and the context the agent had;
- every artifact or action it attempted;
- objective validation results;
- labels from users, reviewers or the environment, each with a reason;
- the measured outcome, when one exists;
- the model, a prompt or config hash, the code commit and the cost.

Then check each record against that test; if it fails, it is not training data yet.
Do not skip the last field: rollback depends on it, because without the config hash you cannot say which version failed.

```text
# one stored trajectory, illustrative
draft 1 -> user rejects, reason: "cites a policy that was retired"
draft 2 -> judge passes
         -> user approves
         -> metric outcome: ticket closed, no reopen
labels:   user, judge, metric
metadata: model, prompt hash, commit, cost
```

Labels can come from a user, a judge, the environment, a metric, a policy or the system.
We prefer trajectories that carry more than one source; the guide calls those the most useful, and a single judge's verdict can be fooled.

## An analyst's finding is a hypothesis until someone else decides it

Can an LLM that reads traces and explains failures feed the optimizer directly? No.
Each finding is a hypothesis that needs an independent decision, the run needs an independent check for missed issues, zero findings does not prove a clean run, and the analyst must be measured on labeled traces before its findings drive changes.

The library enforces the first two.
An archived trajectory cannot become optimizer input until every finding has one independent decision and the run has one independent completeness assessment.
The reviewer must differ from every analyst that produced the run.
Duplicate, unknown, mutated or self-reviewed records make the call throw rather than get filtered out quietly.[^ta]

An empty findings list means no submitted claim passed the evidence rules.
It does not mean the run was correct.

To measure the analyst, run it on traces a person has labeled.
Report issue recall, finding precision, whether the cited evidence is exact, false positives on runs you trust, and agreement between repeat runs.
Report failures, calls, tokens, cost and latency along with them.
On the TRAIL benchmark of human-annotated traces, the best model it tested (Gemini 2.5 Pro) scored 11% at trace debugging.[^trail]

## Put the fix in the cheapest layer that can hold it

Escalate in this order: a memory instruction distilled from the labels, then a replay scenario in your eval set, then prompt or code optimization on separate train, dev and holdout splits.[^ft]
Then decide the layer by what the trace shows:

- the agent had the right tool and misused it: memory or the prompt;
- it lacked a tool, a check or an isolated workspace, which no instruction will supply: the harness, compared with the same model, the same cases and the same judge, so only the harness changes;
- the model itself is the limit: weights, a separate and heavier path that takes this loop's exported trajectories.


The harness is a profile field like any other, next to model, prompt, tools, permissions, hooks and subagents.[^rt]

## Evolving the code around the model sometimes pays, and the papers disagree on how often

Two 2026 papers report large wins from automated harness changes.
In the Agentic Harness Engineering paper, ten iterations lifted Terminal-Bench 2 pass@1 from 69.7% to 77.0%, against 71.9% for Codex-CLI.[^ahe]
In "Evolving Agents in the Dark", one round lifted SWE-Bench Pro from 59% to 78% without external grading.[^rho]
Both are the authors' own results.

A later paper reran the comparison more strictly.
On Terminal-Bench 2.1, automatic harness evolution did not beat simple test-time scaling, with or without test cases, and generalized poorly.[^re]
Its authors also found that earlier work selected candidates on signals drawn from the same benchmark it reported.
It did find real gains on long-horizon games at matched budgets.
We read that as: try harness changes, but judge them against more samples of the current harness, not only against one sample of it.

## Keep the gate's cases where the optimizer cannot see them

Keep train, dev, test and holdout disjoint, keep holdout scores away from the proposer, and keep held-out cases out of prompt text, preference memory, few-shot examples and manual tuning, because a holdout reused inside the search turns its final score into selection-set performance.[^ft][^ms][^au]
If a trajectory becomes a memory entry or a few-shot example, tag it with the split it came from and keep it out of held-out evaluation.

The library enforces part of this:
Training and holdout case IDs must be disjoint.
The component that proposes candidates cannot read holdout scores.
Final-evidence accounting reserves the final cases before search starts and refuses to reuse them across campaigns that share a ledger.[^ms]

Treat any reuse as disqualifying, because we have done it ourselves.
In one archived run, the same holdout set fed both the inner optimizers and the outer comparison.
Its reported final score was really selection-set performance.[^au]
The strict harness paper found the same flaw in earlier harness-evolution work.

## The gate counts incidents, not calls

The gate returns one of five decisions, counts the independent units you declare (otherwise each execution cell counts), which we declare before anyone sees a score, and needs 20 paired observations before it can establish a mean effect on a continuous score; with fewer units, a required dimension is reported as not evaluated, not passed.
The decisions:

```text
ship | hold | need_more_work | model_ceiling | arch_ceiling
```

It also separates missing evidence from a measured failure, which tells you whether to run more cases or rethink the change.[^er]

We count only independent incidents, mapped to units before anyone sees a score.
Repeating one incident a hundred times supplies one incident.
Five paraphrases of the same customer complaint are one unit.
Declaring the grouping first keeps it from drifting toward the answer you want.[^se]

How many is enough? Below 20 paired observations, the gate cannot establish a mean effect on a continuous score, so thin evidence does not pass: a required dimension without enough units is reported as not evaluated, and an observed regression can still hold the gate while that evidence is incomplete.
Twenty is the minimum for the bootstrap on a continuous score, not a sample-size rule.
Size the final set from the variance you saw in development and the smallest effect worth shipping.[^au]

## Test the judge against a dumb baseline before it promotes anything

A judge can be gamed, and so can the metric your optimizer chases.
Before a judge gates promotion, score known-good and known-bad artifacts with it and confirm it separates them.[^er]

Then we try a predictor that does no work.
We learned this after we had already certified a result on it.
On one trace set, an analyst was asked to locate the failing step.
Most cases labeled the final step, so a constant guess of "the last step" beat every prompt we tried, by about three to one.

<Figure n={1} kicker="Trace analyst vs. a constant guess" headline="Always guessing the last step scored 0.568; the LLM analyst scored about 0.180" figure={trivialBaseline} />

We retired that split.
The pooled result it fed can no longer support a claim about analysis quality.

We also watch more than one number.
In one campaign, the metric the optimizer chased rose from 0.163 to 0.187 while recall fell from 0.325 to 0.138.[^au]

## No result we have seen shows an optimizer beating a direct edit from the same evidence

To find out for your agent, run three arms on fresh paired units: the unchanged baseline, a direct edit from the same development evidence, and the optimizer.
Our own archive holds gains, nulls and regressions, and none of it settles the question.[^au]
A GEPA candidate that won its search then lost 0.0561 micro F1 on fresh agent families, and the gate rejected it.
One early win came from an optimizer that was handed requirements the baseline prompt lacked.
No arm tested whether pasting those requirements in by hand did as well.
The strict harness paper points the same way for harness search: compare against the cheap alternative, not only the old version.
Whether an optimizer should rewrite your prompt at all is the subject of [the prompt optimization post](/blog/self-improving-stack-prompt-optimization/).

## Proving a change costs more than finding it

We budget for the comparison, not the search.
In two of our GEPA campaigns, the search was the small line item.

<Figure n={2} kicker="Two GEPA campaigns" headline="Comparing the result cost about 11 times the search in one campaign and 4 times in the other" figure={proofCost} />

The costs we missed were the calls our ledger did not see.
In one archived run, part of the captured worker cost had no phase attached, and the optimizer's own calls had bypassed the ledger entirely.[^au]
Route the optimizer and its reflection calls through the same cost ledger as the worker.
Run a small smoke pass before the full search, and forecast from its observed usage at your current model rates.

## A ship decision is evidence; a person makes it live

No candidate should go live on the gate alone.
With the default gate, a ship decision says the candidate beat the baseline on held-out cases.
Re-measure it on a final-test partition, then have someone approve it; activation is a separate step your application takes.

The runtime keeps candidate promotion separate from live activation.[^rt]
It can re-measure the selected candidate on a final-test partition, and it stops there.
The knowledge library's promotion example says to call it only after your application approves the measured candidate.[^ak]
Agent-eval's own optimization example deploys on ship in caller code, so nothing stops you from skipping approval.
We put an explicit approval in between, and we think your team should too.

```ts
// Illustration: application-provided names, not a library API.
const result = await runCycle(candidateSpec)
if (result.gateResult.decision !== 'ship') return hold(result)

const approval = await requestApproval({
  diff: result.promotedDiff,
  evidence: result.gateResult,
  cost: result.cost,
  previous: currentSurface,
})
if (approval.granted) await activate(result.winnerSurface, approval)
```

The approval carries the diff, the evidence and the surface it replaces.
The reviewer sees what will change and what to restore.

## Roll back from the record; there is no undo button for prompts

The optimizer reports the exact selected change as a diff.[^ms]
Store the surface it replaced yourself, next to the approval and the config hash; rollback needs it.
For prompts and harnesses, we found no documented one-call rollback.
Rolling back means activating the stored previous surface through the same approval path.
Your trace metadata then tells you which runs saw which version.

Knowledge promotions keep more.
Promoting a run's pages into the shared store writes a record with the source run, every page digest, the actor, the reason and the time.
Promoting a candidate checks the original base hash and rejects a stale candidate instead of overwriting newer work.
Knowledge tools keep write history by default, but do not count on it: an application can turn it off, and lower-level writers keep it only when they opt in.
Where it is retained, the before and after snapshots can be inspected or restored.[^ak]

## Block the merge on the score and on the path

The smallest useful CI gate runs the shipped prompt and the candidate on the same scenarios, with the same judge, each in a fresh sandbox.
It exits nonzero when the candidate scores lower.

<Example path="evals/regression-gate" />

In this run both prompts passed both cases, so the build passed.
A score can hold steady while the agent takes a worse route through its tools.
For that, add a trace contract and run it in CI.
It reports pass, fail or error per rule, with the spans that broke it.[^er]

We treat a check this size as a regression catch on known cases.
It is not the held-out gate, and a candidate that passes it still goes through the comparison and the approval above.

If we were starting again, we would build capture and the CI gate first.
Add the analyst only after you have measured it on labeled traces.
Let an optimizer write candidates only once it has beaten a direct-edit arm on fresh incidents, and keep the approval even then.
