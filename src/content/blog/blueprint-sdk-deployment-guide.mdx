Getting a service to run on your laptop is not the same as making it possible for someone else to operate.
That difference becomes important when several independent operators may run the same service for users.

On Tangle, a **Blueprint** is a public service definition that tells operators what jobs exist, what they need to run, and how a consumer can call them.
An **operator** is the person or team that supplies the machine and keeps that service running.
A **service instance** is one deployed copy of the Blueprint that receives real work.

This post explains the path from a local Rust service to an operator-run service.
The answer is not “publish the binary and hope.”
You need a clear definition, a reproducible artifact, a runner that survives real settings, testnet evidence, monitoring, and a way back when a release is wrong.

For payment-specific deployment, read the [payment production checklist](/blog/x402-blueprint-production-deployment-checklist).
For the network choices behind a deployment, read [Remote Providers, Direct Runtimes, and Payment-Native Ingress](/blog/blueprint-deployment-architecture-remote-providers).

## What is being deployed?

A Blueprint has several parts, and each part answers a different operator question.

| Part | Question it answers |
| --- | --- |
| Service definition | What jobs exist, and what metadata describes them? |
| Service code | What does each job do, and how does it reject bad input? |
| Artifact | Which binary, image, or source package should the operator run? |
| Operator settings | Which keys, network endpoints, ports, and environment values are required? |
| Network registration | Where can an operator discover this service? |
| Service instance | Which deployed copy receives a particular job? |

The [Blueprint SDK source](https://github.com/tangle-network/blueprint) contains the public implementation.
The surrounding [Blueprint explanation](/blog/how-blueprints-work) describes how service definitions, operators, and consumers fit together.

The important boundary is that the definition is deployment input, not documentation added after the fact.
If an operator needs a setting to start the service, that setting belongs in the definition or its published run instructions.

## Prove the local service before involving a network

The local loop should answer five simple questions:

- Does a clean checkout compile?
- Do the handlers accept valid input and reject invalid input clearly?
- Does the service definition validate?
- Does the runner start with the settings a new operator will receive?
- Does one known job succeed while one bad request fails safely?

The SDK includes a command-line tool named `cargo-tangle` for creating and deploying Blueprint projects.
The tool is useful only after the service itself is understandable and testable.
Rust’s [Cargo command reference](https://doc.rust-lang.org/cargo/commands/index.html) covers the language-level build and test steps.

Do not use a successful local process as evidence that an operator can run the service.
Local machines often hide missing environment values, filesystem assumptions, open ports, and credentials.

## Make the artifact identifiable

An operator needs to answer three questions before starting a service:

1. What am I running?
2. Where did it come from?
3. How can I tell that the downloaded artifact is the reviewed one?

The answer can be a binary, a container image, or another published artifact.
Whichever format you choose, publish its source, version, and integrity information together.
An integrity value is a short fingerprint that changes when the artifact changes.

Keep dependency versions locked when reproducibility matters.
Cargo’s [lockfile documentation](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html) explains why the lockfile belongs in a deployable Rust project.
If you distribute a container, the [Docker image reference](https://docs.docker.com/reference/cli/docker/image/) explains the image identity an operator will pull.

The source repository and the installable artifact are separate boundaries.
A public source change does not become an installable release until that release is published and tested.

## Use testnet as an evidence run

Testnet is not a ceremony before mainnet.
It is the first place where the complete path meets a network, an operator, and a real service instance.

The testnet run should leave evidence for each of these questions:

| Test | Evidence to keep |
| --- | --- |
| Discovery | An operator can find the registered Blueprint and understand its jobs |
| Startup | At least one operator starts it with the published settings |
| Success | A valid sample job completes from request to result |
| Failure | Invalid input produces a useful error without a stuck service |
| Observation | Logs identify the Blueprint, service instance, job, and failure reason |
| Integrity | The running artifact matches the reviewed source, image, or binary |

This run is where missing environment values, incorrect ports, broken source links, and packaging assumptions become visible.
Record the network, Blueprint identifier, artifact fingerprint, operator version, and sample-job result.

## Write the production envelope

Before production, write down the limits under which the service is expected to work.

| Area | Decision to make |
| --- | --- |
| Artifact | Which immutable source, image, or binary is approved? |
| Keys | Which keys belong to operators, and how are they separated from developer keys? |
| Network | Which endpoints are primary, and what happens if one is unavailable? |
| Price | How does a consumer learn the cost before sending work? |
| Verification | What evidence is appropriate for this kind of job? |
| Monitoring | Who receives health, error, and capacity alerts? |
| Rollback | Which older artifact and settings can be restored? |
| Incident response | What happens if payment succeeds but execution fails? |

Paid services need a payment decision before they go live.
The [x402 payment guide](/blog/x402-payments-for-ai-agents) explains the request-and-payment flow.
Services that handle private data or require trusted hardware need an additional security decision.

## Promote only when the return path works

Promotion means moving from a tested network to a production network.
The safe question is not whether the deployment succeeded once.
It is whether the team can observe a failure and return to a known working artifact.

Promote only when the testnet run, operator instructions, artifact identity, monitoring, and rollback have all been exercised.
Treat payments, private data, trusted execution, and penalties for bad work as separate risk areas rather than one large “production ready” label.

## Keep the release boundary visible

The SDK source is public, but a source change and an installable package can arrive at different times.
Check the package version and the network deployment separately.

The same distinction applies to documentation.
This guide describes a deployment pattern.
The [Tangle verification model](/blog/how-tangle-verifies-work) describes what the network can verify after a job.
Neither page makes a claim about a particular operator’s uptime or a particular service’s correctness without evidence from that service.

## The practical decision

Use this path when several operators need to run the same service and consumers need to discover and call it consistently.

Keep the service private or single-operator when you cannot yet publish an artifact, operator instructions, monitoring ownership, and rollback evidence.
Publishing a definition before those pieces exist creates a service that others can discover but cannot operate reliably.

The next useful action is one isolated testnet job with a recorded artifact fingerprint and a documented failure path.

## Questions readers usually ask

### What does Blueprint deployment add to a normal API deployment?

A normal API is often run by one team.
A Blueprint is a service definition that independent operators can register for and run under Tangle’s network rules.
That makes the operator-facing definition and evidence part of the product.

### What belongs in a Blueprint definition?

It should describe the service metadata, jobs, artifact source, required settings, and integrity information needed to run the service.

### Why deploy to testnet first?

Testnet exposes registration, startup, job execution, logs, and failure behavior before users or payments depend on the service.

### What should I record from the first deployment?

Record the network, Blueprint identifier, artifact fingerprint, operator version, successful sample-job result, and one intentional failure.
