If you want several independent teams to run the same AI service, a decentralized compute protocol has to answer four ordinary questions: what job can a customer request, who runs it, how is it paid for, and what comes back when the job succeeds or fails?
A **Blueprint** is a reusable service definition, and an **operator** is the person or service that runs it on its own machine.
Tangle uses Blueprints and operators to coordinate that work.

You do not need to know Tangle to follow this article.
Think of Tangle as a coordination network for services that are run by independent operators rather than by one company.
The network records the service definition and the important job events, while the operator supplies the machine and runs the program.

The goal is to define discovery metadata, operator requirements, and a job receipt that both sides can inspect.

## Start with a job a buyer can describe

Consider a code-review service.
A buyer sends a repository URL and a set of directories, and expects a report containing findings, file locations, and a severity for each finding.
That sounds simple until the first job times out, the operator runs an old version, or the report is returned without any record of which files were inspected.

A useful protocol definition makes those cases explicit before anyone pays for a run.
The following is an illustrative contract, not a Tangle manifest or a promise about a particular SDK schema:

```json
{
  "job": "review_repository",
  "input": {
    "repository": "https://github.com/example/project",
    "paths": ["src/"]
  },
  "output": {
    "findings": "array",
    "checked_revision": "string"
  },
  "failure": ["invalid_input", "timeout", "operator_unavailable"],
  "evidence": ["operator_id", "service_version", "request_id"]
}
```

The exact fields will vary by service.
The important property is that a caller can predict the input, output, and failure behavior without reading an operator's private runbook.

## Blueprint, operator, instance, and job

Keeping these pieces separate gives each one responsibility and an inspectable state.

| Piece | Plain-language meaning | What the buyer can inspect |
| --- | --- | --- |
| Blueprint | A reusable description of a service and its jobs | The job interface, source, and operating requirements |
| Operator | A person or service that supplies a machine and runs the Blueprint | The operator identity and service status |
| Service instance | One running copy of the Blueprint that can accept work | Its accepted jobs, price, and current version |
| Job | One request sent to a service instance | The request ID, result, timing, and failure reason |

Payment and verification sit around those pieces.
Payment answers whether the request was funded.
Verification answers what evidence is appropriate for this particular job.
A payment receipt does not prove that an AI answer is correct, and a network record does not replace a service-specific test.

## What the protocol changes

With a normal hosted API, one company usually controls the application, the machine, the logs, and the billing account.
That is often the right choice.
It gives the owner a short path to ship and a single place to support customers.

An operator-run service is useful when the buyer wants another choice of provider, the workload can be packaged cleanly, or the operator needs to compete on price, location, hardware, or availability.
The protocol supplies shared rules for finding the service and recording the job.
The Blueprint still has to describe what good execution means.

The request path looks like this:

```text
developer publishes a Blueprint
-> operators inspect the requirements and register
-> a service instance advertises a job and price
-> a buyer sends one request
-> the operator runs the job
-> the buyer receives a result, receipt, and failure details if needed
```

This sequence lets a buyer select a service, fund a job, inspect its receipt, and recover when execution fails.
Calling a service “distributed” without showing this path does not tell a buyer how to use it or recover from an error.

## Use public tools to make the definition runnable

The [Blueprint SDK repository](https://github.com/tangle-network/blueprint) is the public starting point for building these services.
It provides Rust types and a runner so a developer can connect a job number to a function and let an operator run the resulting service.

Here is the smallest public SDK shape shown in the repository's documentation:

```rust
use blueprint_sdk::Router;
use blueprint_sdk::runner::BlueprintRunner;
use blueprint_sdk::runner::config::BlueprintEnvironment;

async fn ping() -> &'static str {
    "pong"
}

let environment = BlueprintEnvironment::default();
let router = Router::new().route(0, ping);

BlueprintRunner::builder((), environment)
    .router(router)
    .run()
    .await?;
```

This example does not create a production inference service.
It shows the boundary that matters: a job has an explicit number, an operator starts a runner, and the runner dispatches the request to code the developer supplied.
The repository and its examples are the authority for the current API, so check the version and follow the linked setup instructions before copying it into a project.

The protocol contracts and Rust bindings live in the public [tnt-core repository](https://github.com/tangle-network/tnt-core).
The [Tangle documentation](https://docs.tangle.tools) covers the network and operator steps.
Keep those sources beside the article because deployment commands and supported networks can change.

## Records buyers need after a job runs

The returned value is only one part of a paid job.
If a browser test returns “failed,” the buyer needs to know whether the page was unreachable, a wallet prompt blocked the flow, or the test assertion was false.

At minimum, a service should make these records available at the boundary where the buyer can use them:

| Record | Why it helps |
| --- | --- |
| request ID | joins payment, execution, and support conversations |
| operator ID | identifies the service provider for this run |
| service version | reveals whether the operator is running the expected artifact |
| start and finish time | separates queue delay from execution time |
| result or artifact link | lets the buyer inspect the actual output |
| failure code | tells the buyer whether to retry, refund, or change input |

An operator can keep private infrastructure details private while still returning this public boundary.
The boundary contract supports a support case without exposing internal logs or asking the buyer to trust an uncheckable status message.

## Timeouts, stale artifacts, and incorrect results

Suppose the buyer pays for the code review and the operator disappears before starting it.
The service needs a documented outcome: a retry with another operator, a refund, or a pending state with a deadline.

Suppose the operator returns a report from an older artifact.
The receipt should identify the service version so the buyer can reject the result or compare it with the current release.

Suppose the model produces a plausible but wrong finding.
The protocol can record who ran the job and what artifact returned the result, but only the code-review service can define a meaningful quality check.
That might be a fixed test corpus, a second review pass, or a human approval step.

These are different failures and should not be collapsed into one “verified” label.

## When this model fits

Choose a decentralized compute protocol when a shared job schema, independent operator requirements, per-request payment, and inspectable results solve a buyer's problem.
Inference, browser tests, code audits, sandbox jobs, and data transformations are reasonable first candidates because each can expose a bounded input and output.

Choose a conventional hosted API when one team can own the runtime, the user already trusts that team, and operator choice would add coordination without improving the product.
Decentralization is a design decision, not a quality badge.

## FAQ

### What is a decentralized compute protocol?

It is a set of shared rules that lets independent operators run a service and lets buyers request, pay for, and inspect jobs through a common interface.

### What is a Tangle Blueprint?

A Blueprint is a reusable service definition that names the jobs, runtime requirements, and evidence an operator must support.

### Does decentralization guarantee a correct AI result?

No.
It can make the operator, artifact, and job history easier to identify, but correctness still depends on the service's code and quality checks.

### What should a team deploy first?

Start with one narrow job whose input, output, price, timeout, and failure behavior can be explained on one page.
