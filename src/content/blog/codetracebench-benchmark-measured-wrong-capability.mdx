Imagine asking an AI agent to review a coding session and point to the step where the agent went wrong.
You need a way to tell whether the answer is useful, so you run it against examples where the incorrect steps are already labeled.

We used CodeTraceBench, a fixed test that compares an analyst's reported steps with labeled steps in a coding-session record.

This makes CodeTraceBench useful for one narrow question: did the analyst locate the labeled mistake?
It does not answer every question a production reviewer cares about, such as whether the analyst explained the cause, ran a check, or proposed a repair that someone could trust.

We ran two analysts over the same 32 pinned records, twice each.
The recursive analyst could inspect the record, run Python over it, and investigate more than once.
The one-shot analyst read the record once and returned its findings.

The benchmark gave them almost the same score.
The recursive analyst cost 5.57 times more.

That is not evidence that recursion is useless.
It is evidence that this score cannot tell us whether the extra investigation helped a reviewer.

This is the first post in [The Instrument Problem](/blog/series/the-instrument-problem/), a series about how a measurement can be correct and still answer the wrong product question.

## First, the terms

A **trace** is the record of an agent run: the model's messages, tool requests, files it touched, and the events that happened along the way.

A **benchmark** is a fixed set of examples used to compare systems under the same conditions.

An **analyst** is a second program that reads that record and reports what went wrong.
It is not the coding agent that produced the original trace.

**F1** is a score that balances two simpler measures.
Precision asks, “When the analyst names a step, how often is it one of the labeled mistakes?”
Recall asks, “How many of the labeled mistakes did the analyst find?”
F1 combines those answers into one number between 0 and 1.

F1 is useful here, but it only sees whether the reported steps overlap the labels.

Here is a tiny example with two labeled mistakes and two reported steps.
The analyst finds one correct step and one false alarm, so both precision and recall are one half.

```typescript
const labeledMistakes = new Set(['step-2', 'step-5'])
const reportedMistakes = new Set(['step-2', 'step-9'])

const hits = [...reportedMistakes].filter((step) => labeledMistakes.has(step)).length
const precision = hits / reportedMistakes.size
const recall = hits / labeledMistakes.size
const f1 = (2 * precision * recall) / (precision + recall)

console.log({ precision, recall, f1 })
// { precision: 0.5, recall: 0.5, f1: 0.5 }
```

CodeTraceBench repeats this comparison over many labeled traces and averages the result.
The arithmetic is clear; the limitation is what the labels leave out.

## What we compared

The input traces, labels, and scorer were held constant.
The table has 64 run slots because each of the 32 traces was run twice.

| Analyst | What it did | F1 | Completed | Cost |
| --- | --- | ---: | ---: | ---: |
| Recursive analyst | Inspected the trace, executed Python, and could investigate in several steps | 0.3644 | 60/64 | $6.73 |
| One-shot analyst | Read the trace once and returned its reported steps | 0.3673 | 63/64 | $1.21 |
| CodeTracer, upstream | The upstream comparison row | 0.3128 | 61/64 | Not reported |

The two main scores differ by 0.003.
For this run, that is a tie.
The recursive run also completed three fewer slots and cost $5.52 more, so the comparison must include completion and cost rather than the score alone.

## What the score rewards

CodeTraceBench labels incorrect steps in an agent trace.
An analyst gets credit when its reported steps overlap those labels.

That is a reasonable measure of step localization.
If your question is “Can this system point to the labeled mistake?”, the table gives you a useful answer.

The recursive analyst did more than the score records.
It executed Python over the trace and returned findings backed by those checks.
CodeTraceBench does not award points for either action.

The extra work may still matter in a real review, but this table cannot show that it matters.

That distinction is the whole result.
A benchmark can be implemented correctly, scored honestly, and still leave out the capability you need to choose a product.

## We tested the obvious fix

The first suspected problem was that the baseline named only one step when several neighboring steps belonged to the same failure.
We changed the analyst so it could report a whole contiguous block of steps.

The change did what it was supposed to do.
The analyst reported blocks with a mean width of 2.27 steps, a median of 2, and a maximum of 11.

The benchmark moved only slightly.

| Measure | One-shot baseline | Failure-block run |
| --- | ---: | ---: |
| F1 | 0.3273 | 0.3407 |
| Precision | 0.2727 | 0.2875 |
| Recall | 0.4091 | 0.4182 |
| Completed | 63/64 | 55/64 |
| Cost | $1.208 | $1.219 |

The analyst found one more labeled step, but it also reported many more steps overall.
Only 16.5% of the predicted steps in the block run landed on a labeled step.

The mechanism worked.
The premise was wrong.
The main problem was not that the analyst needed permission to name more neighboring steps.
The main problem was where it aimed.

## What the benchmark still cannot tell us

The score does not tell us whether a finding includes evidence a reviewer can replay.

It does not tell us whether an executed check passed or failed.

It does not tell us whether a reviewer accepted the proposed repair.

It does not tell us whether the analyst admitted that the trace was too thin to support a conclusion.

Those are separate measurements, not details to hide inside F1.

If the product decision is “Which analyst should help engineers review failures?”, the next version needs columns for replayable evidence, executed checks, accepted repairs, and unsupported claims so the table can answer it.

## The practical decision

Keep CodeTraceBench for step localization.
Do not use its F1 score alone to claim that a recursive analyst is better for engineering review.

Compare the analysts again when the benchmark records replayable evidence, executed checks, accepted repairs, and unsupported claims.
Until then, the honest result is a tie at one-fifth the cost for the one-shot run.

## Questions readers usually ask

### Did recursion improve this benchmark?

No.
The recursive analyst scored 0.3644 and the one-shot analyst scored 0.3673 on the same run slots.
That difference is a tie for this experiment.

### Did the recursive analyst do anything useful?

It investigated the trace, executed Python, and returned findings backed by those checks.
The benchmark does not score those actions, so the result cannot establish their value to a reviewer.

### Why publish a result where the new system did not win?

Because a tie at 5.57 times the cost prevents a false promotion.
It also tells us exactly what the next measurement must include.

### Can I reproduce the numbers?

Yes.
The public reports link the pinned inputs, result files, labels, and scorer information.
Running the model calls yourself still requires the provider access described in the reports.

The evidence supports one narrow claim: CodeTraceBench measured step localization, and it did not show a benefit from the recursive analyst at this cost.
