An agent runs generated code, gets a plausible output, and reports success.
A reviewer opens the result and asks where the file came from, which command produced it, and what happened when the first test failed.
If the system kept only standard output (stdout), the most important part of the run is gone.

That is the useful comparison between Tangle Sandbox and E2B.
Both provide isolated environments where an AI agent can run code, inspect files, and use a Linux system.
They differ in what they keep after the command returns.
E2B fits isolated code execution with a clear input and output.
Tangle Sandbox fits a continuing agent session that must recover, reconnect, expose workspace state, and leave a record of the run.

This is a product-fit comparison, not a benchmark of speed, price, or security strength.

The Tangle examples use the Sandbox SDK: `client.create()` returns a box, `box.exec()` returns `exitCode` and `stdout`, `box.prompt()` runs an agent turn that reports `success`, `usage`, and `costUsd`, and `box.delete()` ends the machine.

## A sandbox is a boundary, not a workflow

The provider may implement a sandbox as a virtual machine, container, or another boundary.
The isolation protects the host and neighboring workloads from the code that runs inside, but it does not decide what the agent may access or what the output means.

An agent runtime is the software that starts the agent loop, gives it tools, enforces permissions and budgets, and records the work.
A durable session is a run that can be found again after the caller disconnects.
A snapshot is a saved environment state that can be used to restore or reproduce a workspace.
A trace is a structured record of the task’s inputs, actions, outputs, timing, and failures.
An agent profile is the configuration of models, tools, budgets, and policies for a run.

## What E2B exposes

E2B describes a sandbox as an on-demand Linux virtual machine with an isolated environment for agents.
Its public quickstart creates a sandbox, runs a command, and reads stdout:

```bash
npm install e2b
```

```js
import { Sandbox } from 'e2b'

const sandbox = await Sandbox.create()
const result = await sandbox.commands.run(
  'python -c "print(2 + 2)"',
)

console.log(result.stdout)
await sandbox.kill()
```

The [E2B documentation](https://e2b.dev/docs) identifies sandboxes and templates as core building blocks.
Its [sandbox reference](https://e2b.dev/docs/sdk-reference/js-sdk/v2.0.0/sandbox) documents Linux access, files and directories, commands, isolated code, and internet access.
Its [template documentation](https://e2b.dev/docs/template/start-ready-command) explains how a template can install dependencies, start a process during a build, wait for readiness, and capture the environment in a snapshot.

E2B also documents lifecycle and persistence features, so calling it “ephemeral” is wrong as a blanket claim.
Its [persistence guide](https://e2b.dev/docs/sandbox/persistence) says what can be paused, resumed, or retained.
The question for an agent is which state is retained, for how long, under which lifecycle operation, and whether it includes the agent’s decision history.

1. Start from a known environment.

## Recover a timed-out run before retrying

Suppose the client times out right after the first test starts.
A timeout is not proof that the sandbox disappeared, so look before creating anything new.

On E2B, store the sandbox ID before dispatching work.
E2B documents [`Sandbox.connect`](https://e2b.dev/docs/sdk-reference/js-sdk/v2.0.0/sandbox) to reattach by ID, and pause and resume in its [persistence guide](https://e2b.dev/docs/sandbox/persistence).
Deciding whether a retry duplicates work stays with your application.

On Tangle, the worker example’s sandbox ID and execution ID are that record.
Dispatching the same session ID while it is still running returns its live status instead of starting a second agent, and passing a `turnId` keeps a finished turn from running again on retry.

On either, create a second sandbox only after you can show the first request never started.

## Separate the template from the live workspace

E2B’s template and sandbox solve different parts of the workflow.
A template describes how to prepare dependencies and a ready process.
A live sandbox holds the mutable files, commands, and external state for one run.
A saved environment can reproduce setup, but it is not a replay of the agent’s decisions.

For the repair task, put the expensive, repeatable setup in the template, create a sandbox from it, copy in the repository, and record the first failing command before the agent edits anything.
If a dependency is wrong, rebuild the template and start a fresh test.
If the agent’s edit is wrong, keep the live sandbox so the reviewer can inspect the failed state.
Store the template identity, sandbox ID, and request key beside the first failure and final result, so a reviewer can tell a new environment from a resumed workspace or a duplicate request.

| Need | E2B | Tangle Sandbox |
| --- | --- | --- |
| Environment | On-demand Linux sandbox from a template or default image | Dev container or microVM with agent-oriented options |
| Basic execution | Commands, files, isolated code, and internet access | Commands, files, ports, prompts, and task sessions |
| Reusable state | Templates and documented persistence features | Snapshots plus durable sessions |
| Agent loop | Compose your own loop or product | Select a coding agent and run it in the sandbox |
| Recovery record | Depends on what the application stores | Durable sessions and traces |
| GPU | Check E2B’s current documentation and limits | Optional GPU lease documented in the SDK |

## Failure cases to test on both

| Failure | Question |
| --- | --- |
| Command timeout | Can the caller distinguish stopped work from unknown work? |
| Lost response | Can it query the original task before retrying? |
| Workspace corruption | Can it restore a known state without deleting useful evidence? |
| Secret exposure | Are credentials excluded from logs, snapshots, traces, and artifacts? |
| Network side effect | Is outbound access explicit and reviewable? |
| Bad answer | Is the output tested separately from the execution record? |

Isolation reduces the blast radius of agent code.
It does not make credentials safe by default, make the model’s plan sound, or prove that a returned file is the right file.

## Choose by the artifact that must survive

Choose E2B when:

- the job is primarily isolated code execution, such as a code interpreter, a generated-script runner, or a data job that returns files;
- a template, command sequence, and output bundle describe the workflow;
- files, stdout, and exit status are sufficient evidence;
- your application wants to own the agent loop and retry policy.

Choose Tangle Sandbox when:

- the agent needs a continuing workspace;
- the run must survive a dropped client or repeated webhook;
- recovery depends on keeping the failed state;
- browser evidence and code changes belong to one review;
- the agent profile, model choice, and trace should travel with the task.

Before migrating, run the repair task above on both with the same input, model, timeout, and retry rules.
Compare completion, recovery, duplicate work, evidence, and cost under the policy you intend to ship.
