Staking puts economic collateral behind a service provider.
In Tangle, the provider that runs a service is called an **operator**.
A **Blueprint** is the public definition of the jobs that service accepts.
Staking does not turn that collateral into an automatic rating for an AI model, and it does not prove that a completion is correct.

**Staking** means locking assets behind the operator according to protocol rules.
If a Blueprint defines a specific failure and the protocol allows it, **slashing** can reduce that locked stake as a penalty.

The useful question is therefore not “which operator has the most stake?”
It is “what behavior does the stake support, and what public evidence lets a buyer or delegator judge that behavior?”

## Start with a paid AI job

Imagine three operators offering the same document-extraction Blueprint.
All three have enough stake to register.
One responds in two seconds with a useful receipt, one responds in thirty seconds with frequent timeouts, and one returns plausible fields from an old model version.

The stake is the same kind of economic bond in each case.
The service history is not.

For a buyer, the important records include:

| Service question | Useful evidence |
| --- | --- |
| Was the operator available? | heartbeat or health history |
| Did it accept the request? | quote or request acknowledgment |
| Did it finish? | result, duration, and failure code |
| Which code ran? | artifact or service version |
| What did it cost? | price, payment record, and refund state |
| Can the result be checked? | test, attestation, comparison, or review artifact |

Staking makes poor behavior economically relevant only when the Blueprint defines how that behavior is observed and what response is allowed.

## What TNT Core provides

The public [TNT Core repository](https://github.com/tangle-network/tnt-core) describes Tangle's EVM-native staking and service protocol.
Its public contracts include operator registration, multi-asset delegation, service management, payment paths, and Blueprint-specific penalty hooks.

The repository's public lifecycle follows six recorded protocol steps:

```text
developer registers a Blueprint
-> operators stake and register for it
-> a user requests a service
-> registered operators approve or accept the service
-> jobs run and results are submitted
-> payment and rewards settle
```

The exact contract names and supported networks belong in the current repository documentation.
The [Tangle docs](https://docs.tangle.tools) are the public source for deployment details.

The protocol can record the operator and job events.
The Blueprint author still chooses the service-specific conditions, such as a timeout, a required number of operators, or a dispute process for a bad result.

## Separate economic capacity, operations, and result quality

Many staking pages collapse several ideas into one number.
Keep them separate:

1. **Economic capacity** asks how much collateral an operator has committed.
2. **Operational behavior** asks whether the operator accepts, runs, and finishes jobs reliably.
3. **Result quality** asks whether the output meets the service's stated requirement.

An operator can score well on one and poorly on another.
A large stake does not make a slow operator fast.
A fast operator can still return a wrong extraction.
A correct result from one job does not establish a general quality record.

The service page should show all three dimensions instead of hiding them behind a single “trusted” label.

## A toy report makes the distinction obvious

This TypeScript is a teaching example, not a protocol scoring formula.
It shows why a dashboard should keep stake and service history in separate fields:

```ts
type OperatorRecord = {
  stake: number
  completed: number
  failed: number
  medianSeconds: number
  checkedResults: number
}

function serviceHistory(record: OperatorRecord) {
  const attempts = record.completed + record.failed

  return {
    stake: record.stake,
    completionRate: attempts === 0 ? null : record.completed / attempts,
    medianSeconds: record.medianSeconds,
    checkedResults: record.checkedResults
  }
}
```

The function does not decide whether an operator deserves delegation.
It exposes the fields a human can discuss.
If `checkedResults` is zero, a high completion rate only tells us that jobs finished, not that their answers were correct.
If `attempts` is zero, a large stake is capacity without service evidence.

Real dashboards should also show the date range, Blueprint version, number of operators, and any missing telemetry.

## When slashing is meaningful

Slashing is useful when the failure is objective enough to define in advance.
Examples include signing two incompatible results for the same job, failing a required liveness check for a stated period, or violating a Blueprint-specific commitment that has a public dispute process.

It is much harder to slash for an open-ended judgment such as “the answer felt weak.”
An AI service needs a reproducible test, a comparison, or a review process before a financial penalty can be fair.

The [TNT Core README](https://github.com/tangle-network/tnt-core) describes Blueprint service managers as the place where service logic, result handling, and slashing conditions are defined.
Read the current contract and audit material before promising a penalty in a product page.

The presence of a slashing hook is not evidence that a particular service has a working dispute process.
The deployed Blueprint, its rules, and the recorded events are what a buyer can inspect.

## Price the real cost of AI work

AI operators pay for model calls, GPU or CPU time, storage, browser sessions, tool requests, and support.
Staking does not remove those costs.
The service needs a price or quote that explains what the caller receives and when payment is refundable.

The request path may look like this:

```text
buyer sends job
-> operator returns a price or quote with an expiry
-> buyer pays
-> operator runs the pinned service version
-> result and evidence return
-> payment, reward, or refund follows the published rule
```

For variable-cost jobs, the public [RFQ job quote guide](/blog/rfq-job-quotes-tangle-operator-accountability) explains how an expiry lets a buyer reject a price after the quote changes.
For payment-native requests, see [x402 Payments For AI Agents](/blog/x402-payments-for-ai-agents).

## What a delegator should ask

Delegators should not choose an operator from stake alone.
They should ask:

- How many jobs has this operator attempted on the Blueprint I care about?
- What fraction finished, and over what period?
- Which service version produced those results?
- How many results had an independent check?
- How often did the operator change price or miss a quote expiry?
- What evidence exists for a dispute, refund, or penalty?

If a page cannot answer because the service does not collect the data, say that plainly.
Missing evidence is different from a clean record.

## When staking is the wrong tool

Keep a service single-operator while it is still changing its job interface, has no objective failure policy, or has too little demand to support operator competition.
Adding collateral and contract rules before the service can measure missed jobs adds process without an accountability record.

Use operator staking when independent providers, economic commitment, and service-level history solve a real buyer problem.
Keep result quality in a separate measurement system and show the reader how the two connect.

## FAQ

### What is operator staking for AI services?

It is the practice of requiring service operators to commit assets while they run AI jobs defined by a Blueprint.

### Does more stake mean a better AI service?

No.
More stake indicates more economic commitment under the protocol's rules.
It does not prove speed, uptime, or answer quality.

### What is slashing?

Slashing is a protocol-defined penalty that reduces an operator's staked assets after a specified failure or misconduct is proven through the Blueprint's rules.

### What should a buyer see?

A buyer should see price, operator identity, service status, version, timing, result, failure reason, and the evidence used to check the job.
