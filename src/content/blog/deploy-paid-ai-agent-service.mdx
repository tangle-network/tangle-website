A paid AI service has two promises to keep.
It must accept a payment correctly, and it must do work that the buyer can understand and review.

An **agent service** is an API that lets software delegate a task to an AI system.
An **operator** is the person or team running that service.
On Tangle, a **Blueprint** is the public service definition that describes the jobs an operator can run.
A **trace** is the record of what happened during one invocation.

The launch question is not “does the endpoint answer?”
It is “can a buyer discover the job, pay for it, retry safely, understand what happened, and challenge a bad result?”

This guide starts with one narrow paid job.
It treats discovery, payment, execution, health, and result evidence as separate decisions so a failure in one area does not disappear inside a generic API error.

## The first service should be small

Choose one input schema, one job, one price, and one output that a reviewer can inspect.

| Boundary | First version |
| --- | --- |
| Input | One documented request shape |
| Price | One fixed amount or a short price table |
| Execution | One agent or Blueprint job |
| Output | One result or artifact with a clear check |
| Retry | An idempotent request identifier, so a duplicate cannot run twice by accident |
| Support | A trace identifier returned with every response |

An **idempotent** request produces the same effect when the client retries it.
Payment retries need this property because a network timeout does not tell the client whether the first request reached the service.

Do not launch a marketplace before one paid job survives a failed payment, failed execution, duplicate retry, and bad-result review.

## Five questions a buyer should answer

Before sending money, a buyer should be able to find:

1. What does this job accept and return?
2. What does it cost, and how long is the price valid?
3. Who may call it?
4. What happens when payment or execution fails?
5. Which record proves what happened?

Discovery metadata, an API description, and a health surface answer the first two questions.
Authorization and payment policy answer the third.
The incident paths and trace answer the last two.

The public [Blueprint Agent repository](https://github.com/tangle-network/blueprint-agent) is one implementation surface.
The [x402 payment explanation](/blog/blueprint-sdk-x402-payments-runnable-jobs) describes the pay-per-request flow.

## Payment is a state machine, not a button

For an x402-based service, the buyer sees this sequence:

1. Request the job.
2. Receive a 402 response with price and settlement options.
3. Sign and settle the payment.
4. Retry with payment proof.
5. Receive either a dispatched job or an explicit rejection.

The service should record which state it reached.
“Payment accepted” is not the same as “job completed,” and “job completed” is not the same as “result accepted.”

The [x402 protocol](https://www.x402.org/) defines the payment format.
The [Coinbase x402 documentation](https://docs.cdp.coinbase.com/x402/welcome) and [Cloudflare’s overview](https://blog.cloudflare.com/x402/) describe related deployment concerns.

## Health should precede payment

Do not accept a payment for work that the operator already knows cannot run.
Check the service and its dependencies before presenting a price whenever the product can do so safely.

Health information should answer:

- can the service accept a new job?
- is the selected model or tool available?
- is the operator within its resource policy?
- is the payment path reachable?
- where will the request record appear?

Health is a capacity signal.
It is not proof that the eventual result will be correct.

## Incident paths must be designed first

Paid services need an answer for each failure that changes what the buyer believes.

| Incident | Required policy |
| --- | --- |
| Payment accepted, job failed | Refund, retry, or support path |
| Job succeeded, result is wrong | Quality dispute and trace review |
| Model or tool route degraded | Fallback or stop policy |
| Operator unhealthy | Refuse new payment or mark the service unavailable |
| Duplicate retry | Return the original result or a clear idempotency error |
| Price expired | Ask for a new quote without running the job |

If those policies are not written down, the first paying customer becomes the incident test.

## The evidence a buyer receives

A useful response includes more than the final text.
It can include:

- a request and job identifier
- the payment identifier and quote fingerprint
- the model or tool route used
- start and completion state
- the result or artifact
- the checks that ran
- fields the service could not observe

This record lets a buyer distinguish a model failure, a payment failure, a capacity failure, and a bad result.
It also gives the operator a reproducible support path.

The [Tangle verification overview](/blog/how-tangle-verifies-work) explains why result checks need to match the job.
Payment alone does not prove quality.

## Keep the product boundary honest

Separate these claims:

| Claim | Evidence needed |
| --- | --- |
| The service is discoverable | Public metadata and working documentation |
| The request was paid | Settlement record and payment proof |
| The job ran | Execution record and completion state |
| The claimed model or environment ran | Model identity or protected-execution evidence |
| The result is correct | Task-specific check, replay, or review |

No single receipt proves all five.
The service should show which claim each field supports.

## The practical decision

Publish one narrow paid job when you can trace every invocation from discovery through payment, execution, and result review.

Keep the service private while any of those states are ambiguous, especially when a payment can settle before a job fails.
Add more jobs, models, tools, or pricing options only after the first job’s failure paths are visible.

The next useful action is a single paid smoke run with one intentional payment failure, one execution failure, one duplicate retry, and one successful result review.

## Questions readers usually ask

### Is x402 required?

No.
It is a good fit for programmatic pay-per-request buyers, while account or subscription billing may fit customers who need invoices, refunds, or long-running contracts.

### What should the service verify before launch?

Verify discovery, authorization, the payment challenge and retry, operator health, execution, records, and the result check.

### Does a healthy operator guarantee a good result?

No.
Health says the service can accept work.
Result quality needs a separate check.

### Why start with one job?

One job makes the payment, retry, and evidence state machine small enough to inspect.
That is the fastest way to find a missing failure policy before more customers depend on it.
