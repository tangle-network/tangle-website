An AI service marketplace becomes useful when a program can find a service, understand its job contract, pay for one request, and decide whether the returned result is usable.
The marketplace is the request path, not a directory of logos.

This article follows one concrete request: an agent needs to extract fields from an invoice.
The service is a Tangle **Blueprint**, which is a reusable definition of a job that independent **operators** can run.
An operator is the person or service that supplies the machine and runs one service instance.
x402 is an HTTP payment flow that lets a program respond with payment information before the caller retries a request.

The example deliberately leaves wallet signing, payment-rail selection, and the operator runtime outside the client.
The linked x402 and Blueprint documentation covers those three boundaries.

## The buyer starts with a job, not a marketplace search

An agent does not want a category label such as “AI services.”
It wants an invoice converted into a typed object with a vendor, date, currency, subtotal, and total.

That distinction determines what the marketplace must publish:

| Marketplace field | Example value |
| --- | --- |
| job name | `extract_invoice` |
| input | PDF or image under a stated size |
| output | JSON fields with confidence and source locations |
| price | fixed amount or an expiring quote |
| expected time | a range with a timeout |
| evidence | input checksum, model version, request ID |
| failure | unsupported file, timeout, or provider error |

A listing that says “invoice AI” without an input and output contract gives the agent nothing it can validate.
The job contract is the product.

## Discovery should be machine-readable

A human page can explain the service, but an agent should not have to scrape marketing prose to decide whether it can call the job.
The marketplace needs a structured record with the same information:

```json
{
  "service": "invoice-extractor",
  "blueprint": "invoice-extraction-v2",
  "jobs": [
    {
      "name": "extract_invoice",
      "input": "application/pdf",
      "output": "invoice-json-v1",
      "price": { "asset": "USDC", "amount": "0.03" },
      "timeoutSeconds": 45,
      "evidence": ["request_id", "input_hash", "model_version"]
    }
  ]
}
```

This is an illustrative catalog shape, not a claim about a current Tangle API.
The schema must be versioned so a cached agent knows when a price, input, output, or evidence field changed.

## The request and payment sequence

The public [x402 documentation](https://docs.cdp.coinbase.com/x402/welcome) describes the general request-payment-retry pattern.
The flow is:

```text
agent discovers a job
-> agent reads input, output, price, and timeout
-> agent sends the request
-> service returns a payment challenge
-> agent pays through the supported rail
-> agent retries with payment evidence
-> an operator runs the Blueprint job
-> service returns result, receipt, and failure details
```

On the retry, the service verifies the payment evidence before allowing the paid job to run.
It does not prove that the extracted invoice fields are correct.
The service still needs a validation policy, such as checking that the total equals the subtotal plus tax when those fields are present.

## A small TypeScript buyer

The following toy client shows how a buyer should keep discovery, payment, and result checking separate.
It uses ordinary `fetch` and a callback for payment rather than pretending to be an x402 SDK.
Use the current x402 client for a real deployment.

```ts
type Job = {
  endpoint: string
  price: { asset: string; amount: string }
  timeoutSeconds: number
}

type Invoice = {
  vendor: string
  subtotal: number
  tax: number
  total: number
}

async function buyInvoiceExtraction(
  job: Job,
  file: Blob,
  pay: (challenge: unknown) => Promise<string>
): Promise<Invoice> {
  const first = await fetch(job.endpoint, {
    method: 'POST',
    body: file
  })

  if (first.status !== 402) {
    throw new Error(`expected payment challenge, received ${first.status}`)
  }

  const challenge = await first.json()
  const paymentEvidence = await pay(challenge)
  const second = await fetch(job.endpoint, {
    method: 'POST',
    headers: { 'payment-evidence': paymentEvidence },
    body: file
  })

  if (!second.ok) {
    throw new Error(`paid job failed with ${second.status}`)
  }

  const result = (await second.json()) as Invoice
  if (result.subtotal + result.tax !== result.total) {
    throw new Error('service returned an inconsistent invoice total')
  }

  return result
}
```

The header name and payment callback above are placeholders for the current client library.
That limitation is intentional: inventing a protocol header in a blog would create a broken integration.
The code still demonstrates the important design: a payment response is handled before retry, a paid failure is surfaced, and a cheap deterministic check runs after the model result.

## Where Blueprints and operators fit

The marketplace can describe a Blueprint and list service instances, but it does not execute the invoice extraction itself.
An operator runs the public artifact and reports the job result.
The public SDK exposes `Router`, `BlueprintRunner`, and `BlueprintEnvironment`; the [SDK README](https://github.com/tangle-network/blueprint/tree/main/crates/sdk) shows how the runner connects a job number to a function.
The [Blueprint deployment documentation](https://docs.tangle.tools/developers/blueprint-sdk) covers the current `cargo tangle blueprint deploy` command, network selection, and operator setup.

For each listed service, the marketplace should expose:

| Marketplace field | Buyer decision |
| --- | --- |
| Blueprint and version | Is this the interface the agent integrated with? |
| operator identity | Who ran this request? |
| price or quote expiry | Can the buyer predict the cost? |
| timeout and status | Should the agent wait or retry elsewhere? |
| result and evidence | Can the buyer inspect what happened? |
| refund rule | What happens after payment but before a usable result? |

That information also lets an agent choose among operators without pretending that the cheapest listing is always the best one.
An operator with more complete receipts may be easier to debug than one with a lower quote.

## Handle paid failures before adding more services

The first marketplace launch should support one job end to end.
For the invoice example, test these cases:

- the file is an unsupported type and should be rejected before payment;
- the payment challenge expires and the agent must request a new one;
- payment succeeds but the operator times out;
- the result arrives with an invalid total;
- the operator runs a service version older than the catalog entry.

Each case needs a visible result for the agent.
“Something went wrong” is not a retry policy.
The service should identify whether retrying the same operator is safe, whether a new operator can use the payment, and whether a refund is due.

For variable-cost jobs, [RFQ Job Quotes And Tangle Operator Accountability](/blog/rfq-job-quotes-tangle-operator-accountability) explains how quote expiry controls the price-validity and operator-acceptance window.
For privacy boundaries around paid inference, read [Anonymous LLM Usage With Shielded Payments](/blog/anonymous-llm-usage-shielded-payments).

## Why crypto payments can fit this shape

Pay-per-request payment is a natural fit when an agent makes many small calls, a service has variable cost, or a buyer does not need a long-lived account.
It is not automatically better than cards or subscriptions.
Subscriptions may be easier for a human team with predictable usage, refunds, and procurement requirements.

Crypto rails help when a program can settle a precise price or quote without a recurring account or procurement workflow.
They do not solve discovery, operator quality, support, or result correctness.
Those are marketplace and service-contract problems.

## Decision rule

Build an AI service marketplace with crypto payments when you can define one bounded job, publish its input and output, quote it before work starts, and return evidence after it finishes.
Do not begin with a directory of vague assistants.
Begin with one paid request that a program can discover, pay for, validate, and retry.

## FAQ

### What is an AI service marketplace with crypto payments?

It is a catalog and request path where people or programs discover a defined AI job, pay through crypto-native rails, and receive a result with evidence.

### Why use pay-per-request instead of a subscription?

Pay-per-request can fit one-off jobs, machine-to-machine calls, and services whose cost changes with input size.
Subscriptions can still be better for predictable human usage.

### What services should launch first?

Choose a job with a bounded input, clear output, observable success check, and explicit failure path, such as invoice extraction, browser testing, code audit, or data transformation.

### What does Tangle add?

Tangle provides the public Blueprint and operator model for services that independent providers can run.
The marketplace still has to publish prices, versions, evidence, support, and failure behavior.
