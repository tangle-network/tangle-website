Imagine asking a coding agent to upgrade a dependency.
The useful result is not a paragraph saying that the upgrade should work.
It is a changed `package-lock.json` with the new version recorded, a test run, the error from the first attempt, and a clear explanation of what changed.

To produce that result, the agent needs to write files, install packages, run commands, inspect a failure, and try again.
Give it your laptop and one bad command can expose a credential or damage unrelated work.
Give it only a one-shot code box and it cannot keep the workspace it is trying to repair.

An **AI agent sandbox** is the middle layer: an isolated workspace where an agent can use files, processes, tools, and network access under explicit rules.
Tangle Sandbox creates that workspace through `client.create`, waits for `running`, runs commands with `box.exec`, and removes it with `box.delete`.
Before calling `box.delete`, the client must copy the patch and test logs to durable storage so the temporary workspace can disappear while the review record remains available.

This guide explains what that means in practice, shows a small policy example, and then uses the public Tangle Sandbox SDK to run a real command.
You do not need to know Tangle’s other products to follow along.

## The problem is a workspace, not a prompt

A chat model can generate a plausible answer without touching a filesystem.
An agent has a longer job:

1. Read the project it was given.
2. Change one or more files.
3. Run the project’s tools.
4. Learn from the result and decide what to do next.
5. Return both the result and enough evidence for someone else to check it.

That loop needs a place to live.
A useful sandbox isolates its own filesystem and process boundary, applies a network policy that allowlists required hosts and denies others by default, and exposes a delete operation that closes the workspace when the task is over.
It also needs a snapshot so a retry can start from the same files instead of repeating setup.

This is why an agent sandbox is different from a prompt with a tool attached.
The prompt describes the job; the sandbox supplies the working environment.

## The vocabulary: runtime, policy, evidence

The vocabulary around agents is often used as if everyone arrived with the same dictionary.
Here is the short version.

| Term | Plain-language meaning | Why it matters |
| --- | --- | --- |
| **Agent runtime** | The software and machine where an agent’s work executes | It determines which files, commands, tools, and limits exist |
| **Policy** | The rules that say what the agent may do | A rule can allow tests while blocking a request to send data to an unknown host |
| **Evidence** | The files, output, and events left behind by a run | A reviewer can check the result instead of trusting the agent’s summary |

A sandbox is therefore more than a container with a model inside it.
It is a place to make a change, observe the outcome, and decide whether the next action is allowed.

## A small policy example

Before wiring a policy to a service, it helps to make the decision visible in ordinary TypeScript.
The example below only evaluates a policy object and prints a decision; it does not execute a command, so it is safe to run in a browser or a local TypeScript playground.
It is a teaching example, not a security boundary.

```typescript
type Operation = {
  command: string
  needsNetwork: boolean
  writes: string[]
}

const allowedCommands = new Set(['pnpm test', 'pnpm lint'])

function review(operation: Operation) {
  if (!allowedCommands.has(operation.command)) {
    return { allowed: false, reason: 'command is not on the allowlist' }
  }

  if (operation.needsNetwork) {
    return { allowed: false, reason: 'network access needs an explicit decision' }
  }

  const writesOutsideWorkspace = operation.writes.some(
    (file) => !file.startsWith('workspace/'),
  )

  if (writesOutsideWorkspace) {
    return { allowed: false, reason: 'writes must stay inside the workspace' }
  }

  return { allowed: true, reason: 'test command stays inside the workspace' }
}

console.log(
  review({
    command: 'pnpm test',
    needsNetwork: false,
    writes: ['workspace/test-report.xml'],
  }),
)
```

The important part is the shape of the decision.
The agent receives a reason it can understand, while the reviewer receives a record of which rule was applied.
In production, the process enforcing the rule must evaluate it outside the prompt; a JavaScript function shown to the agent cannot protect a machine by itself.

## Try the public surface first

Tangle Sandbox publishes a machine-readable [service manifest](https://sandbox.tangle.tools/.well-known/tangle-agent.json) and a scoped npm package.
The manifest lists the SDK’s primary `Sandbox` class, the `TANGLE_API_KEY` environment variable, and the discovery calls that do not require an account key.

```bash
npm install @tangle-network/sandbox
curl -fsS https://sandbox.tangle.tools/health
curl -fsS https://sandbox.tangle.tools/v1/public-templates
```

The first request answers a narrow question: can the public service answer a health check?
The second discovers templates when the public catalog has entries.
At the time of writing, the health response is `{"status":"ok"}` and the catalog can legitimately be empty while a template publish is still pending.
Neither response proves that an authenticated workspace can be created or that a particular command will succeed.

Use the same distinction for any service: separate capability discovery from an authenticated workload test.
Discovery tells an agent what a service says it supports; a real workload tells you what happened when you asked it to do something.

## The real SDK loop

Run the following example from a Node.js process or TypeScript service.
Keep the API key on the server; a browser demo should call your own small backend rather than shipping the key to every visitor.

```typescript
import { Sandbox } from '@tangle-network/sandbox'

const client = new Sandbox({
  apiKey: process.env.TANGLE_API_KEY!,
  baseUrl: process.env.SANDBOX_BASE_URL ?? 'https://sandbox.tangle.tools',
})

const box = await client.create({
  name: 'dependency-review',
  environment: 'universal',
  resources: {
    cpuCores: 2,
    memoryMB: 4096,
    diskGB: 20,
  },
})

try {
  await box.waitFor('running')

  const result = await box.exec('node --version && npm --version')
  if (result.exitCode !== 0) {
    throw new Error(result.stderr)
  }

  console.log(result.stdout)
} finally {
  await box.delete()
}
```

For this example, the smallest useful lifecycle covers creation, readiness, command execution, result inspection, and cleanup even when the command fails.
The public [Sandbox package documentation](https://unpkg.com/@tangle-network/sandbox@0.17.3/README.md) also covers file reads and writes, snapshots, sessions, network controls, and agent prompts.

For a dependency update, the command would become a sequence such as `npm install`, `npm test`, and an artifact read from the workspace.
The agent can keep the failed test output, make a second change, and run the test again without pretending the first attempt succeeded.

## Isolation, failures, network, recovery, cleanup

Run these checks with a small, throwaway task before giving an agent access to an important repository.

| Check | What a useful result looks like |
| --- | --- |
| Isolation | A file created in the workspace does not appear on the host running the client |
| Failure visibility | A failing command returns a non-zero exit code plus standard output and error text |
| Network control | An outbound request is allowed or denied according to a rule you can inspect |
| Recovery | A second command can see the first attempt’s files and logs |
| Cleanup | Deleting the workspace removes temporary state unless you intentionally saved a snapshot or artifact |

The checks are deliberately boring.
Each one produces observable evidence: files for isolation, exit codes for failures, network decisions, retained logs for recovery, or cleanup state.

## When a different tool is the right tool

An agent sandbox is not automatically the best answer for every workload.

| Tool | Choose it when | Reach for a sandbox when |
| --- | --- | --- |
| Code interpreter | You need one short calculation or generated chart | The task needs a project directory, several commands, or a retry |
| Browser automation | You need to click through a site and capture UI state | The browser is one part of a larger build or research workspace |
| Serverless job runner | The input and output are fixed and the job can run to completion once | The agent must inspect an intermediate result and choose the next command |
| Agent sandbox | You need files, processes, packages, policy, and evidence together | You should still add the smallest permissions and lifetime that fit the task |

[Browser Agent](https://github.com/tangle-network/browser-agent-driver) can provide browser state and screenshots, while Sandbox can host the files and processes around that run.
The broader [agent runtime guide](/blog/agent-runtime-environments/) explains how a workspace fits into an agent’s execution loop.

## What this proves, and what it does not

The SDK example shows that the public client has a clear lifecycle for creating, using, and deleting a workspace.
The policy example shows how a permission decision can be made explicit and testable before it is connected to an enforcement service.

Together, they do not prove that an agent will make the right change.
They also do not prove that a particular network rule, credential configuration, image, or workload is safe for your organization.
Those claims require a task-specific test with the same permissions, inputs, and failure paths that production will use.

The useful promise of a sandbox is narrower and more practical:
it gives an agent a bounded place to work, and it gives the rest of the system somewhere to collect the evidence.

## Start with one real task

Pick a task that is valuable but disposable, such as installing a package and running its tests against a small sample project.
Record the files changed, command exit codes, network decisions, elapsed time, and artifacts produced.
Then repeat the task after a deliberate failure and check whether a human can understand what happened without reading the agent’s private conversation.

If that experiment passes, you have learned something concrete about your workload.
If it fails, the failure has already paid for the sandbox by showing which boundary needs work before a larger agent receives access.

## FAQ

### What is an AI agent sandbox?

An AI agent sandbox is an isolated workspace where an agent can edit files, run processes, use tools, and return evidence without directly controlling the host machine.

### Is a code interpreter the same as an agent sandbox?

Usually not.
A code interpreter is designed for a bounded execution request, while a sandbox is designed to keep a multi-step workspace alive long enough for an agent to inspect results and recover from failure.

### Is an AI agent sandbox safe by default?

No.
Safety depends on the rules around files, network access, credentials, tool permissions, time limits, logging, and cleanup.
A sandbox reduces the area a mistake can affect; it does not remove the need to design and test those rules.

### When should I use Tangle Sandbox?

Use Tangle Sandbox when an agent needs a disposable development environment with files, processes, packages, and a reviewable result.
Start with the public health and template calls, then run one small authenticated workload before connecting a larger agent.
