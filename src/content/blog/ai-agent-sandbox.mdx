We run Claude Code, Codex and OpenCode inside Tangle's hosted sandbox, and we measure it the way you would have to defend it to your team. A Tangle sandbox keeps an agent's files through stop and resume. It limits the network by policy, and it caps a fleet's machines and spend before anything boots. The catches are as concrete. The default boundary is a container, where E2B gives every session a Firecracker microVM and Modal uses gVisor; on Tangle, Firecracker is something you ask for. In our benchmark week, a new sandbox was ready in 1.5 s at the median and 12.4 s at p95, eight times the median. And 13% of create attempts failed. So ask for Firecracker when the code is hostile, size timeouts to p95, and retry every create.

## A hosted sandbox moves the blast radius off your machine

A coding agent installs packages, runs tests and executes code a model wrote a second ago. On a laptop, that code runs next to your SSH keys, your cloud credentials and every other repository you have checked out. A local Docker container narrows the filesystem. It still shares your network and whatever you mounted into it.

A hosted sandbox is an isolated machine with files, a terminal and, if you want one, a browser. The agent's code runs there, and nothing of yours is on that disk unless you put it there.

The threat is runaway or prompt-injected code. One agent deletes the wrong directory. Another reads a poisoned README and tries to send your code somewhere. The sandbox contains the first on its own. The second needs a network path and something worth stealing, so close both: restrict egress, and keep the credentials you control out of the box. The box is not empty of keys: it carries a scoped per-box key that the platform mints and revokes.[^boxkey] In our 18 November runs, each box's router key allowed only the requested model, expired an hour after create and was revoked when the box was deleted.

The SDK helps with the credentials. Application secrets you inject can carry a lifetime, after which the runtime removes them. The same call refuses platform-managed credentials such as your Tangle API key.[^creds]

If you are weighing a local container library against a hosted sandbox, compare what surrounds the container. You want a disk that outlives your process, a network policy the platform enforces, caps on a fleet, and a machine that holds none of your secrets.

## The default boundary is a container, so ask for Firecracker for untrusted code

The boundary on each:

- **Tangle, default.** A container on the host kernel. Our recorded egress test's default box ran on the docker runtime.
- **Tangle, on request.** A Firecracker microVM with its own kernel, chosen with `runtime: "firecracker"` at create. It never falls back to Docker. An account not placed on Firecracker gets a runtime-disabled error.
- **E2B.** A Firecracker microVM per session.
- **Modal.** gVisor, according to third-party comparisons such as [LogRocket's](https://blog.logrocket.com/comparing-ai-agent-sandbox-platforms-e2b-modal-daytona-and-more/).

The SDK README also mentions Firecracker as an isolated image builder for container boxes. That builder is a separate thing from the per-sandbox runtime above.

We think the no-fallback rule is right, because a silent downgrade is the bug you would never notice. Check availability for your account before you build on it. Our one recorded Firecracker box is the egress test below; every other recorded example in this post used the default.

Is a container enough? Anthropic's guidance on securing source code with LLMs draws the line where we would. Containers are fine for an agent reading code, but the target and its exploit code belong in a microVM or full VM with egress locked down.[^anthropic] So an agent editing your own repository can live in the default container. An agent running code from strangers gets Firecracker, where your account has it, and a blocked network: a microVM runs its own kernel, while a container shares the host's.

## Lock egress to an allowlist before the agent reads anything untrusted

Set the policy at create: `egressPolicy: { mode: "strict", allowDomains: [...] }` sets an allowlist of the domains you list, and `includeImplicitDomains: true` adds the platform's default allowlist to yours.

- Mode `blocked` refused every request in our test below. The other modes are `open` and `strict`.
- Omit the policy and the box inherits your team's policy, or the platform default outside a team.
- To tighten a running box, the SDK typings document `box.egress.update()`. We have not run that call.

## A new sandbox was ready in 1.5 s at the median and 12.4 s at p95

The short version, from one benchmark week (2 to 9 November 2026, 11,066 samples across every measure):[^window]

- A new sandbox was ready in 1.5 s at the median and 12.4 s at p95: the tail was 8 times the median, so plan for p95, not the median. A base-image create's p95 was 5.5 times its median.
- Measured from the create call, Factory Droid, Codex and Claude Code first replied in 2.9 to 3.4 s at the median.
- A timeout set from the median cancels creates that were about to succeed, so we set ours from p95.

These are live values, so read the [benchmarks page](https://tangle.tools/benchmarks/) for today's numbers.

## Files survive stop and resume, and a parked sandbox keeps them for 30 days

What happens to a stopped sandbox:

- **Files.** `stop()` keeps the filesystem and `resume()` brings every file back. The run below shows it.
- **Retention.** Without `deleteAfterStoppedSeconds`, the platform keeps a parked sandbox at least 30 days and may reclaim it after that. Set the field for a shorter life.
- **Secrets.** When the platform removes a stopped box's runtime, resume must supply your secret env values again. It throws `ResumeEnvRequiredError`, which names the missing keys.
- **Cost.** A stopped sandbox accrues no compute charge. The SDK README says compute, which covers vCPU, memory, disk and the hourly minimum, accrues only while the sandbox runs ([rate card](https://sandbox.tangle.tools/v1/pricing/sandboxes)).

<Example path="sandboxes/stop-and-resume" />

I got persistence wrong in the first version of this post, which implied that only a snapshot or a durable session kept files. Keep anything precious in a snapshot or your own repository.

## Branching copies the workspace into parallel attempts

Fan out from a snapshot or from a running box:

- **Snapshot, then create.** `box.snapshot()` saves the filesystem, and `client.create({ fromSnapshot })` starts new sandboxes from it. The fork took 1.85 s at the median.
- **Branch.** `parent.branch(n)` copies a running sandbox into n children. Sixteen children took 12.7 s at the median.
- **Memory.** The example's comment says memory is copied too. Our run shows files only, and we have not tested process state.

<Example path="sandboxes/branch-into-two" />

Both children saw the shared setup plus their own line. Branching is also the least reliable call we measured: in the Branching panel, 87 of 226 attempts failed. Snapshot-and-fork attempts failed 16% of the time. If you fan out four approaches today, we would fork from a snapshot and retry the failures.

## Run Claude Code, Codex or OpenCode inside the box

The whole loop is short:

- Clone the repository at create with `git: { url }`.
- Name the coding agent in `backend: { type }`: claude-code, codex, opencode or pi.
- Send the task with `box.prompt()`.
- Check the result yourself with `box.exec("npm test")`. The agent's own report of success is not the check.
- Keep model credentials on a trusted server: grant a stored one with `grantNativeCredential`, or route model calls through Tangle Router.

## You pay for compute by the hour and for model tokens per turn

We price compute per CPU core-hour, memory GB-hour and disk GB-hour, with a minimum hourly charge. Rates change, so read them from the [pricing endpoint](https://sandbox.tangle.tools/v1/pricing/sandboxes).

Model spend is billed separately. Each turn reports its token usage and its model cost. The test fix above cost $0.0145 in model spend, and most of its input tokens were cache reads. The browser task cost $0.02.

## Cap machines and spend before the fleet boots

Use the control that fits the job:

- **Fleet policy.** Hard caps on machines, concurrent creates, CPU, memory and spend, checked before the platform provisions anything. They sit under your account quotas, not in place of them.
- **Fleet budget.** The platform refuses any charge past it, mid-turn included.
- **`runBatch()`.** For one-off parallel tasks, it creates temporary sandboxes and removes them after the run.

This is the policy from the SDK README's fleet example. We have not run it.

```ts
  policy: {
    maxMachines: 3,
    maxConcurrentCreates: 2,
    maxTotalCpu: 6,
    maxTotalMemoryMb: 12_288,
    maxSpendUsd: 2,
    allowAccelerators: false,
  },
```

This recorded example sets a $2 hard cap and cancels every agent once the fleet has spent $0.20, checked from the client; the run stopped all six at $0.21 total.

## Expect failed creates, and retry with the same idempotency key

In the benchmark week, 56 of 425 create attempts failed, and so did 31 of 209 base-image lifecycle runs. Your code needs a retry path on day one:

- Pass an idempotency key on create, and reuse it only when retrying the same logical request.
- Let the SDK pace its own retries from the platform's retry-after value.
- Set create timeouts from the p95, not the median.
- For one sandbox per customer, call `client.instances.ensure()`. It creates, resumes or replaces a sandbox that was deleted or keeps failing to start. While it waits to replace a sandbox that keeps failing to start (60 s by default), it throws a restarting error with a retry delay.

<Figure n={3} kicker="Tangle sandbox benchmark, one week" headline="Between 13% and 16% of create, lifecycle and snapshot attempts failed; branching failed 38%." figure={failures} />

The benchmark does not say whether each failure came from the platform or from the benchmark's own client. Read these as failed attempts in our test, not a service level.

## Which sandbox should you pick?

Pick Tangle's sandbox when your agents need files across sessions, a fleet with a spend cap, and percentiles you can plan against. Ask for Firecracker before you run code from strangers, and confirm your account has it. If you need a microVM per session by default, E2B's default gives you one. If you must run on your own servers, Tangle does not fit yet. Whichever you shortlist, run the cold-start script with your own image on each, and decide on the p95.

## How we tested

- **Benchmark window.** 2 November 2026 16:25 UTC to 9 November 2026 16:25 UTC, from the data behind https://tangle.tools/benchmarks/. The window's 11,066 samples count every measure together; no single row has that many. Each figure's note gives its rows' sample and attempt counts. Failures are counted per panel attempt; the percentiles cover the steps that returned a timing.
- **Runtime.** The recorded examples set no runtime, so they ran on the platform default. The benchmark data does not record which runtime its runs used. Our one Firecracker box is the egress refusal run.
- **Egress.** The browser run used strict mode with the default allowlist plus the Playwright hosts and news.ycombinator.com; it proves listed domains pass. On 18 November 2026 we created two boxes with `egressPolicy: { mode: "blocked" }`, one with `runtime: "firecracker"` (sandbox-96e412dc6d06) and one on the default docker runtime (sandbox-5ca151905f1b). In each, `curl -sS -m 5 https://example.com` exited 7 with "CONNECT tunnel failed, response 403", and Node's `fetch` got status 403 from the egress proxy. Both boxes were deleted and read back as deleted. Strict-mode refusal of an unlisted domain has not been deliberately tested; the browser run's receipt shows one incidental refusal of storage.googleapis.com.
- **Recorded examples.** Each `<Example>` renders the example file with its production run receipt; the receipts' call lines and output match the files. All were recorded on 12 November 2026 with `@tangle-network/sandbox` 1.0.168, except `fleets/cancel-on-cap`, which was re-recorded on 18 November 2026 with 1.0.443 (tangle-website#547). The stop-and-resume run printed "first draft" after the resume. The branch run printed "shared setup" plus each child's line in both children. `fix-a-test` reported $0.0145 of model spend over 192,627 input tokens, 175,408 of them cache reads. `browser-task` reported $0.02. The E2B example has no run receipt; it is typechecked only.
- **One cold-start run.** `runtime/time-a-cold-start` on 12 November 2026: create 1,842 ms, first command 567 ms, delete 872 ms. One run is a smoke test, not a distribution.
- **Lifecycle extras.** Base-image stop took 1.2 s at the median. Resume took 4.7 s at the median and 10.7 s at p95. Fork a snapshot: 1.85 s at the median and 16.8 s at p95. The "Snapshots and checkpoints" panel, snapshot and fork together, failed 82 of 506 attempts.
- **Tail ratios.** For a new sandbox (Ready), p95 was 8.0 times the median; for a base-image create, 5.5 times. Other create rows in the data fall outside that range, such as a desktop-image create at 3.0 times and a large-size create at 22 times.
- **Stopped-sandbox billing.** From the `@tangle-network/sandbox` 1.0.447 README, read 18 November 2026: "A stopped sandbox accrues no compute charge". An earlier version of this post, through its example's comment, said a stopped sandbox bills for its disk; that was wrong. That comment, line 8 of the stop-and-resume example, was corrected on 17 November 2026 (tangle-website#545), after the example's 12 November run; the receipt's call lines and output still match the file; only that comment changed.
- **Rivals.** Daytona, Modal, Northflank and Beam figures are their own published claims, as linked from https://tangle.tools/compare/. Modal's half-second median is from its post of 16 July 2026. E2B's Firecracker microVM is from the same compare data. We have not run any rival through our benchmark.
- **SDK behaviour.** Runtime, credential, retention, retry, fleet-policy, batch and ensure behaviour is from the [`@tangle-network/sandbox` README](https://www.npmjs.com/package/@tangle-network/sandbox), version 1.0.440, read on 17 November 2026. The egress modes and `box.egress.update()` are from its typings.
