Ask an AI agent to verify a checkout flow.
It opens the store, fills a form, clicks “continue,” and reports success.
What did it see after the click?
Did the total change, did a validation message appear, or did the page stop loading while the model guessed?

**Browser automation for AI agents** is the practice of letting an agent operate a real browser while preserving enough page state and evidence to answer those questions.
The loop states a goal, observes the accessibility tree and a screenshot, performs one action, compares the new page with the expected state, closes a consent banner or retries a bounded step when needed, and stops at a named checkpoint.

This article uses a read-only checkout check so no payment is submitted.
The same mechanism applies to accessibility reviews, wallet flows, account settings, and end-to-end tests: observe the current state, take one allowed action, verify the checkpoint, and stop before an irreversible effect.

## What a browser agent can see

A browser exposes more than a screenshot.

The **DOM**, or Document Object Model, is the structured tree of elements that describes headings, links, buttons, fields, and their attributes.
An **accessibility tree** maps elements to roles and accessible names used by assistive technology.
It excludes visual styling.
A screenshot shows the visible layout at one viewport size and omits collapsed or off-screen content.

Each view answers a different question:

| Observation | What it answers | What it can miss |
| --- | --- | --- |
| DOM or accessibility tree | Which controls and text the page exposes | Visual overlap, hidden menus, and layout problems |
| Screenshot | What the user sees at one moment | Hidden labels and the precise element identity |
| Network and console logs | Which requests and browser errors occurred, such as an HTTP 500 or a stack trace | Whether the business action was accepted |
| URL and page state | Which route and form state are active | Whether the model interpreted the result correctly |

Choose evidence by the task’s final condition.
For a read-only search, a DOM excerpt and URL may be enough.
For a visual regression, add a screenshot.
For a payment or wallet flow, stop on the confirmation page, save a screenshot showing the total, and leave the signing or payment action to a person.

## Start with public discovery

Tangle Browser Agent publishes a [machine-readable manifest](https://tangle.tools/.well-known/tangle-browser-agent.json) and the scoped package [`@tangle-network/browser-agent-driver`](https://github.com/tangle-network/browser-agent-driver).
The manifest lists the `bad` command, its safe help commands, and the SDK exports.

```bash
npm install -g @tangle-network/browser-agent-driver
npx playwright install chromium
bad --help
bad run --help
bad snapshot --help
```

The help commands only parse the locally installed CLI metadata; they do not open a browser or send a request to a customer site.
Run them first to confirm which options the installed version exposes.
An actual task needs a model provider key to authenticate the model calls that plan and select browser actions, and it should begin with a public, read-only page.

## A published SDK example

The package exports a `PlaywrightDriver` that controls a Playwright page and a `BrowserAgent` that turns a goal into browser actions.
This example asks the agent to read a public page and return a structured result.

```typescript
import { chromium } from 'playwright'
import {
  BrowserAgent,
  PlaywrightDriver,
} from '@tangle-network/browser-agent-driver'

const browser = await chromium.launch({ channel: 'chrome' })
const page = await browser.newPage()
const driver = new PlaywrightDriver(page)

const agent = new BrowserAgent({
  driver,
  config: {
    model: process.env.BROWSER_AGENT_MODEL ?? 'gpt-5.4',
    observationMode: 'hybrid',
    plannerEnabled: true,
  },
})

try {
  const result = await agent.run({
    goal: 'Read the page title and confirm that the page is public',
    startUrl: 'https://example.com',
  })

  console.log({ success: result.success, reason: result.reason })
} finally {
  await browser.close()
}
```

The `hybrid` observation mode combines the accessibility tree with a screenshot.
`plannerEnabled` lets the agent make a short plan before it executes browser actions.
The goal is deliberately read-only, and the `finally` block closes the browser even when the run fails.

The [public repository README](https://github.com/tangle-network/browser-agent-driver) documents the remaining options, including test cases and output directories.
Keep the model key on the server or in the runner that owns the browser session.

## The evidence loop

A browser agent needs a record for every meaningful transition.

| Event | Record to keep | Why it matters |
| --- | --- | --- |
| Goal accepted | Goal text, start URL, and allowed actions | Shows what the agent was asked to do |
| Observation | URL, DOM or accessibility excerpt, and screenshot | Shows what the agent could see |
| Action | Action type, target reference, and input value | Shows what the agent attempted |
| Result | New URL, changed element, console output, or network status | Shows what changed after the action |
| Recovery | Failed assumption and replacement strategy | Shows why the agent tried something different |
| Stop | Stop reason and final page state | Shows why the run ended |

The [AI browser testing evidence guide](/blog/ai-browser-testing-evidence-traces) applies the same record to automated tests: goal, observation, action, result, recovery, and stop events.
For wallet-specific flows, see [natural-language testing for wallet apps](/blog/natural-language-test-automation-browser-agents).

## Recovery is part of the task

Real pages differ from the plan.
A cookie banner can cover a button, a date picker can render a different month, or a network request can return an error page.

When an observation does not match the expected state, the agent should:

1. Record the current screenshot, page state, and error.
2. Decide whether a safe alternative can reach the same checkpoint.
3. Try one bounded recovery, such as closing a consent banner or reopening a form.
4. Re-check the page instead of assuming the action worked.
5. Stop with the evidence if the checkpoint still cannot be reached.

The agent should not click random controls until a model says the page “looks right.”
An explicit retry limit and stop reason make a failed run useful to a reviewer.

## DOM, vision, or both

The right observation mode depends on the claim you need to make.

| Mode | Good for | Main limit |
| --- | --- | --- |
| DOM | Stable text, links, labels, and attributes | It cannot show whether a control is visually covered |
| Vision | Layout, screenshots, and visual state | Coordinates can drift and text can be misread |
| Hybrid | Tasks that need structure plus visual confirmation | It uses more observation data and needs a clear priority when views disagree |

For a checkout check, use the DOM to find the total and a screenshot to show the visible order summary.
For a design review, screenshots expose layout, overlap, and visual hierarchy that the DOM cannot represent.
For an accessibility review, make the accessibility tree and keyboard actions required evidence.

## Stop before the irreversible action

Browser agents can fill forms and navigate to a final confirmation page.
That does not mean they should click the final purchase, submit, or sign transaction without a separate approval.

Define the last safe checkpoint in the goal:

```text
Goal: Verify that a discounted order reaches the review page.
Allowed actions: open the public store, add the sample item, enter a test address.
Stop condition: capture the order total and review-page screenshot.
Forbidden action: submit payment or place the order.
```

The stop condition is a product rule, not a suggestion to the model.
The runner should reject an action outside the allowed set and record that rejection.

## Browser and Sandbox have different jobs

The browser holds page state and user-visible interactions.
The [Tangle Sandbox](/blog/ai-agent-sandbox) can hold the test files, parsers, and reports around that session.

For example, a test runner can save screenshots and DOM excerpts into a workspace, run a comparison script, and delete the workspace after copying the report to durable storage.
The browser session should still receive only the credentials and permissions required for the test.

## What a browser run does not prove

A browser run establishes only the page state observed for the tested inputs and session.
It does not prove that every account, device, locale, or network condition behaves the same way.
It does not prove that a business transaction was accepted unless the system records a confirmation from the service that owns the transaction.

Keep the tested URL, browser version, model, observation mode, inputs, screenshots, action log, and stop reason with the result.
Those fields let a reviewer distinguish a site failure, a model mistake, a network issue, and an incomplete test.

## The practical decision

Use Playwright alone when the flow is deterministic and the selectors are stable.
Use Browser Agent when a task needs a natural-language goal, page interpretation, recovery, or evidence capture.
Use both when deterministic assertions should anchor an agent’s flexible navigation.

Start with one public, read-only task.
Add authentication only after the evidence loop and stop condition work without secrets.

## Questions readers usually ask

### What is browser automation for AI agents?

It is browser control guided by a task goal, with observations, actions, recovery, and evidence recorded for review.

### Is a browser agent the same as Playwright?

No.
Playwright controls the browser.
A browser agent adds goal interpretation, observation choices, recovery, and a result record around that control layer.

### What should a browser agent capture?

Capture the goal, URL, browser version, page state, screenshot, actions, errors, final condition, and stop reason.

### How do I test a wallet or payment flow safely?

Use a test account and an isolated environment, define the last safe checkpoint, and require a person to approve any signing or payment action.
