During an afternoon review, an agent receives a private PDF and needs to produce a short summary before it can decide what to do next.
The team does not want to build a GPU service, a browser runner, and a payment system for one workflow.
It opens a service catalog and finds several names that sound close to the job.

The names are not enough.
Before sending the PDF, the team needs to know who receives it, what the service can access, what the result looks like, how payment works, and what happens when the service disappears halfway through the request.

That is the practical use of a public service contract.
A **Tangle Blueprint** is a public description of a service that another team can run.
The contract gives a caller a place to inspect the service before choosing who runs it.
The contract does not make every service safe or production-ready.
It gives the caller a place to ask the questions that a catalog name cannot answer.

This guide reads the catalog as a builder.
It follows one job from request to result, shows a small contract model in TypeScript, explains how to inspect the public SDK and source, and gives separate decisions for callers and operators.

## A Blueprint is a service contract

A **Blueprint** is a public description of a service that another team can run.
It names the jobs the service accepts, the inputs and outputs for each job, the resources it needs, the way a caller pays, and the evidence available after execution.

An **operator** is the person or service that runs the Blueprint.
The operator may provide a GPU, a browser, a protected machine, chain access, or another resource that the caller does not want to maintain.

A **job** is one request to a Blueprint.
For an inference service, the job might contain a prompt, model identifier, and output limit.
For a browser service, it might contain a URL, allowed actions, and a screenshot requirement.

The public [Blueprint SDK](https://github.com/tangle-network/blueprint) is a Rust toolkit for building these services.
The [Tangle documentation](https://docs.tangle.tools/) explains the network concepts and deployment choices.
The [public Blueprint catalog](https://github.com/tangle-network/awesome-tangle-blueprints) is a changing collection of examples, so its names are discovery aids rather than maturity labels.

If the word Blueprint still feels abstract, connect it to a familiar service boundary.
A normal API documents a route, request body, response body, and authentication method.
A Blueprint has to describe those application details plus the operator, resources, payment behavior, and result evidence that exist outside one company's API server.

## Three parties share one job

The service is easier to reason about when the responsibilities are separated.

| Party | What it controls | What it needs to know |
| --- | --- | --- |
| Caller | The input, acceptance policy, and retry decision | Which operator receives data and which result evidence is sufficient |
| Operator | The machine, credentials, runtime, and service process | What resources the job requires and what it must return |
| Network and payment path | Registration, service state, and payment records | Which service and operator the request refers to |

No party automatically supplies the others' missing decisions.
The network can record a payment without judging a summary.
An operator can return a summary without proving that the requested input was used.
The caller still has to decide what it will accept.

That division is useful because it prevents a single status label from carrying too much meaning.

## Start with the job you need

Reading a catalog from top to bottom creates the wrong kind of confidence.
Start with the job your application must complete and write down the contract it needs.

| Job family | Example request | Questions that decide whether it fits |
| --- | --- | --- |
| Model inference | Summarize a document or classify an image | Which model, context limit, data policy, and output checks apply? |
| Sandboxes and browsers | Run code or navigate a site for an agent | What files, network destinations, browser state, and credentials are allowed? |
| Training and data work | Train, transform, or evaluate a dataset | Which data is transferred, which hardware is needed, and how is the artifact checked? |
| Trading and chain work | Observe state or validate an action | Which block, market, or contract state is used, and what counts as success? |
| Cryptography and protected execution | Produce a key-dependent result or protect a secret | Which parties hold the keys, what evidence is returned, and how does recovery work? |

These categories tell you where to look.
They do not tell you that two services in one category have equal safety, speed, or cost.

For example, two inference services may both accept a prompt.
One may run a fixed model in a protected environment and return a signed output hash.
The other may forward the prompt to an unlisted provider and return only text.
The category is the same.
The caller's risk is not.

## Follow one job from request to result

Return to the private PDF.
The team could send it to a conventional hosted API, or it could request a summarization job from an operator-run service.

The caller should be able to answer each step below before integrating the service.

1. **Request:** What exact fields leave the application, and which fields are optional?
2. **Operator:** Which party receives the request, and what hardware or credentials does it control?
3. **Quote:** What price is offered, how long does it remain valid, and when does payment happen?
4. **Execution:** Where does the job run, and can it reach the public network, a browser, or other services?
5. **Result:** Which fields are returned, and how can the caller connect them to this request?
6. **Failure:** What happens on timeout, malformed output, operator outage, or a disputed result?

The quote and payment step deserves its own check.
The [x402 protocol](https://github.com/coinbase/x402) lets software authorize payment for an HTTP request.
An x402 receipt can show that a payment was authorized.
It does not show that the model produced a useful answer or that the operator followed the job's data policy.

The execution step deserves its own check too.
If confidentiality depends on protected hardware, read the [TEE explanation](/blog/trusted-execution-on-tangle) and ask how the report is tied to the job.
If the job needs a browser, compare its boundary with the [AI agent sandbox guide](/blog/ai-agent-sandbox).

## A job contract should be readable before code

The following object is an illustrative contract, not a copy-paste SDK type.
It shows the information a caller needs before choosing an operator.

```ts
type ServiceContract = {
  name: string
  input: string[]
  output: string[]
  resources: string[]
  evidence: string[]
  failure: string[]
}

const privateSummarizer: ServiceContract = {
  name: 'private-document-summary',
  input: ['documentBytes', 'language'],
  output: ['summary', 'inputHash', 'outputHash'],
  resources: ['confidential-compute'],
  evidence: ['attestation-report', 'input-output-binding'],
  failure: ['reject-expired-report', 'retry-on-timeout', 'human-review-on-low-confidence'],
}

function missingRequirements(contract: ServiceContract, required: string[]) {
  return required.filter((item) => !contract.evidence.includes(item))
}

console.log(
  missingRequirements(privateSummarizer, ['attestation-report', 'input-output-binding']),
)
// [] means the toy contract names both requested evidence items.
```

The example does not claim that every Blueprint needs an attestation report.
It shows why a service name is insufficient.
The caller can compare the contract's inputs, resources, evidence, and failure behavior with the risk of the job.

A good contract also makes an uncomfortable answer possible.
If a service cannot return input and output bindings, the caller can decide not to send a sensitive document.
If a service cannot say what happens after a timeout, the caller can keep it out of an automated retry loop.

## The public SDK gives builders a starting point

If you are building a Blueprint rather than consuming one, the public SDK README documents the current CLI path for creating a project.
The commands below are a starting point for an experiment, not a production deployment recipe.

```bash
cargo install cargo-tangle --git https://github.com/tangle-network/blueprint --force
cargo tangle blueprint create --name document-summary
```

The [Blueprint SDK repository](https://github.com/tangle-network/blueprint) is the source for current package names, release behavior, and examples.
Check the release and documentation state before copying a command into a long-lived build process.

A useful first Blueprint has one narrow job.
It has typed inputs and outputs, a resource list, an operator startup path, a result check, and a failure response that you can exercise locally.
Adding more jobs before those pieces are understandable makes the service harder to operate and harder for callers to evaluate.

The [Blueprint SDK deployment guide](/blog/blueprint-sdk-deployment-guide) covers the next step from a local service to an operator-run job.
The [Tangle re-introduction guide](/blog/building-ai-services-on-tangle) shows how inference and code execution fit into the wider service model.

## How to inspect a public Blueprint repository

Open the repository before you depend on the service.
The following inspection order keeps the review focused on decisions that affect your application.

### 1. Find the job contract

The public description should identify required fields, optional fields, size limits, output format, and any data that is stored or forwarded.

If you cannot describe the request and response without reading private implementation details, the service is not ready for an outside caller.

The contract should also say whether a job is read-only or can change state.
A document summary can usually be retried.
A trading or chain job may submit a transaction, and a retry can create a second action.

### 2. Trace the resource boundary

Look for the network, filesystem, browser, GPU, chain, and credential requirements.
An inference job that needs one model endpoint has a different risk from a browser job that can sign transactions.

The service should state which boundary is enforced and which boundary is left to the operator's environment.
“Runs in a container” is not a complete data policy.
You still need to know which mounts, network destinations, and credentials are available inside that container.

### 3. Read payment and retry behavior

Read when the quote expires, when payment is collected, how duplicate requests are handled, and what the caller receives after a timeout.
Do not assume a retry is free or idempotent.
An inference retry may cost twice.
A chain action retry may change state twice.

Write the retry rule in your application before you send the first paid request.
For example, a caller might retry a timed-out read-only summary once, while requiring human approval before retrying a transaction-producing job.

### 4. Identify result evidence

Find the smallest artifact that lets the caller decide whether to accept the result.
It might be an output hash, a signed receipt, a browser screenshot, a test report, a block reference, or a hardware attestation.

The evidence should be tied to the job that produced it.
An operator uptime signal alone does not prove that a particular response came from the requested input.

If the service returns only prose, your application may have no durable way to distinguish a correct result from a plausible one after the fact.

### 5. Read tests and maintenance instructions

Look for a repeatable local example, a versioned release, and a documented response to a failed job.
Read the tests for the job you plan to call rather than the tests for a neighboring module.

If the repository has no way to exercise the job or reproduce its result, treat it as an experiment and keep your integration small.
The missing test is a product risk, not a documentation inconvenience.

## The catalog is a map, not a maturity label

A catalog can help you discover that a service exists.
It cannot tell you that every entry has the same release quality, operator coverage, or result evidence.

The public [awesome-tangle-blueprints catalog](https://github.com/tangle-network/awesome-tangle-blueprints) changes as new services appear and old examples move.
Use it to create a shortlist.
Then open the source repository and inspect the exact release, job contract, tests, and operator instructions you would depend on.

The old version of this article used a catalog count in its title.
Counts age quickly and say little about whether a particular service fits your job.
The more durable question is whether you can explain the request, execution, payment, result, and failure path to another engineer.

## The operator has a different decision

An operator should choose a Blueprint by responsibility, not by catalog count.

Start with the resources you can provide safely.
A GPU may make an inference service practical, while a cryptographic service may require key custody, multiple parties, or a recovery plan you do not have.

Then estimate the work around each job.
Include startup time, storage, network egress, monitoring, failed requests, support, and the cost of keeping credentials available.

Finally, decide whether you can explain failures to callers.
An operator who can run a job once but cannot identify timeouts, stale quotes, malformed output, or lost state is not ready to take paid requests for it.

The strongest operator portfolio is the small set of services that can stay healthy and return evidence callers understand.

## A failure story is more useful than a feature list

Consider a service that quotes a fixed amount of ETH for the private summary.
The caller waits five minutes while a large PDF is processed.
The operator restarts the worker, the quote expires, and the caller retries with the same request.

If the service contract is clear, the caller can see that the first request has expired and that the second request needs a new quote.
If the service has no request identifier or payment status, the caller may pay twice while guessing whether the first job is still running.

The catalog entry may still describe the service accurately.
The missing lifecycle details make the integration unsafe.

This is why a Blueprint review should include one unhappy path before any production call.
Run a timeout, an expired quote, a malformed output, or an unavailable operator in a low-risk environment.
Record what the caller sees and what the operator must repair.

## When a hosted API is the better choice

An operator-run service is not automatically the right answer.

Choose a conventional hosted API when one provider already meets your data, uptime, latency, and compliance requirements and you do not need to choose the operator separately.
The hosted service may offer better support, a simpler billing relationship, or a more mature result contract.

Choose a Tangle Blueprint when the operator choice, resource boundary, payment path, or execution evidence is part of the application decision.
The extra flexibility comes with extra review work.
Your application must decide which evidence is sufficient and how it recovers from failure.

That tradeoff is the reason to read the contract before reading the catalog.

## A first integration should be deliberately small

Use three passes for a new service.

### Pass one: inspect

Read the public contract, release notes, tests, operator requirements, and result evidence.
Write down the one job you intend to call and the one decision that will accept or reject its output.

### Pass two: exercise

Run one low-risk request with a non-sensitive input.
Force one timeout or malformed result if the service supports a safe test mode.
Confirm that the caller can distinguish success, failure, and “still running.”

### Pass three: narrow the permissions

Send only the files, network access, credentials, and payment authority that this job requires.
Do not grant a browser or chain capability because another catalog entry might need it later.

This sequence turns a catalog candidate into a decision based on observed behavior.

## A practical decision rule

Use the catalog to find a narrow capability.
Use the public repository to inspect its contract.
Run one low-risk job before sending valuable data or authorizing meaningful payment.

Keep the integration only if you can answer these six questions in plain language:

1. What exact input leaves my application?
2. Which operator receives it, and what can that operator access?
3. What does the quote cover, and when does it expire?
4. What result fields can my application consume safely?
5. Which artifact lets me accept or reject that result?
6. What does my application do when the job fails?

If the Blueprint answers those questions, it is a candidate for a measured integration.
If it does not, the missing answer is more important than the catalog category.

## FAQ

### What is a Tangle Blueprint?

A Tangle Blueprint is a public service definition that an operator can run under Tangle network rules.
It describes jobs, inputs, outputs, resources, payment behavior, and result expectations.

### Are all Tangle Blueprints production-ready?

No.
The catalog contains services at different stages.
Inspect each repository's releases, tests, operator instructions, result checks, and failure behavior before depending on one.

### Why do Blueprints matter for AI agents?

Agents need capabilities beyond text generation, including browsers, sandboxes, training jobs, chain access, cryptography, and paid APIs.
Blueprints give those capabilities a service contract that an application can request and evaluate.

### Does an operator see the caller's private data?

That depends on the job's execution boundary and the operator's access.
Read the service's data policy and evidence design.
If confidentiality depends on protected execution, check the attestation and secret-release path before sending the data.

### How do operators choose which Blueprints to run?

Choose by hardware, data risk, expected demand, verification work, margin, and recovery responsibility.
Run only the services you can keep healthy and support when a job fails.

### Where can I find the current catalog?

The [awesome-tangle-blueprints repository](https://github.com/tangle-network/awesome-tangle-blueprints) is the public catalog.
It changes over time, so use it to find candidates and then inspect each Blueprint's source and release state.
